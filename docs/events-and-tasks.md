# 事件与任务（Events and Tasks）

> **适合谁**：想把跨小时的复杂工程交给 Pipiclaw 在后台自主推进，或安排定时提醒、工作日巡检与条件触发工作的用户。
> **读完你会得到**：如何用 `/tasks` 遥控后台项目（查看、插话、暂停、追加预算）、如何用 `/events` 设置单次提醒与周期巡检，以及两者的文件结构、预算守护与恢复机制。

Pipiclaw 通过两层职责正交的长程机制，从“被动应答的聊天框”变成“能按时唤醒、带着团队把项目做完的负责人”：

| 机制 | 存放在哪 | 解决什么问题 | 典型用法 |
|---|---|---|---|
| **后台任务（Tasks）** | `desk-<name>/tasks/<id>.md` + `<id>.jsonl` | **做什么、做到哪、在等谁**——承载一个一次性项目的目标、验收清单（DoD）、工作项与执行记录 | 跨多文件的接口改造、带独立审查的功能开发、长耗时排查 |
| **定时事件（Events）** | `desk-<name>/events/*.json` | **什么时候唤醒**——唯一的时间与传感器入口 | 一次性提醒、每周一早会提醒、带 `preAction` 脚本门控的每日仓库巡检 |

> 💡 **一句话分清**：**事件管时间，任务管项目，聊天频道只是遥控器。** 周期性的复杂工作（如每日巡检、周报）由**事件按 `task` 模板每次生成一个独立任务实例**，在后台任务车道里推进，绝不挤占你的日常聊天上下文。

---

## 第一部分：后台长程任务（Tasks）

当你在聊天里交办一项需要拆解步骤、派发子代理、反复验证并最终汇报的工作时，主智能体会创建一个后台任务。**任务在独立的「任务车道（Task Lane）」和专属会话中运行**——聊天回合不等任务步骤，任务步骤也不阻塞你继续聊天。

### 1. 从聊天管理任务（`/tasks`）

以下命令由运行时直接响应（零模型消耗），**即使当前聊天正在忙碌也可随时发送**，在绑定到同一工位的任意频道中均生效：

| 命令 | 说明 |
|---|---|
| `/tasks` | 列出本工位所有活跃任务：状态、实时活动、等待条件、工作项进度与累计用量 |
| `/tasks show <id>` | 查看单个任务的完整看板：状态、在途委派、工作项清单、最近记录与任务说明摘要 |
| `/tasks log <id>` | 查看最近 15 条任务执行记录（步骤结论、委派派发与结算、用户消息等） |
| `/tasks msg <id> <内容>` | **向任务传话或回答提问**：步骤执行中会在当前工具批次后直接送达，否则排入下一步 |
| `/tasks adopt <id>` | 将任务的汇报频道改绑为当前频道，并立即按序补发暂存的汇报、提问与回执 |
| `/tasks pause <id>` | 暂停任务：中止当前正在跑的模型步骤（已在途的外部委派继续运行，结果照常入账） |
| `/tasks resume <id> [+steps N\|+usd X]` | 恢复已暂停的任务；预算耗尽时可按增量追加上限（如 `/tasks resume export-api +steps 20 +usd 10`） |
| `/tasks cancel <id>` | 取消任务：**同时中止当前步骤、终止所有绑定的在途委派与后台作业**，并归档 |
| `/tasks archive` | 查看已归档的历史任务列表 |
| `/tasks doctor` | 诊断手工编辑导致的坏文件头、损坏记录、未完成归档或待重试投递（只诊断，不改写文件） |

> **注意**：`/stop` **只停止当前聊天回合**，不会暂停后台任务（聊天空闲时发 `/stop` 会列出本工位运行中的任务并提示 `/tasks pause`）。你也可以直接在聊天里用自然语言让助手查看进度、补充要求或回答任务提问。

### 2. 状态与等待

任务状态完全由运行时**根据客观事实自动推导写入**，模型没有任何参数能自行声明“我在等待”——从根源杜绝“显示在等、但其实没有任何东西能叫醒它”的假死状态：

| 界面状态 | 事实依据与唤醒条件 | 占用并发槽 |
|---|---|---|
| **排队中**（`queued`） | 等待任务车道释放空闲执行槽 | 否 |
| **执行中**（`running`） | 任务会话正在运行一个模型步骤（单步限时 20 分钟） | **是** |
| **等结果**（`waiting: work`） | 本任务绑定的子代理委派或后台作业仍在运行，结算或卡顿时立即唤醒 | **是** |
| **等你回复**（`waiting: user`） | 负责人通过 `task_ask` 向你提问。**不设超时**，仅由你的消息唤醒（期间回来的委派结果先记入日志，等你回复后一并呈现） | 否 |
| **等到 HH:mm**（`waiting: time`） | 负责人通过 `task_wait` 约定了下次检查时刻，到点唤醒 | 否 |
| **已暂停**（`paused`） | 由你手动暂停（`by: user`）或触发运行时守护规则暂停（`by: runtime`） | 否 |
| **汇报暂存 / 已冻结** | 汇报频道临时换绑到其他工位期间，**后台任务照常推进**，汇报、提问与回执暂存于 `tasks/.delivery/`（切回工位或 `/tasks adopt <id>` 后按 FIFO 补发）；仅当汇报频道缺失、工位已归档或所属渠道（如钉钉）关闭时车道才冻结步骤 | 否 |

运行时回执统一使用四类醒目标记：`✅` 完成、`⚠️` 需要你的决定（提问或异常提示）、`🛑` 暂停或取消、`⏳` 进行中。任务步骤默认静默，只有负责人显式调用 `task_report`（每步最多 3 条）、`task_ask` 以及运行时的确定性回执会发往汇报频道。

### 3. 团队看板与工作项

在任务会话中，负责人像技术组长一样通过看板协调子代理与后台作业：

- **自动归属与工作项绑定**：任务步骤内发起的 `subagent` / `subagent_inline` 与 `bash async` 后台作业自动绑定到本任务，可通过 `item: "W2"` 关联具体工作项。每次派发与结算自动写入 `tasks/<id>.jsonl`，成本计入任务总预算，结果直接唤醒任务车道（不打扰聊天频道）。
- **增量输入与按需上下文**：仅首步（及会话压缩或契约修改后）注入完整任务说明；后续步骤只注入新增的 `<task_inputs>`（委派结果、卡顿告警、你的传话）与 `<task_board>`（工作项状态与产物路径），大幅节省长程 Token 消耗。
- **外部卡顿主动唤醒**：绑定的外部 Coding Agent 若连续 **10 分钟无任何输出**，运行时会在任务记录写入卡顿报告并唤醒负责人，由负责人查看 `stderr` 后决定继续等待还是取消重派。
- **独立检查（`purpose: verify`）**：委派检查者按只读/验收协议核查产物并以 `VERDICT: PASS|FAIL` 收尾，结论展示在看板上供负责人裁决（`VERDICT` 是决策证据而非机械门禁；需结构性只读时应选用 `codex-review` 等带 CLI 沙箱的角色）。

### 4. 任务文件与契约格式

工位下的任务目录结构如下（已关闭任务自动移入 `archive/`）：

```text
workspace/desk-<desk>/tasks/
├── export-api.md          # 任务说明（契约：Frontmatter 归运行时，正文归负责人）
├── export-api.jsonl       # 追加式任务记录（步骤、派发、结算、传话、汇报）
├── .sessions/             # 每个任务独立的模型会话 JSONL
├── .delivery/             # 待确认送达的汇报与回执（断线/重启自动退避重试）
├── .closing/              # 归档事务快照（崩溃恢复用）
└── archive/               # 已完成或已取消任务的说明与记录归档
```

`tasks/<id>.md` 示例（正文控制在约 4KB 以内）：

```markdown
---
state: waiting
waiting: {"kind":"work","since":"2026-10-04T14:40:00+08:00"}
channel: dingtalk:group:cidXXXX
usage: {"startedAt":"2026-10-04T14:02:11+08:00","steps":6,"usd":3.4,"usdEstimated":true}
budget: {"steps":60,"usd":30}
---

# 导出接口改造

## Goal
为订单服务新增 CSV 导出接口（说明目标、范围、允许的外部动作与关键约束）。

## DoD
- [ ] /export 接口返回符合字段规范的 CSV
- [ ] 新增单测覆盖空结果与超大结果
- [ ] npm run check 通过

## Work Items
- [x] W1 调研现有序列化与分页实现
- [ ] W2 实现导出接口与单测
- [ ] W3 独立审查 W2 的实现
```

- **工作项四态**：`[ ]` 待办、`[x]` 完成、`[!]` 受阻、`[~]` 放弃。只有负责人核实证据后才能将条目勾选为 `[x]`。
- **完成条件**：`DoD` 存在且全部勾选、`Work Items` 无待办（`[ ]`）或受阻（`[!]`）项、无在途委派或作业，且当步的最终 `task_report` 已确认送达后，`task_close` 才会正式归档并由运行时附上历时、步数与费用统计。
- **两套模型工具面**（由 `tools.json` 的 `tools.tasks.enabled` 总开关控制，默认开启）：
  - **聊天会话**：`task_list`、`task_create`、`task_log`、`task_close`、`task_message`、`task_pause`、`task_resume`
  - **任务会话**：`task_log`、`task_close`、`task_report`、`task_ask`、`task_wait`（任务会话内无 `task_create`、`memory_save`、`event_manage`）

### 5. 预算、守护与并发恢复

- **并发执行槽**：每个工位最多同时运行 **3 个**占槽任务，整个 Pipiclaw 实例最多 **5 个**（仅 `执行中` 与 `等结果` 占槽，其余状态不占；满槽时新任务自动排队）。Git 仓库内并行写委派推荐传 `worktree: true` 自动使用独立工作树；主会话与任务步骤的 `write` / `edit` 也会自动检查活跃的写租约与验收读租约以防并发踩踏（`bash` 命令仍共享工作树，请注意避让）。
- **项目预算与自动熔断**：默认上限为 **`steps: 60`（模型步数）** 与 **`usd: 20`（已知归因美元成本，含绑定委派）**。不报告美元成本的外部执行器（如 `codex-cli`、`cursor-cli`、`antigravity-cli`、`exec`）单独累计 `unknownCostCount` 并明确提示，不冒充零费用。命中以下任一守护规则时，运行时自动暂停任务并推送带恢复命令的回执：
  - **超预算**：开启新步骤前任一维度达上限；
  - **连续空转**：连续 2 个正常结束的步骤未调用任何工具；
  - **单步超时**：单步满 20 分钟请求中止，连续 2 次超时暂停；
  - **连续报错**：前两次出错分别退避 1 分钟、5 分钟重试，连续 3 次出错暂停。
- **崩溃与重启对账**：daemon 重启后自动扫描所有活跃任务，为中断步骤补写记录并按真实在途工作重算状态（零模型消耗），未送达的汇报/提问按 1–15 分钟退避继续重试，最长每 15 分钟全量巡检兜底。

## 第二部分：定时事件与周期巡检（Events）

工位目录 `workspace/desk-<name>/events/*.json` 中的每个 JSON 文件代表一条定时事件。运行中的事件监听器会自动加载、热更新并在到点时触发：纯文本（`text`）提醒仅在 `channelId` 仍绑定于本工位时投递（未绑定记 `channel_not_bound` 跳过）；任务模板（`task`）事件即使投递频道临时换绑到其他工位也会照常在后台立项推进，汇报暂存待切回送达（工位归档时停止定时事件）。

### 1. 管理入口与 `/events` 命令

日常最省心的做法是**直接在目标频道里让助手帮你创建或修改事件**——助手调用 `event_manage` 工具会自动绑定当前频道 ID，并在落盘前完成 Cron 密度、结构与安全命令校验（避免手写错格式被监听器静默清理）。

你随时可以用 `/events` 命令直接查看或删除工位内的事件（不调用模型）：

| 命令 | 说明 |
|---|---|
| `/events list` | 列出本工位全部事件的文件名、类型、目标频道、计划时间与内容预览（跨频道事件会标出频道名，定义无效会提示原因） |
| `/events show <name>` | 查看 `events/<name>.json` 的完整 JSON 定义（后缀 `.json` 可省略） |
| `/events delete <name>` | 删除指定事件文件（仅停止后续触发；若该事件已生成过未结束的任务实例，需另用 `/tasks` 处理） |
| `/events history [name]` | 查看最近的调度审计记录（可按事件名过滤） |

> **防自激励保护**：无论通过 `event_manage` 还是手工编辑，运行时均禁止 `immediate` 立即触发类型；新建 `one-shot` 至少提前 **2 分钟**（上限约 24.8 天）；普通 `periodic` 最密每 **30 分钟**一次，挂载 `preAction` 脚本门控时放宽至最密每 **5 分钟**一次；单工位上限 **50 个**事件文件。

### 2. 两类事件与字段规范

所有事件共用字段：`type`（`"one-shot"` 或 `"periodic"`）、`channelId`（如 `dingtalk:dm:<staffId>`、`dingtalk:group:<cid>`、`webapi:conv_<id>`，可在 `workspace/CHANNELS.md` 查阅）、`text` 或 `task`（**二选一**），以及可选的 `preAction`。

#### 单次事件（`one-shot`）

在未来指定时刻触发一次，触发成功后自动删除 `.json` 文件（建议 `at` 明确带时区偏移如 `+08:00`；若停机期间错过触发点，重启恢复后会补执行一次）：

```json
{
  "type": "one-shot",
  "channelId": "dingtalk:dm:your-staff-id",
  "text": "提醒我检查今天下午的发布监控与回滚指标。",
  "at": "2026-10-03T18:00:00+08:00"
}
```

#### 周期事件（`periodic`）

按五段 Cron（`分 时 日 月 周`，**统一按宿主机本地时区解释**，不设 `timezone` 字段）循环触发，不会自动删除，修改保存后立即热重载：

```json
{
  "type": "periodic",
  "channelId": "dingtalk:dm:your-staff-id",
  "text": "整理今天最需要跟进的待办；如果没有异常需要汇报，只回复 [SILENT]。",
  "schedule": "0 9 * * 1-5"
}
```

- **常用五段 Cron 速查**：`0 9 * * 1-5`（工作日每天 09:00）、`0 18 * * 5`（每周五 18:00）、`30 10 1 * *`（每月 1 日 10:30）。
- **无事静默（`[SILENT]`）**：文本型周期事件在无异常需要汇报时，可指示助手仅返回 `[SILENT]`，运行时将静默结束本轮、不向聊天刷屏。

### 3. 事件动作门控（Action Gate）

在唤醒大模型之前，可通过可选的 `preAction` 先跑一段确定性本地脚本（受 `security.json` 的命令守卫约束，默认超时 `10000` 毫秒；工具参数中写 `timeoutMs`，落盘字段为 `timeout`）：

- **退出码 `0`**：条件成立，正常入队唤醒大模型或生成任务实例；
- **非 `0` 退出码或超时**：条件不满足，**静默跳过当次触发，零 Token 消耗**（下次 Cron 照常评估）。

示例——仅在脚本判定今天是“本周最后一个工作日（考虑节假日调休）”时才触发周报提醒：

```json
{
  "type": "periodic",
  "channelId": "dingtalk:dm:your-staff-id",
  "text": "现在是本周最后一个工作日下午，请帮我汇总本周工作要点。",
  "schedule": "0 16 * * 1-5",
  "preAction": {
    "type": "bash",
    "command": "node ~/.pipiclaw/workspace/skills/check-last-workday.js",
    "timeout": 10000
  }
}
```

### 4. 任务模板事件：周期性复杂工作

需要多步排查、委派子代理、对照验收清单交付报告的周期性工作（如每日仓库巡检、每周发布复盘），应使用 `task` 字段替代 `text`。每次到点（且 `preAction` 通过后），运行时会：

1. 按 `<事件名>-<YYYYMMDD>-<HHmm>` 幂等生成独立任务实例（`origin` 记录来源事件名），交由后台任务车道执行；
2. **防重入重叠**：若该事件上一轮生成的任务实例尚未结束（含已暂停或等你回复），本次**不生成新实例**，而是向频道发送一条提示回执，引导你先用 `/tasks show <id>` 处理上一实例；
3. **跨周期基线交接**：新实例首步会自动参考上一已归档实例的收尾备注与最终汇报，实现增量对比。

#### 完整模板示例：工作日只读仓库巡检

保存为工位下的 `events/daily-repo-review.json`（替换 `channelId` 与目标仓库绝对路径，或直接发给助手用 `event_manage` 创建）：

```json
{
  "type": "periodic",
  "channelId": "dingtalk:dm:your-staff-id",
  "schedule": "0 9 * * 1-5",
  "task": {
    "title": "本地仓库只读巡检",
    "goal": "只读检查 /home/you/projects/example 的本地 Git 分支、HEAD、提交记录与未提交改动摘要（严禁修改文件、fetch 或运行构建脚本）。首次运行概览最近 5 条提交建立基线；后续参考上一实例收尾备注对比新增变化（分支变更或基线失效时如实说明并重建基线）。每次通过 task_report 交付简短报告，并在收尾备注写明本次检查时刻、分支、HEAD 与待持续观察项。",
    "dod": "- [ ] 已核实仓库路径、当前分支、HEAD 与工作区状态\n- [ ] 已对比上一可用基线的变化（首次或基线失效已说明）\n- [ ] 已通过 task_report 交付本轮报告，并留好下一轮基线收尾备注",
    "budget": { "steps": 6, "usd": 2 }
  }
}
```

> `budget` 是**每次生成实例**的独立预算。任务模板使用 `task_report` 汇报结果，不使用文本事件的 `[SILENT]` 规则。

### 5. 可靠投递与调度审计记录

- **至少一次投递（At-Least-Once）**：事件触发后先持久化写入 `${PIPICLAW_HOME:-~/.pipiclaw}/state/dispatch/` 再入队执行；进程中途退出或重启后会自动重放租约过期的记录，因此涉及外部副作用的操作应具备幂等性。长期后台事件与任务需运行常驻 daemon（无 daemon 时仅在 `pipiclaw tui` 打开期间生效）。
- **调度历史日志**：每次文件加载、触发、`preAction` 放行/拦截、入队或跳过均追加记录在 `${PIPICLAW_HOME:-~/.pipiclaw}/state/events/history.jsonl`（本地时区时间戳，仅保留文本摘要以保护隐私），可直接通过 `/events history [name]` 查阅。
