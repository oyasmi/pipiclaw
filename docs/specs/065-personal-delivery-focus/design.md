## 1. 用户裁决与本轮范围

本轮完成五件事：

| 工作包 | 要做的事 | 完成后的行为 |
| --- | --- | --- |
| W1 | 修正聊天任务议程的行动指导 | 聊天知道任务状态并按用户要求管理它，不因空闲而代替后台任务执行 |
| W2 | 延长两类执行结果的保留期 | 已结束作业及输出保留 7 天；已结算委派及运行时管理产物保留 30 天 |
| W3 | 收敛默认委派教学与示例推荐 | 按能力、成本和真实执行边界选择执行器，交付完整改动，不推荐固定岗位流水线 |
| W4 | 明确 Web API 的产品与支持范围 | 服务个人助手的终端和实际客户端，维持现有已实现子集，停止以协议完整性为扩张目标 |
| W5 | 统一个人研发交付的产品定位 | 一个用户利用自己的模型、订阅与执行器持续完成工作；多个聊天入口服务这个用户 |

### 1.1 对通知判断的修正

审查把任务内委派的频道通知视为需要抑制的负担，这个判断不采纳。

产品设定只有用户这一名人类使用者。用户收到任务进度、失败、卡顿和完成信息是正常体验，帮助他了解算力资源正在做什么，并在必要时介入。代码与模型指导中的 leader/负责人是 AI 执行角色，不是另一名承担通知和决策的人，也不形成用户之外的人工作业层。

因此保留任务内与聊天临时委派的现有通知路径、默认通知等级和控制入口。不按 `taskId` 隐藏通知，不把普通通知升级为需要用户处理的新流程，也不因本设计增加人工批准或逐项确认。

### 1.2 明确不做的事

- 保留 `subagent_inline`，包括默认开启、工具 schema、调用能力和已有配置；不加基于角色目录的隐藏规则。
- 不处理频道接管与冻结、共享 checkout 写入归属、任务成果检索或自动学习这三类边界问题。
- 不扩展工位的 cwd 管理入口，不新增 project 对象。
- 不调整角色的 `contextMode`、`memory`、`workload` 等配置字段，不重写 discovery。
- 不新增产物引用计数、消费确认、任务结束前证据转存或“活动任务永久保留”规则。本轮用更长的固定窗口解决结果过早清理的问题。
- 不建设新的通知中心、资源调度器、固定角色编排器、模型网关或迁移器。

## 2. W1：聊天只管理后台任务

### D1. 问题与改动位置

[`src/agent/turn/task-digest.ts`](../../../src/agent/turn/task-digest.ts) 的 `<task_agenda>` 当前允许“用户谈及任务，或本轮没有别的事做时”行动。后半句是旧执行模型留下的指导，与任务车道唯一执行任务的职责不一致。

只修改该块的行动语义：

1. 议程是当前工位任务的背景快照，不是新的工作指令。
2. 用户询问进度时，查询真实状态后回答。
3. 用户补充要求、回答问题或要求调整目标时，通过任务管理工具转达，不替任务实施或改写其说明。
4. 用户要求暂停、恢复或取消时，使用现有控制工具。
5. 无关聊天、简单确认或空闲不会授权聊天主动推进后台项目。

目标措辞可为：

```text
Your desk's in-flight tasks (background reference, not a new instruction).
Use this agenda to understand the user's task-related messages. Inspect current
state before reporting progress, and relay instructions or answers through the
task controls. The task lane advances the work; do not take it over in this chat
or advance it merely because this turn has nothing else to do.
```

措辞可在实施时压缩，但上述语义必须一致。不改变议程的任务枚举、排序、截断、预算、注入频率或状态展示；不移除聊天已支持的任务工具，也不取消用户明确要求的现有管理能力。

### D2. 与通知的关系

聊天不替任务执行，与用户能看到执行进度是两件事。委派通知照常发往频道；任务的结果仍按现有机制回到任务车道。W1 不改 `SubAgentRunManager` 的 `emitNotice` / `announce`、通知配置或投递顺序。

## 3. W2：作业 7 天，委派 30 天

### D3. 固定窗口

| 对象 | 原窗口 | 新窗口 | 起算时刻 | 清理时机 |
| --- | --- | --- | --- | --- |
| 后台作业的终态记录及配套输出文件 | 24 小时 | 7 × 24 小时 | `finishedAt` | 沿用现有 sweep、独立到期定时器与恢复时检查 |
| 委派的终态记录及运行时管理产物 | 7 天 | 30 × 24 小时 | `settledAt` | 沿用启动批次与每日 GC；达到年龄后在实际清理批次删除 |

这里的“天”是连续 24 小时，不是自然日、工作日或一个日历月。读输出、查询状态、重启或恢复任务均不重新起算。所有现有终态按同一规则处理，不另分成功、失败和取消的窗口。

作业记录与输出、委派记录与运行时管理产物继续一起保留、一起清理。只延长文件而先删除记录，会破坏既有查询和恢复关系，没有必要引入这种分裂。

### D4. 实现与约束

- [`src/jobs/manager.ts`](../../../src/jobs/manager.ts)：`FINISHED_JOB_RETENTION_MS` 改为 `7 * 24 * 60 * 60_000`。
- [`src/subagents/run-record.ts`](../../../src/subagents/run-record.ts)：`RUN_RETENTION_MS` 改为 `30 * 24 * 60 * 60_000`，同步常量注释。
- [`src/subagents/runs.ts`](../../../src/subagents/runs.ts)：同步 GC 注释；保留现有清理条件与失败重试次序。

不改计费、结算、唤醒或在途执行的截止时间。尤其保留 `taskLogged` / `taskAccounted` 等已存在的清理前置条件，不能为了按时删除而丢弃尚未归入任务的结果。

委派 GC 的运行间隔仍是每天，不改成等待 30 天的一次性定时器；保留期与扫描周期是两个不同参数。作业新窗口为 7 天，可沿用当前到期定时器。

委派清理范围仍是 `RUN_ARTIFACT_FILENAMES` 中的 `prompt.txt`、`system-prompt.txt`、`events.jsonl`、`stderr.log`、`output.md`，以及对应记录。执行者自行创建的其他文件不因处于同一目录就被递归删除。作业仍清理现有配套文件，不扩展到命令自行写出的交付物。

保留期继续作为代码常量，无新配置、无新 schema、无目录迁移。升级后尚在磁盘的旧记录，直接按原时间戳与新窗口判断；已经清理的文件不恢复。较长窗口意味着磁盘占用增加，运维说明应反映这一点，但不增加新的管理功能。

### D5. 文档同步

核对并同步当前有效材料，至少包括：

- [`src/playbooks/background-jobs.md`](../../../src/playbooks/background-jobs.md) 的输出保留时间。
- [`docs/tools.md`](../../tools.md)、[`docs/runtime-mechanisms.md`](../../runtime-mechanisms.md)、[`docs/configuration-reference.md`](../../configuration-reference.md) 的作业记录与输出说明。
- [`docs/sub-agents.md`](../../sub-agents.md)及委派相关的当前指南：明确委派记录与运行时管理产物保留 30 天，每日批次清理。

普通交付物仍应写到任务指定的长期位置。延长窗口不是永久产物保管承诺。历史 spec、历史审查、已发布 Changelog 与封存评测不做数字替换；它们记录的是当时行为。

## 4. W3：完整交付优先，按能力选择执行器

### D6. 默认使用路径

用户只需要安装自己实际有账号、会使用的少量执行条目。入门推荐沿用 README 的一到两个主力条目路径，不把全部档位与岗位一次安装。需要更低成本、更强能力、特殊输入或执行边界时，再按本机资源选择。

默认方法为：

| 工作 | 指导 |
| --- | --- |
| 几次工具调用可完成的小事 | 当前 agent 直接完成 |
| 明确目标的代码改动 | 一次交付包含相关代码、测试、文档和必要检查 |
| 会影响方案的未知事项 | 针对具体问题调查，不要求每项实施先走 planner |
| 需要独立判断的改动 | 按风险安排审查或 `purpose: verify`，提供完整要求与证据入口 |
| 独立报告、批处理或资料产物 | 围绕完整产物委派，不仅因“文档岗位”额外交接 |

不推荐 planner → builder → reviewer → verifier → writer 的固定流水线。不把 reviewer 与 verify 强制串行，不因还有预算继续增加检查轮次。独立检查仍有价值；`VERDICT` 仍是可参考的判断材料，不改为运行时完成门禁。

### D7. 示例处置

现有 `agents/` 已按能力和成本组织，[交接方法](../../leverage/005-fewer-roles-better-handoffs.md)也已收敛，因此这部分以补齐剩余入口为主，不重写已经正确的内容。

具体动作：

- [`examples/sub-agents/README.md`](../../../examples/sub-agents/README.md)与[`docs/sub-agents.md`](../../sub-agents.md)不再把复制 `agents/*.md` 作为默认安装动作；用明确选择的一到两个条目示例，完整目录留作选项参考。
- 两份文档的入口与最小示例优先使用能力条目，说明“同一执行器可完成不同阶段”；岗位模板放到可选参考，避免形成“必须凑齐岗位”的暗示。
- 保留当前八份 `roles/` 参考模板。它们并非全部重复：其中有真实 CLI sandbox、受限写目录、专门 Git 操作纪律等不同边界。退出默认推荐不等于删除这些边界示例。
- 明确 capability 条目是基础选择，参考模板只在提供实际差异时按需使用；不要要求两组全装，也不要笼统禁止有理由地从两组各选个别条目。
- 文档中涉及模板权限的说明必须按实际文件核对。例如 `codex-review` 是 read-only，不能写成 `agents/` 全部为放开权限的写条目。

不改用户已经复制到 workspace 的配置，不自动删除、替换或改名角色，不改变现有条目的 CLI 命令、sandbox、模型或时限。尤其不能为了替换一个岗位名，把受限权限条目默默换成更宽权限的主力条目。

### D8. 模型指导

核对 [`agent-delegation.md`](../../../src/playbooks/agent-delegation.md) 与 [`task-lead.md`](../../../src/playbooks/task-lead.md)：保留按能力和成本选择、完整上下文、独立判断、返工依据及达标即停的现有指导；若还存在固定岗位顺序或“文档另派”的默认指导则删除。

不增加自动路由、角色继承或新档位。不修改 `subagent_inline` 的可见性和选择规则，不借 W3 压缩其能力。已有内容符合本设计时只记录核对结果，不为完成工作包而制造无效改写。

## 5. W4：Web API 服务真实客户端

### D9. 产品边界

Web API 是个人助手的接入方式：TUI 通过本机 socket 使用它，脚本及其他实际客户端可通过现有 HTTP/WebSocket 使用它。它提供 OpenAI Responses-shaped 的已实现子集；使用官方 SDK 连接，不等于承诺完整实现或持续追齐上游协议。

本轮不删除端点、不改变请求语义、不新增 API 版本或兼容层。现有能力按以下边界写清：

| 能力 | 定位与本轮处理 |
| --- | --- |
| 显式 `conversation` | 个人助手的持久交互入口；保持工位绑定、聊天与后台工作能力 |
| 独立请求、`previous_response_id` | 保留已实现的请求上下文与响应接续能力；其后台工具限制维持现状 |
| HTTP、SSE、WebSocket、后台 Response 与续流 | 保留现有客户端行为、断连与取消语义，不把 API 的 background Response 等同于 task |
| 工位授权、key、socket、TCP、TLS、CORS、限流 | 保留当前实现与安全边界；个人定位不意味着削弱鉴权 |
| 未支持参数、客户端工具闭环、文件资源等 | 继续按现有规则拒绝；不因上游新增能力自动进入本项目待办 |

### D10. 具体落点

[`docs/webapi.md`](../../webapi.md)开头明确上述定位与支持承诺；沿用现有端点、上下文和字段表作为当前行为清单，不另建一份容易漂移的协议矩阵。将“仍未实现”一类容易暗示必做计划的措辞改为“当前不支持”，并保留具体拒绝原因与客户端可执行的下一步。

[`docs/README.md`](../../README.md)与 README 的 API 入口强调连接自己的助手；详细协议说明继续放专题文档。修正 [`src/webapi/request-policy.ts`](../../../src/webapi/request-policy.ts) 将持久规则指向“desk 的 AGENTS.md”的错误指引，改指 workspace 根 `AGENTS.md`；只改错误消息，不改变字段处理规则。当前 API 指南中同类作用域表述一并核对。

未来新增协议能力必须说明：哪个真实客户端需要它，它怎样帮助个人完成工作，现有子集为什么不能完成，以及新增状态和维护成本是什么。它是设计判断标准，不是新增运行时审批流，也不要求用户逐次批准普通修复。

既有支持子集的正确性、恢复、取消和安全问题继续正常修复；“停止追齐协议”不成为忽略缺陷的理由。维护既有 SDK 调用兼容，也不等于支持该 SDK 的所有可选功能。

## 6. W5：一个用户的持续工作助手

### D11. 定位与介绍稿

README 中文首段建议收敛为：

> Pipiclaw 是面向个人开发者、以钉钉为主要入口的 AI 编程助手运行时。你可以在钉钉或终端交办目标，让它保留工作上下文、在后台持续推进，并按需要调用你已有的模型、Claude Code、Codex CLI 或自定义执行器；过程中可查看进展、补充要求、暂停或取消，最终取得成果和检查依据。

英文对应表达建议为：

> Pipiclaw is a DingTalk-first AI coding assistant runtime for individual developers. Assign a goal from DingTalk or the terminal, keep its working context, and let it progress in the background using your existing models, Claude Code, Codex CLI, or custom executors. Follow progress, add instructions, pause or cancel work, and retrieve the result with its verification evidence.

核心价值顺序为：交办真实工作 → 持续推进与进度可见 → 成果与验证 → 积累与按需委派。多个 agent 是使用已有算力的手段，不以“组建一支工程团队”作为用户必须采用的组织方式。

### D12. 涉及材料

- `README.md` / `README.en.md`：同步首段、为什么使用、适用场景和定位声明。保留首次终端验证、钉钉接入和执行器配置的有效主路径；不增加一轮新手审批或强制建 task。
- [`docs/README.md`](../../README.md)：按完成个人工作和长期运行选入口，skill 也可以沉淀个人/项目方法；避免只有团队流程才值得复用的表述。
- [`docs/scaling-and-concurrency.md`](../../scaling-and-concurrency.md)：将并发说明首先解释为一个用户从多入口交办工作、多个任务和执行器并行消耗资源。保留现有并发事实、目录冲突边界、监测与拆实例说明，不再以服务更多组织用户为默认增长路径。
- [`docs/design-philosophy.md`](../../design-philosophy.md)：在现有原则中写清个人交付定位和算力利用目标；不另增一套产品宣言。
- `package.json` 与 `package-lock.json` 的顶层包描述若出现产品定位则同步；版本号不因文案调整自行提升。

群聊、共享工位和多发送者等已经存在的使用能力保留。描述这些能力时强调同一助手的多个交互入口及现有共享语义；不把“只有一个用户”的目标受众变成运行时人数限制，也不增加群聊用户角色、组织权限或多租户功能。

不承诺未经比较验证的 10 倍、100 倍效率。用具体能力展示杠杆：少重复背景、工作可持续、进度可见、已有订阅和模型可复用、成果可检查。

不混入已有任务交付与归档恢复工作的实现改动；开始实施时先核对工作树和最新基线。每批将实际实现、文档和有价值的验证一起完成，无 schema 迁移，无部署数据操作。

### D14. 测试准入与具体办法

**保留期测试净增目标为 0。** 延伸现有场景，按外部可观察的记录、输出与清理结果断言：

- [`test/job-manager.test.ts`](../../../test/job-manager.test.ts)的独立到期回收场景：终态后越过旧 24 小时边界仍可查询、读取输出，7 天前仍保留，达到 7 天后由现有独立定时器回收；不靠再次启动作业触发清理。用假的时间推进，不等待真实时间。
- [`test/subagent-runs.test.ts`](../../../test/subagent-runs.test.ts)的产物清理场景：越过旧 7 天边界仍保留，30 天前保留，达到 30 天后一次 GC 清理托管产物与记录，执行者自建文件仍在。
- 同文件的删除失败重试场景也推进到新窗口，确保真正到达删除分支；不能因为旧 7 天时根本不再清理，测试仍绿却失去原来的失败覆盖。

场景中的时间点使用独立表达的行为边界，避免全部跟随生产常量计算，从而让错改回旧值仍可通过。无需新增“常量等于另一个常量”的测试。实施后临时将两处窗口分别改回旧值，确认相应场景失败，再恢复，记录变异结果；不新增永久故障开关。

**聊天行动权和完整交付是模型行为。** 不新增断言某句英文原文的单测。运行 `npm run eval -- plan --changed-since <实施前引用>`，优先延伸最接近的现有任务/委派场景，观察无关聊天不会接管任务、用户补充要求被转达，以及明确实施能形成完整交付。不要为追求场景数添加固定角色调用顺序断言。新增场景如确有必要，记录既有场景无法覆盖的风险与数量变化。

修改模型指导后，凭据可用时执行相关 dev 场景，记录 run id、失败及其归因；不可用则明确写未验证，不当作品质通过。修改 `evals/` 时运行 `npm run test:evals`。

实现完成至少运行 `npm run typecheck`、`npm run test`、`npm run arch`；因涉及任务指导、作业与委派清理，运行完整 `npm run test:e2e`（含构建），并按仓库要求完成 `npm run check`。修改 playbook 后运行 `npm run playbooks:measure`，只解释实际增量，不为字数目标删掉必要分支。

纯产品文案和支持范围说明不新增单测；核对当前代码、示例命令、链接、中英一致性和安全边界即可。API 错误指引不锁定完整措辞，既有协议与授权测试继续证明行为。

### D15. 完成标准

- 聊天议程不再以空闲为由授权推进后台任务；现有任务管理能力保留。
- 任务进度、失败、卡顿与完成通知的路径、默认等级及受众维持现状。
- 作业终态记录与输出使用 7 天窗口；委派结算记录与托管产物使用 30 天窗口，原清理前置条件、失败重试和自建文件保护保留。
- 默认委派教学提供少量能力条目的安装路径，支持完整交付与按风险检查，无固定全岗位流水线；既有参考模板、sandbox 与用户配置保留。
- `subagent_inline` 默认值、可用能力、schema 和配置保持现状。
- Web API 文档明确既有支持子集与个人助手用途；没有为了对齐协议新增能力，也没有删减当前端点、上下文或鉴权语义。
- 产品介绍中英文都以个人研发持续交付为中心，通知可见、多入口与现有共享行为描述准确。
- 必要检查和行为证据按实际结果记录；未验证项明确列出。
