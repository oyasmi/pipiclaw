# 056：让行为评测进入日常迭代

日期：2026-10-14。范围：`evals/` 工具链与贡献者工作流；不改变生产 runtime。

人工校准与复核部分已由 [057 的无人参与闭环](../057-autonomous-evals/design.md) 取代；本文件保留首批改进的设计依据。

## 现状评估

现有实现值得保留：隔离 trial home、进程级停止、真实 runtime、代码 oracle 与模型 judge 分工、独立的主体/judge 并发池、资源账本、不可变原始证据、冻结计划、续跑、重评、严格配对比较和基线晋升。这些机制已足够支撑项目，重建平台或增加第三套执行器会增加维护负担。

问题在使用闭环与场景维护，不能靠再加几十个 case 解决：

| 证据（本机历史产物与当前代码） | 影响 |
| --- | --- |
| catalog 引用了已删除的 T-deadline-01、T-recur-01、TL-signal-01；当前 list/plan 校验直接失败 | 日常入口实际不可用，类型检查发现不了目录漂移 |
| 评测 EvalBot 缺少 getCardGeneration 等生产端口，runtime 捕获异常后无模型请求也无交付，旧 runner 仍标 completed | 六个场景会出现假行为失败；类型断言掩盖接口漂移，新增真实 worker 离线接线保护 |
| dev 无过滤时选择整个 catalog；默认串行；core 为 12 × 3 | 快速检查和完整回归没有清楚分界 |
| 2026-09-12 的 core 基线 36/36，主体执行合计 30.6 分钟、约 211 万 token；C-test-proof 三次约占 7.4 分钟 | 每次小改动重复完整实验没有投入产出比；合计执行时间不能等同并行后的实际耗时 |
| 同一基线 report.md 为 102 行，每次 trial 资源清单位于失败和结果之前，人工复核为 0 | 报告无法直接回答“是否要处理，先处理什么”；设计了复核能力但尚未形成习惯 |
| T-job/T-run 仍匹配 kind=job/run，生产 schema 已变为 work；Goal 中仍提 notify | 未同步产品契约的评测会制造假回归 |
| dev 只跑 1 次，冻结 required gate 却至少要求 3 次 | 一次成功的排错检查也只能得到 inconclusive，退出码无法辅助日常判断 |
| changed-since 未覆盖所有 runtime 公共入口；无匹配时回退整个 core 可能越过显式过滤器 | 计划不够可靠；更严重的是计划尾部执行命令会丢过滤条件 |

历史数据只用于定位成本和工作流问题，不能据此宣称当前版本质量通过。旧基线的全通过也不足以证明场景难度无效：应结合负例敏感性和人工复核判断，不能自动把高通过率当坏事。

## 决策

### 1. 两种频率，沿用一套执行和证据协议

- `npm run eval` 默认展示快速检查计划，不计费；`npm run eval -- run` 才执行。
- dev 默认六个代表场景：C-fix-01、M-overflow-01、T-job-01、D-verify-01、U-path-01、S-inject-core-01，各一次。覆盖编码、记忆、任务、委派、工具、安全的日常高风险路径；交互、反思、长程变更仍需要定向选择或 core/explore。它不是完整覆盖的替代品。
- core 保留 12 个家族各三次，candidate 保留各十次。保留原 gate 阈值，禁止把一次 smoke 晋升成正式基线。
- `--case/--family/--domain/...` 显式选择范围；`--all` 运行全部活跃场景。retired/quarantine 默认不执行，显式 case/lifecycle 才能选中。list 默认保留完整目录便于发现历史场景。
- `--changed-since REF` 从当前过滤后的代表场景映射变更；未知路径保守回退 core，但仍遵守用户过滤。没有变更就明确说明，不暗中扩大范围。
- 并发默认仍为 1，提供 `--concurrency N`、`--judge-concurrency N`，plan/run 使用相同正整数校验。没有 provider 实测前不声称并发提速倍数，不改模型/thinking 来制造提速。
- 计划展示主体预算上界、串行执行上界（不是耗时预测）、并发与模型 judge 决策数量；judge 预算单独说明。复现命令必须保留所有选择条件。

### 2. 结论与诊断分层

- `report.md`：结论、已执行/计划、通过/行为失败/基础设施异常、主体与 judge 费用（未知不能记零）、实际本次耗时（历史缺失就不编造）、最多五组优先问题、证据链接及下一步、明细入口。失败优先按安全违规、执行异常、行为失败分组；同 case 的重复失败合并。
- `details.md`：保留既有全部资源、case 区间、grader 诊断、复核校准。JSON/trace/artifacts 不删不改。
- 终端结束时直接显示摘要；`eval report RUN`/`eval report RUN --verbose` 可重新渲染。复核追加后重渲染仍保留原判定。
- smoke 使用冻结 scoring mode：完整且全部成功 exit 0（仅 smoke 通过）；已知行为失败/安全违规 exit 1；执行/证据/评分不可用或计划不完整 exit 2。不得把 provider/fixture 失败的衍生缺失产物描述成模型退化。正式 gate 模式保留原门槛；修正不可用执行的 acceptance 为 unknown，保留其衍生 oracle 失败作诊断，防止污染行为失败分母；晋升明确拒绝 smoke。
- 报告不自动声称相对 baseline 提升；严格配对的 compare 是唯一差值入口。

### 3. 场景维护比数量重要

首轮不净增行为场景，修复缺失 catalog 引用和 work/report 契约。EvalBot 实现生产 DingTalkBotPort 接口，缺失端口在编译期报错；普通用户步骤没有观察到模型结果时判场景执行不可用。复用现有正反例单元测试，使“不 park 却声称完成”“无效等待类型”失败，正确 work 等待通过。离线 CI 继续检查整个 catalog。T-run 只根据成功执行后的持久化记录判断是否重复派发，允许可恢复拒绝后的自主修正，并补齐 W1 初始工作项。旧场景指纹自然变化，旧基线保留为历史证据，必须重新采样后才能比较。

每次行为修复的闭环：先读失败 evidence → 判断产品/fixture/oracle/provider → 修改所属层 → 单 case 排错 → 定向回归 → 需要版本决策时完整 core/candidate 配对。来自真实问题的用例应替换弱场景优先；每个新增样例写明风险和能拒绝的伪完成，不以数量和总分作为质量目标。

### 4. 运作约定

- 日常：改动相关场景一次；修改 prompt、模型、task/memory 公共流程时跑快速集合并补相应 domain。
- 每周或发布前：core 三次，记录本次失败的归因和修复；更换主体模型、重要 prompt 策略时按相同条件做 candidate 配对。
- 人工复核先处理安全失败、模型 judge 的争议样本及少量通过样本（失败/错误判定全部入队，至少保留一个模型判定，避免小 run 的复核队列为空）；每次实际复核几条，持续积累 holdout。40 条只是既有校准的起步刻度，不是可靠性保证；不能为凑数填 agree。
- 暂不接付费自动 nightly：先验证本地运行体验和真实质量收益，再根据凭据管理、时限与费用额度接 CI；离线 CI 一直保持无凭据可运行。

## 验收与限制

离线验证：现有工具链回归、catalog 全量校验、正反例 oracle、plan/run 范围一致、smoke 不可晋升、报告不会把异常当通过、类型/架构/单元测试。现有场景优先扩展，记录 case-count delta。生产 runtime 未改动，因此不新增 deterministic e2e 场景。工具链测试净增 1 条：真实 worker → mock provider → 交付，既有 subprocess 用例只跑自造脚本，无法检测 EvalBot 与生产端口漂移；已验证原始缺失方法时请求数为 0、此用例失败。`test:evals` 先构建当前 worker，防止旧编译产物掩盖问题。

真实模型试跑单独记录选定场景、模型/思考档位、结果/费用/耗时及失败归因。没有实测不得承诺“几分钟内完成”或“质量已提升”。第一轮的目标是恢复可运行、缩小默认工作量、让失败可行动，并建立之后能持续积累的证据；统计结论仍需要重复采样。
