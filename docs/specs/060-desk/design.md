## 1. 问题与结论

058 正确地将通信地址与工作状态解耦，但“独立助手个体”的定义仍将多个人格带进产品。059 消除了首次使用必须创建、绑定 dot 的门槛，但 `workspace/dots/default/` 保留了不必要的目录层级。

Pipiclaw 是用户的一个助手。它可以在不同工位处理不同工作，也可以从多个钉钉对话使用同一个工位。工位划分记忆、任务、文件和会话的归属，不重新定义助手是谁。

本 spec 采用 `desk`（工位），删除 dot 这一产品与代码概念；默认工位名固定为 `default`。共享文件继续放在唯一的 workspace 根目录，所有工位都直接放在其下，默认工位没有特殊布局。

这次同时收回迁移复杂度：产品只读写一种当前格式，升级转换在停机状态下由 AI agent 根据[一次性迁移说明](../../desk-migration.md)执行。不交付通用迁移脚本，不留下旧格式读取、字段别名、双写、自动搬目录或迁移标记协议。

## 2. 概念与所有权

| 概念 | 职责 | 不承担 |
|---|---|---|
| Pipiclaw | 同一个助手的身份、语气、共同规则和能力 | 多人格注册与切换 |
| workspace | 这次部署唯一的共享工作环境，包含共享文件与工位目录 | 每个群一个 workspace |
| desk | 一组工作的记忆、日记、任务、事件、产物与会话归属 | 独立人格、独立权限沙箱 |
| channel | 消息来源与回复地址；钉钉私聊、群聊或终端 | 文件路径、助手身份 |
| conversation | 某个渠道在某个工位里的独立会话 | 所有渠道混合的全局上下文 |

同一工位的渠道共享长期积累，各自保留模型 session。不同工位的常规记忆和会话检索分开；workspace 共同背景仍共享。任务、事件、作业、委派继续记录明确的投递渠道，结果只回到仍绑定在该工位的原渠道。

“一个助手”不是“全进程只有一个 SDK session”：保留按 `(desk, channel)` 编排、渠道间并行、渠道内串行的执行模型。工位间也不自动交换记忆，或自动复制、锁住代码 checkout。

## 3. 目标目录与格式

```text
<app-home>/
├── channel.json / auth.json / models.json / settings.json / tools.json / security.json
├── workspace/
│   ├── SOUL.md / AGENTS.md / ENVIRONMENT.md
│   ├── MEMORY.md                       # 人工维护的共同背景
│   ├── CHANNELS.md                     # 生成的渠道索引，列出工位
│   ├── skills/ / sub-agents/
│   ├── desk-bindings.json              # 渠道 → 工位，唯一绑定记录
│   ├── desk-default/
│   │   ├── desk.json
│   │   ├── memory/<name>.md / MEMORY.md # 工位事实源 / 生成索引
│   │   ├── journal/YYYY-MM-DD.md
│   │   ├── tasks/ / events/
│   │   ├── subagent-artifacts/ / subagent-runs.jsonl
│   │   ├── .memory-work/ / .locks/
│   │   └── conversations/<kind>-<n>/
│   └── desk-research/                  # 与默认工位同构
└── state/
    ├── dingtalk/conversations.json
    ├── jobs/<desk>/ / subagent-runs/<desk>/
    ├── memory/<desk>/<conversation>.json
    ├── dispatch/ / events/history.jsonl
    └── usage/ / logs/
```

工位逻辑名是 `default`、`research`，磁盘段是 `desk-default`、`desk-research`。命令、绑定、状态目录、派发 id 使用逻辑名，不混用带前缀的目录名。工位的工作目录默认就是它的目录；保留记录里可选的绝对 `cwd`，只改变文件工具与执行器的工作位置，记忆等状态仍属于该工位。

名称保留现有的 1–32 位小写字母、数字、连字符规则，首尾不能是连字符。目录前缀由路径函数恰好加一次；若用户将工位命名为 `desk-work`，目录就是 `desk-desk-work`，不猜测、不截去用户名称的一部分。渠道 id 始终只作数据键，不能拼入路径。

### 3.1 工位记录

`workspace/desk-default/desk.json`：

```json
{
  "version": 1,
  "name": "default",
  "createdAt": "2026-10-23T00:00:00.000Z",
  "conversations": {
    "dm_example": { "dir": "dm-1", "createdAt": "2026-10-23T00:00:00.000Z" }
  }
}
```

`name` 必须与 `desk-<name>` 的逻辑名匹配，不能直接与完整目录名比较。`conversations` 的唯一目录分配、按 kind 递增编号、已有渠道恢复原目录等约束保留。

### 3.2 绑定表

`workspace/desk-bindings.json`：

```json
{
  "version": 1,
  "bindings": {
    "dm_example": { "desk": "default", "boundAt": "2026-10-23T00:00:00.000Z" }
  }
}
```

文件名和字段共同定义当前格式；不接受 `dot` 字段，不同时寻找 `dots/bindings.json`。绑定表只记录实际绑定，没有通配符或运行时虚拟默认行。创建空表属于共用初始化；此后钉钉绑定由一个 daemon 修改，TUI 不修改绑定条目。

### 3.3 枚举与共享目录

只从 workspace 的直接子目录中识别 `desk-` 命名空间，读取对应 `desk.json` 后分类为可用、缺失记录或记录无效。不递归扫描、不将任意工作文件夹当工位、不因看到目录就补写记录。具有该前缀但名称不合法的目录可以在管理报告里显示为无效，不能参与执行。原子创建使用隐藏暂存目录，不能落入工位枚举结果。

删除 `getDotsDir` 这一中间容器抽象；工位路径和绑定表路径都直接由 workspace 解析。根目录的共享文件及 `skills/`、`sub-agents/` 保持原位，不引入 `shared/`。

## 4. 一个人格的实际加载规则

共同身份与规则明确来自 workspace 根目录的 `SOUL.md`、`AGENTS.md`；共享 skills、角色、环境、模型与安全配置继续使用现有加载范围。

当前 `agent/prompt/resources.ts` 会优先选择 dot 自己的 `SOUL.md` 和 `AGENTS.md` 并整体替代根文件。实施时删除这条覆盖路径及为它保留的参数、测试分支，不能机械改名为“工位自己的 SOUL 优先”。工位内同名文件不成为另一套人格配置；已有局部内容如何保留或整理，由离线迁移决定。SDK 的项目规则加载仍遵守现有能力和指令层级，不新增工位人格覆盖机制，也不靠 cwd 的祖先遍历碰巧找到共享身份文件。

模型提示、记忆反思指导和 runtime playbooks 中，将“独立助手个体”改成“同一 Pipiclaw 的工作范围”。说明当前工位、记忆和文件的范围即可，不重复注入整套人格，也不在默认聊天中要求模型向用户解释 desk。

根 `MEMORY.md` 是人工共同背景；工位 `MEMORY.md` 是从 `memory/` 生成的索引。两者不可互换，不把工位自主积累自动提升为所有工位的共同背景。

### 4.1 Runtime playbook 是实施与验收的一部分

Playbook 是模型执行工作的机制参考，必须与 desk 运行时同一变更落地。仅在代码、用户手册或本 spec 里解释正确，不算完成；也不能把正文中的 dot 机械替换成 desk 后就判定机制说明正确。遵循[现有 playbook 编写规则](../../runtime-playbooks.md)，复用当前七份手册，不另建重复的 desk 总手册。

**`runtime-orientation.md` 是 desk 概念、文件归属和管理入口的统一导航。** 至少清楚说明：

- 同一个 Pipiclaw 在多个工位工作；共享人格与能力，工位划分工作状态。workspace 只有一个，各渠道在工位里仍有独立会话。
- 默认工位由运行时初始化，新获准渠道由运行时接入 `default`；正常聊天不要求用户先创建工位、执行 bind，也不要求模型自行修建运行时状态。
- 当前工位名、工位绝对路径、workspace 绝对路径、实际 cwd 和渠道地址以运行时上下文为准。逻辑名 `default` 对应 `workspace/desk-default/`，不是 `workspace/default/` 或 `workspace/dots/default/`。
- `deskDir` 是记忆、任务、事件和会话等状态的位置；实际 cwd 可以由记录中的绝对 `cwd` 指定，二者不能写成恒等。通用相对路径和默认委派工作目录服从已解析的 cwd；定位状态使用 deskDir，定位共同资源使用 workspace 路径，不从自定义 cwd 猜 workspace。
- 根 SOUL、AGENTS、共同 MEMORY、ENVIRONMENT、skills 和角色目录的职责，以及工位事实源、生成索引、日记和会话的职责。删除“工位内同名 SOUL/AGENTS 整体替换根文件”的说明。
- `desk-bindings.json` 是根目录唯一绑定记录；创建、切换使用运行时管理入口。明确写成“用户命令：`/desk …`”，不能把斜杠命令当模型可调用工具，也不能用文件写入模拟创建/换绑。
- 换绑只改工作归属，不搬移记忆和文件；旧工位发往该渠道的工作暂停或不投递，切回沿用原会话。普通换 cwd、选择仓库路径和委派 workingDirectory 都不等于换工位。

其他手册在各自的决策点补充作用范围，需要完整地图时路由回运行时导航，不复制一整段 desk 定义：

| Playbook | 必须核对的 desk 语义 |
|---|---|
| `runtime-orientation.md` | 上述统一导航；frontmatter 触发语也覆盖工位（desk）、绑定、共享范围与文件定位 |
| `memory-and-learning.md` | 记忆与 session 检索的工位范围、同工位多渠道共享、不同工位不自动回忆；用户事实写清归属的人；共同背景与工位生成索引不可混写，不能自动把偏好提升为跨工位规则 |
| `agent-delegation.md` | 角色目录共享不等于继承主会话；显式交代相关工位事实与真实工作入口；省略 workingDirectory 使用已解析的执行 cwd，不能一律说 deskDir；运行额度按工位/宿主区分，结果回发起渠道且仍需绑定匹配 |
| `background-jobs.md` | 作业与限额属于工位，任务关联属于实际任务；完成通知回发起渠道，换绑后不转投新工位或其他群；保留 daemon/TUI 的恢复能力区别 |
| `event-scheduling.md` | 定义、数量限制、历史和任务实例按工位归属；投递 channel 与工位不同，换绑导致原渠道工作暂停；模型通过既有事件工具管理，不直接改绑定来让事件投递 |
| `task-lead.md` | 任务、任务会话、委派/作业记录与等待恢复属于当前工位；步骤静音、report 的投递渠道和换绑后的暂停规则；不能把任务步骤读成整个工位共享的聊天会话 |
| `outbound-media.md` | 文件归属和消息收件地址分开；附件发送到实际当前渠道，同工位共享文件不等于向工位所有渠道广播；回执与幂等交付要求保持 |

**渐进加载与事实来源：** 当前工位、workspace/工位路径、实际 cwd、渠道等动态事实由 `<runtime_turn_context>` 及其他既有运行时块提供，不能让模型通过读静态手册推断。按这些事实补齐上下文，保持精简；静态 playbook 解释语义和操作。常驻 prompt 只保留必要事实、不变量与目录触发，不常驻整份工位指南，不要求每轮重读已在上下文中的手册。

`runtime-orientation.md` 保持不设 `requires-tools`，禁用任务、记忆写入或委派工具时仍可发现；目录只包含名称和短触发语，正文按需 `read`。同步核对 frontmatter、`playbooks/catalog.ts`、prompt 的机制入口和 `docs/runtime-playbooks.md` 的目录/门控说明。不把某次安装的工位记录或绑定表快照硬编码进静态手册，不把迁移流程当作模型的日常工作协议，也不复制到用户 workspace 的 AGENTS/skills。

**同步发布：** 改动源手册时同时完成对应 reader、工具说明、回合上下文与用户手册的更新。正式构建、eval 构建和安装包都必须取得同一批当前手册，并清除退役资源；checkout 优先读取源目录的行为不能掩盖安装包里仍有旧文案。实施前不把活动 playbook 提前改成尚未存在的 desk 行为。

**验收分层：** 扩展既有 playbook 用例，验证导航可发现、目录不带正文、当前手册可读取、构建复制与旧资源清理、真实 JSON 样例和引用入口有效；机制 e2e 核对提供方请求中的动态工位/cwd 事实与实际读取的手册资源。不能用逐字快照、规定某句话必须出现或只查无 dot 字符来证明模型理解正确。真正是否按工位记忆、正确选择工作路径/投递范围、无需 bind 就正常处理请求，使用相关 dev 行为探针验证并记录结果。改后运行 `npm run playbooks:measure`，检查新增内容与重复注入成本；只在阅读决策点保留必要知识。

## 5. 初始化：默认可用，已有状态可保全

初始化是程序机制，不能交给模型推断。`bootstrapAppHome`、daemon 嵌入入口与 TUI 使用同一套规则，继续保持现有公开入口的同步/异步契约。仅打印 help/version 不初始化；首次实际运行即使只生成配置模板后正常退出，也准备好空绑定表与默认工位。终端不需要钉钉凭据即可完成初始化。

app 层负责共享模板和启动装配，desk 域负责名称、记录、绑定表校验及默认工位初始化，不反向依赖 app/agent/runtime。同步 scaffolding 与异步运行时复用同一份当前格式校验规则，不能各维护一套宽严不同的 JSON 判断。共用的关键名字是 `DEFAULT_DESK`、`getDeskDir` 和 `getBindingsPath`，不在各调用者手写目录前缀。

### 5.1 顺序与状态判断

1. 确定 app home 和唯一的 workspace，读取当前格式的绑定表与直接工位目录；先判断状态，再补写文件。
2. 真正首次初始化，即绑定表不存在、也没有任何当前格式的工位目录时，以“仅在不存在时创建”的方式发布空 `desk-bindings.json`。
3. 校验现有绑定表。读取失败、JSON/条目损坏或不支持的版本都必须报错，不能解释为空表；有工位目录却丢失绑定表也必须报错，避免把已接入渠道重新分配到默认工位。
4. 默认工位存在时原样保留；目录无记录、记录损坏或逻辑名不匹配时标为不可用，不原地修补。
5. 默认工位不存在，且绑定表没有引用 `default` 时，原子创建空的 `desk-default/desk.json`。已有其他工位和绑定不改动。
6. 绑定表已引用 `default` 而目录丢失时，不创建空替身。保留绑定并报告该目标不可用。其他可用工位可以继续服务；终端显式打开其他工位也不应被这个局部故障阻断。

正常状态下安装只写共享模板、空绑定表与工位记录，`memory/`、`tasks/` 等按需创建，不预建会话，不调用模型、不启动任务或发通知。重复初始化不重写创建时间、记录或已有文件。

绑定表必须先于首个工位发布。这样，“有工位、没有绑定表”可作为当前格式的数据完整性故障，不需要额外引入安装标记或迁移完成标记。若空绑定表发布后进程中断，下次直接补建默认工位即可。

### 5.2 并发与故障

daemon 与 TUI 可能同时首次启动。空绑定表的发布必须原子且不能覆盖已有文件，不能使用“先 exists、再覆盖式 rename”的实现，否则迟到的初始化会清空已接入渠道。败方重读、校验胜方的结果。工位记录在隐藏暂存目录写完整后再发布，竞争失败返回已有状态，不暴露半个工位。

创建时保留现有落盘和父目录持久化保证；后续 `desk.json` 读改写继续使用 `.locks/desk-json.lock`。已有非空或异常目标不覆盖。明确创建命令也不能通过重建同名记录，绕过“已有绑定指向丢失工位”的故障保护。

不要为这些正常初始化与原子写入增加迁移状态机。程序只校验当前格式，不为旧目录命名、旧迁移标记或旧字段设计启动分支。旧部署必须在新版本首次实际启动前完成离线转换；产品不承诺自动辨认所有未转换旧 home。误启动也不得自动搬移、合并或删除未知文件。

## 6. 渠道接入、切换与后台工作

获准的真实钉钉消息，在图片保存、命令分流及创建 runner 之前执行 `ensureDefaultBinding`。未经发送者准入的消息不创建绑定或会话。

没有绑定时，串行事务依次分配默认工位会话、提交绑定表、更新内存视图、激活工位；提交绑定之前目标工位不能为这个渠道产生后台工作。必须在写队列内再次检查绑定，防止两个新渠道丢失更新，或迟到的自动绑定覆盖显式切换。

已有绑定无论目标可用与否，都不自动改成 `default`。首条消息是图片、`/new` 或运行时命令时遵守同一接入规则。真实 Stream 入站与直接入站路由入口都要覆盖；可选初始化钩子不存在时，不无故增加异步等待、改变嵌入场景的原有时序。

只读路径解析、后台任务、定时事件、委派/作业完成唤醒和通知均不自动建立绑定。合成事件携带 `desk`，仅在目标渠道仍绑定到该工位时准入。默认接入不构成后台工作重新绑定渠道的理由。

显式切换保留现有事务语义：忙碌拒绝、分配会话、落盘绑定、激活目标、释放旧 runner、处理旧工位休眠或暂停。原 runner 的最后反思仍写入原工位。切换不复制工作文件或记忆，切回恢复原渠道会话；`/new` 只重置当前渠道。

`DeskRuntime` 仍是 daemon 对绑定与激活状态的唯一权威；run manager、job manager 按工位持有，`SubAgentRunManager` 仍独占结算、用量、租约和完成唤醒。任务等待必须继续经过 `resolveTicket`/`redeemTicket`，任务步骤仍使用任务会话并默认静音。重命名不能改变这些机制。

## 7. 命令、终端与用户文案

| 入口 | 目标行为 |
|---|---|
| 直接聊天 | 新渠道使用默认工位，不先解释 desk、不要求 bind |
| `/desk`、`/desk list` | 列出工位、当前工位、关联渠道与不可用状态 |
| `/desk new research` | 显式创建空工位，暂不改变当前渠道 |
| `/desk bind research` | 切换当前钉钉渠道的工位，说明实际暂停的工作 |
| `/desk bind default` | 回到默认工位，恢复该渠道原有会话 |
| `pipiclaw tui` | 固定打开 `default`；多个工位存在时也不猜测 |
| `pipiclaw tui --desk research` | 打开已存在工位，保留独立终端会话 |
| `pipiclaw tui --desk research --create` | 显式创建不存在的工位；故障目标不当作新工位修补 |

不保留 `/dot`、`--dot` 或旧类型别名；旧参数按普通未知命令/参数处理并给出当前用法，不新增专门的历史参数识别分支。TUI 仍不绑定钉钉渠道，也不获得 daemon 的持久外部委派恢复能力。

普通用户文案使用“工位”，需要操作时展示工位名与 `/desk`；默认入门流程只说直接聊天。CLI 输出和运行日志保持英文。报告、错误、预算与 actionable next step 继续遵守 spec 053；不要把模型机制指导直接投到用户渠道。

### 8.1 必须删除的迁移遗留

脚本与脚本专用测试在本 spec 阶段删除，不留空壳；实施 desk 时一并删除 `src/dot/legacy-layout.ts` 及其旧布局扫描、旧事件目录扫描、迁移标记探测和所有调用。默认初始化不能继续通过调用旧布局检查来决定是否创建工位。若绑定表错误仍需专用 startup error，将其定义为当前领域的错误，不能为复用一个 error class 而保留迁移模块。

删除相应旧格式测试和历史目录夹具，保留/更新当前格式的腐坏状态、并发和恢复测试。新的部署不写、不读 `dots-migration.*`、`task-migration-v5.done` 等迁移凭据；旧 home 中的清理由离线说明承担。不得为迁移引入配置开关、旧路径候选列表、软链接、兼容 re-export 或后台整理服务。

当前代码中还应逐项收掉这些相关分支：`channel/channel-index.ts` 的旧四列行判断；`events/commands.ts` 用渠道集合推断无所有权字段的旧事件历史；`jobs/record.ts` 仅为未迁移记录容忍缺失投递 channel 的契约；评测 artifact/regrade 的 `channelDir` 旧字段回退。仅为这些分支传递的参数、端口、夹具和测试随之删除。`memory/review-log.ts` 中仅为旧迁移写入保留且已无生产者的 reason 值也移除；历史原文可以保留在操作记录中，不需要常驻迁移生产入口。

不要把“删除迁移遗留”理解为删除正常故障容错：例如绑定表损坏拒绝启动、调度恢复、完成唤醒的真实性检查、无法证明进程身份时的保守处理，以及标准时间解析仍然必要。这里删除的是为旧产品格式提供第二条读写解释的代码，不放宽当前数据约束或重写无关协议。

### 8.2 仍然有效的 058 决策与不变量

代码注释里约有 60 处引用 “spec 058, D*/INV-*”。058 已被本 spec 取代，正文仍用 dot 的说法，但下列编号的约束没有改变；读到这些注释时，按本表的 desk 含义理解。编号和原意以 [058 design.md](../058-dots/design.md) 为准。

| 编号 | 当前含义（desk 术语） |
|---|---|
| INV-1 | 一个频道最多绑定一个工位；`desk-bindings.json` 是唯一事实来源，只有 daemon 写 |
| INV-2 | 工位只能被显式创建：`/desk new`、TUI 的 `--create`，以及默认工位的初始化；入站消息和后台服务不创建工位 |
| INV-3 | 频道 id 永远不作路径段，只作数据键 |
| INV-4 | 每项后台工作都在自己的数据里显式写明投递频道，不存在主频道 |
| INV-5 | 后台工作只投递给仍绑定在产生它的工位上的频道 |
| INV-6 | 多个进程可以同时使用同一个工位；共享写入的文件经跨进程短锁串行，每个会话区同一时刻只有一个进程写入，后台工作只由 daemon 执行 |
| INV-7 | 一个会话区只属于一个（工位，频道）组合，登记在 `desk.json`，分配后目录名不变 |
| INV-8 | 同一个工位的所有记忆写入方以工位名为键串行 |
| D5 | `/desk` 的 list / new / bind 语义，以及 bind 的顺序：校验、分配会话区、提交绑定、最后激活目标工位 |
| D6 | `DeskRuntime`：工位的激活与休眠、按工位运行的后台服务、跨进程短锁 |
| D7 | 合成事件（唤醒、定时触发）只在其频道仍绑定在它被产生时的工位上才被准入 |
| D8 | 挂起：没有任何绑定的工位整体休眠；投递频道不在本工位的任务被冻结；事件触发时频道未绑定则跳过（`channel_not_bound`）；绑回后自动恢复 |
| D9 | 没有项目范围：工作目录是工位目录（`desk.json` 可设 `cwd`），不存在项目边界或 `/project` |
| D11 | 频道 id 的格式只在 `channel/channel-id.ts` 定义；`desk` 模块在第 2 层，不解析频道 id |
| D12 | 记忆存在工位级，各写入方共用以工位为键的队列；reflect 的单位是会话区 |
| D13 | 任务存在工位级，frontmatter 的 `channel` 是投递频道；任务修改跨进程串行；TUI 创建的任务投递频道是 `tui`，daemon 不会推进它 |
| D14 | 事件归工位所有，数量上限和历史按工位计；`channelId` 是投递频道，由 `event_manage` 绑定而不是由模型传入 |
| D15 | 委派和作业的管理器按工位组织；记录里的 `channelId` 是发起频道，完成唤醒发往它 |
| D16 | runner 由 `DeskConversation` 构造；`/new` 只重置本频道的会话区 |
| D17 | 入站图片先解析绑定，已绑定才保存到工位的 `inbox/`；`log.jsonl` 写入会话区，`subagent-runs.jsonl` 写入工位根 |
| D19 | 用量记录带 `desk`，`/usage` 按工位统计 |
