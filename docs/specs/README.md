# 历史设计记录

`docs/specs/` 保存 Pipiclaw 各阶段的需求、设计、实施计划和审查记录。它们的价值是解释“当时为什么这样设计、替代方案为什么被放弃”，不是当前用户手册。

## 如何判断当前行为

遇到描述冲突时，按以下顺序判断：

1. 当前代码和测试
2. `README.md` 与 `docs/` 顶层专题手册
3. 当前版本的 `src/playbooks/`
4. 历史 spec

Spec 中的旧路径、绝对路径、已删除字段、当时尚未实现的计划和阶段性结论会原样保留。不要为了让历史文档“看起来最新”而重写已经发生过的设计过程；实现落地后的准确用法应写进顶层手册。

## 主题分组

| 编号 | 主题 |
|---|---|
| `001`–`003` | 初始记忆、子智能体与上下文设计 |
| `004`–`008` | E2E、安全、Web、事件动作与早期审查 |
| `009`–`018` | 记忆增长与维护、交互模式、工具注册、日志、fallback、TUI |
| `019`–`029` | 任务台账、可见性、driver、治理、提示词架构、周期任务和生命周期收敛 |
| `030`–`036` | 附件、唤醒可靠性、子智能体采用、调用面和配置/API 瘦身 |
| `037`–`039` | Plan、记忆试用期、任务自治 v2、provider 登录 CLI |
| `040` | 异步委派与外部智能体统一 run 生命周期 |
| `042` | 委派链路一致性加固（收敛 040 的实现分叉） |
| `043` | 会话身份、项目作用域与回合恢复（active-session 指针、双根目录、中断回合的分支修复） |
| `044` | 原生文件 I/O（文件工具从 shell 管道迁到 `FileStore`，修静默截断与多字节损坏） |
| `046` | 工具调用面切分（按 payload 形状拆分 `task_manage` 与 `subagent`，描述长文还给 playbook） |
| `047` | 收尾三个 `*_manage`（`event_manage` 补 `list`、`memory_manage` 去 `kind` 并切分、`subagent_manage` 切成 list + run） |

`041` 号被短 runId 与 `/subagents` 命令那轮工作占用（代码注释中引用为 "spec 041"），当时未留下 spec 目录，因此编号从 `040` 直接跳到 `042`。

`045` 号同样只存在于代码注释（`spec 045`：只读 `skill` 工具、`glob` 工具、以及用运行时 describer 取代模型侧 `label` 参数），未留下 spec 目录，因此编号从 `044` 直接跳到 `046`。

目录名包含主题，例如 `040-async-delegation-and-external-agents/`。需要理解当前外部智能体能力时，先读顶层的 [智能体委派指南](../sub-agents.md)，只有在研究设计取舍时再进入 spec 040。

## 维护规则

- 新机制先在 spec 中记录问题、原则和取舍，实现后同步更新对应顶层手册。
- 不从 spec 直接链接用户 Quickstart；用户路径必须经过 `README.md` 或 `docs/README.md`。
- Spec 中的完成状态不证明当前代码仍保持该行为，重大版本变更后以测试和当前架构文档复核。
