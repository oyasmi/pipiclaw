本次查阅 Grok Bot、Muse、Dots 的官方产品材料，以及 OpenAI、xAI 的语音 API 文档。AIHOT 的当周检索未提供直接回答本题的产品资料，下面的产品事实以逐页核对的官方材料为依据。厂商描述不等于独立体验测评；公开文档未披露的调度算法、内部语音模型和端到端延迟不作推断。

**核心判断**

Pipiclaw 可以沿两条相互补充的路径发展：持续替用户留意变化并推进工作；让用户通过持续通话随时交办、询问、纠正和决策。两者共享同一套工作事实、任务控制与交付记录，但各自有不同的节奏。后台可以工作数小时，通话必须及时回应；后台完成一项工作，也不意味着此刻应该插话。

**语音方案的核心边界：Pipiclaw 的工作接口仍接收文字要求，返回文字、响应状态和结构化事件；语音接入层负责声音和谈话节奏。** 接入层可以采用“语音识别＋语音合成”，也可以采用持续语音模型。后者会处理交谈、澄清和口头表达，按需要把工作交给 Pipiclaw；它不要求把 Pipiclaw 核心改成音频 agent。

这里的“客户端”是使用 Pipiclaw 的一整套接入应用，可能包含手机/桌面设备、可信服务端桥接和语音供应商。不能理解为所有推理、转录和合成都在用户设备本地完成。

## 0. 阅读口径与建议范围

本文区分三种材料：第 1 节记录官方材料描述的产品能力；第 6 节记录代码基线上的现有机制与缺口；其余章节主要是据此提出的候选设计与验证方法。文中的价格是当日快照，延迟数字是原型目标，都不能作为已通过的性能或成本承诺。

建议先验证一个用户、一个 desk、一个持久会话中的实时通话，再验证一个有截止时间的主动工作场景。语音体验可以先独立成立，主动发现也可以先复用事件与任务模板；不以新建职责平台、通知中心、电话网络接入或替换 agent runtime 为前置工程。

## 1. 领先产品已经公开了什么

### 1.1 Grok Bot：持久职责、可见的自动化、持续语音

Grok Bot 有一个作为主要联系人的 primary Bot，它会主动联系用户并协调其他 Bot。长期规则和职责通过对话调整，区别于单次任务指令。这是产品公开的能力，文档没有披露主动联系的内部打分和检查频率。[官方 Bots 文档](https://docs.x.ai/grok-bot/bots)

重复工作由 routine 表达，执行方法由 skill 表达。触发可以来自时间、Slack、GitHub、Linear、Sentry、PagerDuty、邮件或 webhook；官方建议先把一次性流程做可靠，再自动化，并缩小事件匹配范围。Webhook 的接收成功只表示启动工作，不能当成交付完成。[官方 routines 文档](https://docs.x.ai/grok-bot/skills-routines-and-automations)

通知有一个很具体的时机设计：macOS/Windows 桌面活跃时优先通知桌面；需要用户输入且尚未处理的事项，约三分钟后再提醒手机；当前正在看的 Bot 会话不重复弹窗。Linux 和其他状态的规则有所不同。它把“新结果”与“需要处理”分别呈现。[官方通知文档](https://docs.x.ai/grok-bot/settings-and-notifications)

语音输入、语音留言和实时语音聊天是三个不同入口。实时通话是与一个 Bot 持续说话，可看转录、静音、调整声音和语速；短暂掉线会尝试重连，结束后保留通话记录，并可继续在聊天里跟进工作。这是 App 内的用户—Bot 通话，不能据此推断支持电话号码呼入或 Bot 主动拨号。[官方交互文档](https://docs.x.ai/grok-bot/chat-and-collaboration)

另一个应修正的旧认知：官方 FAQ 说明 Grok Bot 会选择第一方或第三方模型，用户不能选模型；不能继续用“只运行 Grok”解释它的内部实现。其产品通话是否采用公开的 Grok Voice API，本次材料不足以确认。[官方 FAQ](https://docs.x.ai/grok-bot/faq)

### 1.2 Muse：目标、主动想法和打扰门槛

Muse 的产品设计文章明确表达了两次判断：在相关事件和计划时刻继续工作；后台有结果后，再判断是否值得告诉用户。其 Ideas 区还容纳了适合被用户稍后发现的建议，而不是把所有想法都变成即时消息。用户可以要求调高、调低或关闭主动性。文中的及时提醒案例是厂商叙述，不能证明它准确掌握用户随时的可打扰程度。[Muse 设计文章](https://introducing.muse.ai/)

Meta 在 Connect 的官方介绍中描述，Muse 的语音模式允许深入交谈，同时在后台做事。这支持“谈话与工作并行”的产品判断；材料不足以确认其端到端延迟、中文表现、完整打断语义或电话网络能力。[Connect 官方介绍](https://about.fb.com/news/2026/09/the-biggest-news-from-connect-2026/)

### 1.3 Dots：委托工作、主动研究和语音上下文分开

Dots 可在委托工作中决定何时暂停和再次跟进，也支持明确保存的定时工作及服务支持的事件监测。主动研究则使用受限的读取能力，寻找关联并保存笔记；它本身不能发送消息、修改应用或操作电脑。研究发现与执行授权有明确边界。[Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

用户可以发起与 dot 的实时通话，在通话中继续打字；挂断结束语音会话，已交办工作仍可继续。文档明确把 dot 主动呼入列为发布后的计划，不能当作已上线功能。[Message your dot](https://learn.chatgpt.com/docs/dots/channels)

上述记忆文档还提醒：通话拿到的是选定的上下文，可能与后台任务所见不同。因此，“同一个助手”不应理解为把所有工作上下文原样复制进音频会话。

### 1.4 对 Pipiclaw 的直接启示

| 产品证据 | 可借鉴的设计 | 不能从证据推出什么 |
| --- | --- | --- |
| Grok 的 routine 与 skill 分开 | 触发条件与工作方法分别维护，流程先验证再自动化 | routine 可以无条件理解一切用户意图 |
| Grok 的跨设备通知规则 | 依据已有的活跃状态选择提醒位置和升级时机 | 产品能准确推断人在想什么 |
| Muse 的结果筛选与 Ideas 区 | 做事、保存发现、主动联系分别决策 | 所有完成都应该弹消息或播报 |
| Dots 的主动研究边界 | 可先找证据，再按已有委托决定后续行动 | 连接信息源即授权持续监控和修改 |
| 三者的谈话与后台并行 | 用户说话时仍能工作，用户能持续改变方向 | 原有文字 agent 接上朗读即可获得同样体验 |

## 2. 主动性至少有四种“时机”

以下是基于调研提出的 Pipiclaw 方案，不是对厂商内部算法的复述。

### 2.1 何时观察

观察入口可以组合使用：

- 外部事实变化：新问题、PR 回复、测试状态、依赖版本变化。
- 承诺的时间窗口：用户要求明天查看，或者某个截止日期临近。
- 内部工作事实：任务完成、失败、阻塞条件解除。
- 低频复盘：发现已知信息之间的冲突、遗漏的跟进或过时的计划。

事件支持 webhook 时优先使用可信事件，缺少事件能力时使用低成本轮询。没有任何新活动、时间条件或待复盘材料时，可以跳过模型调用。门控脚本应判断条件，不能在工作还没可靠接收前推进唯一游标，否则一次崩溃会丢掉变化。

复盘也需要预算、适用范围和终止条件。记忆里提到某个兴趣，并不自动意味着应创建长期巡检；一次随口想法可以先成为建议。

“帮我盯住发布准备”表达的是一项持续职责，不能直接等同于一个永不结束的 task。首次实验可把关注范围、来源、期限、授权、预算及汇报条件写成可查看的工作说明，由事件按需触发有限的一次性任务。是否值得新增职责实体，应在这个闭环验证后再决定。

### 2.2 何时开始行动

用户的目标给出目的，已有授权限定行动范围，新证据决定现在是否值得做。判断至少应能解释：关联哪个目标，发生什么变化，已有任务是否覆盖，拖延的代价是什么，是否在授权与预算内。

有明确截止日期的工作可以倒推最晚开始时刻：

```text
最晚开始 ≈ 截止日期 − 预计执行时间 − 必要的用户决策时间 − 余量
```

这是规划估计，不是保证。估计不确定时应保留余量，并在风险实质变化时更新计划。与其每天问“要不要发版”，更有用的是提前发现“剩余测试时间已经不足”。

有价值的下一步可能只是查清事实、复现问题、准备修复或生成可审阅的结果。已有授权足够时继续完成；确实需要用户选择时，带着证据和具体选项回来，不新增逐项审批。

### 2.3 何时回来检查

每次检查应留下一个可解释的下一次触发依据：等待某个外部事件、已承诺的时间，或一段有上限的复查间隔。没有变化时可以退避，临近真实截止时间时再提高关注度，完成或过期后结束。

这里应复用现有事件、作业和任务事实，不新增模型可宣称的 waiting/paused 状态。任务仍由任务车道推进；聊天和语音只传达要求、回答问题、查询和调整任务。

现有周期事件的无门控最小间隔为 30 分钟，有 preAction 时为 5 分钟；不能让新 prompt 绕过这些限制，或建立数秒一次的自激励循环。需要秒级反应的外部变化应设计真正的事件入口。

### 2.4 何时联系用户

可先使用简单、可解释的规则，再依据真实使用修正：

| 情况 | 建议行为 |
| --- | --- |
| 正在通话，结果直接回答当前问题 | 等用户说完，在最近的自然停顿回复 |
| 正在通话，另一个任务有普通进展 | 更新屏幕与文字记录，稍后合并口头摘要 |
| 新证据意味着当前决定会出错 | 尽快简短纠正，说明具体变化 |
| 需要用户决策，且临近最后可处理时刻 | 立即通知适当入口，给出理由、最晚时刻与选项 |
| 有价值但不紧迫的新想法 | 留待摘要或下次用户接入时提出 |
| 事项已失效、已经处理或只是重复 | 不再发起新的主动联系 |

“没有回复”不能自动等同于“再加大打扰”。重复提醒需要新的证据、真实截止时间或用户约定的节奏；没有来电授权时不升级为呼叫。

Pipiclaw 的用户已经明确选择保留任务进度、失败、卡顿与完成的可见性，见 [065](../specs/065-personal-delivery-focus/design.md)。这里的筛选针对新增的主动建议和音频播报；不能借此删掉既有通知、改变默认通知等级或建设一个通用通知中心。

### 2.5 用一个完整时间线验证时机

以下发布场景是验证夹具，不是厂商案例或当前功能演示：用户要求周五发布前持续关注阻塞，允许调查和准备修复，具体实施范围沿用其授权。

| 时刻与新事实 | 后台应做什么 | 对用户的表达 |
| --- | --- | --- |
| 周二，新增一条相关错误报告 | 判断与发布的关联，检查是否已有任务覆盖，必要时启动一次调查 | 尚无可靠结论时记录进度；用户当前无需决策 |
| 周三，查明回归至少需要一天，相关修复仍未准备好 | 更新最晚开始估计，准备影响与可选处理方式 | 明确指出周五目标受到影响，以及最晚需要什么时候决定 |
| 周四，用户正在通话，后台验证通过 | 保存证据和实际结果，更新任务事实 | 等自然停顿，简短说明验证通过；细节留在文字中 |
| 周五，同一 webhook 重投或轮询仍读到旧错误 | 识别已处理的证据及原任务，不再创建相同工作 | 不把旧错误再次当成新的发布风险 |
| 发布取消或关注期限结束 | 结束临时检查和新任务派生，保留已有记录 | 确认这项关注已结束，已有工作按用户要求处理 |

时机策略应同时观察提前发现的收益、漏报、重复工作和无效打扰。只统计发送了多少主动消息，无法证明主动性有效。

## 3. 通话改变的是协作方式

### 3.1 应先交付什么体验

首版目标可以很具体：用户走路时接入 Pipiclaw，了解正在做的事，交办一项工作，继续补充和纠正，挂断后工作继续，结果回到持久会话。

示意对话：

> 用户：帮我查一下发布准备得怎么样。
>
> Pipiclaw：我先核对最新结果。你比较关心测试还是上线风险？
>
> 用户：上线风险。先别改代码。
>
> Pipiclaw：好，先调查，不改代码。
>
> 后台查明后：发现一个阻塞：登录回归还没通过。我可以继续定位原因，你也可以先听其他检查结果。
>
> 用户：继续定位，我先挂了，结果发钉钉。

这是候选交互，不是已实现能力。最后一句的跨入口投递必须有明确关联和授权；当前任务回原发起频道的规则不能悄悄改成“发到最近使用的频道”。

### 3.2 说话内容需要独立设计

- 每轮先说结论和当前最需要用户理解的事，默认一到三句，用户追问后展开。
- 状态来自真实工作记录；不能把“收到请求”“工作已启动”“已完成”“结果已播放”混为一谈。
- 路径、代码、表格、长日志和证据链接留在文字与文件中，口头说明它们对决定的影响。
- 提问一次聚焦一个关键缺口；已经授权的事不因换到语音入口就重新确认。
- 不把工具调用、内部推理、模型 prompt 或后台日志逐条朗读给用户。
- 用户在想、阅读或检索材料时允许安静；不要用固定频率的“还在吗”“正在处理”填满空白。
- 接通时基于近期工作提供简短衔接；上下文不明时先问一句，不擅自认定用户想继续哪项工作。

即时回应与语义完整都重要。用户说“明天……不，后天”时应保留更正；“嗯”可能只是正在听，不一定构成某个行动的同意。高影响参数存在歧义时只澄清该歧义，不把所有语音操作都变成确认流程。

### 3.3 停止说话与停止工作是不同控制

| 用户表达 | 音频行为 | 工作行为 |
| --- | --- | --- |
| “停一下，先听我说” | 立即让出话语权，丢弃旧播放队列 | 原有工作继续，等待进一步要求 |
| “别修了，只调查” | 停止旧解释，按新要求回应 | 把范围变化转达给相关任务，确认实际控制结果 |
| “取消这个任务” | 简短回应处理进度 | 使用任务控制，成功后再报告取消结果 |
| “我先挂了” | 结束音频会话 | 已持久委托的工作继续，保留交付地址 |

OpenAI 的 GPT-Live 指南也明确区分语音打断和后台取消；仅靠 prompt 无法精确保证何时停止发声，应用必须控制播放并处理过期音频。[语音 prompt 指南](https://developers.openai.com/api/docs/guides/live-prompting)、[播放控制](https://developers.openai.com/api/docs/guides/voice-server-controls?api=live)

## 4. 技术路线比较

### 4.1 同一个文字边界，两种语音接入方式

最直接的管线如下。识别和合成可以使用本地组件或远端服务，取决于部署选择：

```text
用户声音 → 语音识别 → 文字要求 → Pipiclaw
Pipiclaw → 文字与状态 → 语音合成 → 用户听到声音
```

这是“转录成文字与 Pipiclaw 交互，再把输出转成声音”的准确描述。若希望能打断、边等结果边说话、口头摘要与屏幕详情不同，接入应用还要补上相应的控制逻辑。

另一种方式使用持续语音模型。用户与它直接以音频交谈，模型保留语音中的表达与节奏；需要工作能力时，由可信桥接把相关转录和状态组织成文字请求发给 Pipiclaw。结果仍以文字和事件返回，由语音模型解释，未必逐字朗读。无需额外假设前面必须再串一个独立识别服务。[官方迁移说明](https://developers.openai.com/api/docs/guides/live-migration)

因此，对 Pipiclaw 而言接口可以保持文字；对用户而言，两条路线的谈话体验与客户端维护成本可能不同，需要比较。

### 4.2 三类实现路线的取舍

| 路线 | 优势 | 接入方案需要承担什么 |
| --- | --- | --- |
| 流式识别 → 现有 agent → 流式合成 | 可替换各组件，原有文字工作流容易复用 | 端点检测、插话、播放队列、连续输入和后台并行的调度 |
| 单个 speech-to-speech 会话调用 Pipiclaw 的能力 | 语音理解与生成链路直接，减少中间串行步骤 | 避免把所有编码工具和长工作塞进通话模型；处理工具等待与工作状态 |
| 持续语音模型 + 独立工作后端 | 语音保持交互，原有 agent 继续推理与执行 | 上下文选择、授权、委托映射、结果播报和生命周期桥接 |

OpenAI 当前文档将 GPT-Live、Realtime API、串联管线列为不同架构。GPT-Live 支持全双工，并允许用 client delegation 接入自己的后端模型或 agent。因此它是 Pipiclaw 值得优先验证的一条路线，不代表已经测得中文或网络体验最优。[架构指南](https://developers.openai.com/api/docs/guides/voice-agents)、[GPT-Live 入门](https://developers.openai.com/api/docs/guides/live)

Grok Voice 是另一条可比较的 speech-to-speech 路线，公开 API 支持双向音频流、函数及其他工具，文档还提供语音与工具返回重叠的处理建议。API 的“亚秒级”宣传不能作为 Grok Bot 的实测数据，也不能代表调用 Pipiclaw 完成真实任务的延迟。[API 文档](https://docs.x.ai/developers/model-capabilities/audio/speech-to-speech)、[语音概览](https://docs.x.ai/developers/model-capabilities/audio/voice)

供应商选择应在同一中文录音集、网络环境、任务后端和设备上比较。重点包括中英混说、技术名词、任务 id、否定与更正、耳机及外放回声；不凭英语演示选择中文产品方案。

### 4.3 优先验证的组合与职责分工

```mermaid
flowchart LR
    U[手机或桌面语音客户端] <-->|实时音频| V[持续语音模型]
    V <-->|会话与委托事件| B[语音接入桥]
    B <-->|现有 Web API| P[Pipiclaw 持久会话]
    P --> T[现有任务车道与执行器]
    T --> R[真实状态与结果]
    R --> B
    B -->|经筛选的简短事实| V
    R --> D[文字记录与交付]
```

| 组成部分 | 负责 | 与其他部分的边界 |
| --- | --- | --- |
| 手机、桌面或网页设备端 | 麦克风、播放、静音、挂断、转录显示与本地播放控制 | 不持有服务端长期凭据，不直接读写 desk 状态 |
| 语音模型或识别/合成服务 | 理解声音、生成声音；持续语音模型还处理交谈和表达 | 依赖后端已核实事实，不自行宣告任务或外部动作完成 |
| 可信服务端桥接 | 鉴权、上下文选择、转录与请求关联、连接、恢复、结果路由 | 通过 Web API 使用助手，不建立另一套任务状态机 |
| Pipiclaw | 文字工作请求、模型和工具、任务推进、预算、持久化及交付事实 | 保持既有领域所有权；音频分片不进入聊天回合队列 |

语音入口是同一助手的客户端，不再创建另一套自我推进的编码 agent。语音模型可以回答简单口语互动；涉及任务现状和动作结果时，Pipiclaw 的实际记录是依据。

GPT-Live client delegation 的具体接线有两个容易漏掉的点：委托事件给的是 id、时间等元数据，不包含完整任务文本，应用要结合转录与工作状态构建请求；返回给语音模型的不同更新可以选择供其稍后使用，或建议它立即说出来。后者仍可能被改述，事件确认也不证明已经播放。[委托文档](https://developers.openai.com/api/docs/guides/live-delegation)

这些 API 中称为 thinking 的上下文更新也可能影响后续发言，不是存放隐私推理或秘密的安全区。桥接只传允许在本次通话表达的事实。

### 4.4 电话按钮与电话号码应分期

第一阶段可以是用户点开桌面或手机网页中的通话按钮，通过 WebRTC 持续交流。浏览器通常需要 HTTPS 或 localhost 和麦克风许可；API key 留在可信服务端。不能把长期 Web API key 放进链接或浏览器静态资源。[官方连接说明](https://developers.openai.com/api/docs/guides/live)

从钉钉卡片打开通话页面，符合 DingTalk-first 入口。内置 WebView 的麦克风、回声、后台保活、蓝牙及锁屏行为需要真机测试；必要时使用系统浏览器。此次没有确认“现有钉钉 Stream 机器人直接接入一对一实时通话音频”的可用公开接口，不能以此为首版前提，也不能由搜索不到断言平台绝不支持。

PSTN/SIP 电话号码、系统来电界面、Bot 主动呼叫和呼叫第三方是不同后续能力。公开语音 API 有 SIP 路线，但这不证明 Grok Bot/Dots 产品本身已经提供对应功能。用户主动呼叫可以独立成立，不必等主动拨号和电话运营接入。

### 4.5 当前价格仅用于估算

截至调研日，GPT-Live 1 的模型页标注每分钟 0.05 美元，按秒计费，后端模型及工具另计。十分钟的基础时长约 0.50 美元；完整成本还应核对初始化、重复连接、网络和后端工作，不能当作最终账单。[模型页](https://developers.openai.com/api/docs/models/gpt-live-1)、[成本指南](https://developers.openai.com/api/docs/guides/voice-latency-cost?api=live)

因此可以让工作持续运行，而按需要建立语音会话。长时间静音仍可能产生会话时长费用，语音空闲策略不能简单等同于关闭麦克风。

成本文档还说明，WebRTC 创建请求初始化时计入 15 秒语音时长，成功运行后抵扣到会话时长中，不能再向正常通话重复加 15 秒。频繁预建但未使用的连接和重连仍需纳入成本测量。

## 5. 延迟怎么解决、怎么测

### 5.1 把几种时间分别测量

| 时间 | 测量边界 | 意义 |
| --- | --- | --- |
| 接通时间 | 点击通话 → 可正常收发音频 | 包括鉴权、麦克风、协商与冷启动 |
| 首次回应时间 | 用户实际说完 → 客户端开始播放恰当回应 | 可包含必要的澄清或承接，不能等同答案到达 |
| 首个有用结果时间 | 用户实际说完 → 播放首个已核实的结果 | 防止用“正在查”掩盖后端延迟 |
| 打断停止时间 | 用户开始打断 → 旧声音在客户端停止 | 必须算播放缓冲，不能只看服务端取消 |
| 持久交办时间 | 用户给出有效要求 → 任务等事实可靠保存 | 防止“说已安排”但实际没有留下工作 |
| 最终交付时间 | 请求明确 → 结果可取得 | 单独观察工作耗时、失败和恢复 |

建议原型的初始目标：普通承接或简短上下文答复 p50 不超过 0.8 秒、p95 不超过 1.8 秒；明确打断后的旧音频停止 p95 不超过 0.3 秒。它们是候选验收线，不是厂商实测，也不适用于任意复杂任务。根据真实中文录音和部署网络调整。

语音端点与延迟计时以录音中真实的发声边界和客户端播放为准，不能只用服务端转录事件代替。用户犹豫、改口或停顿后继续说时，抢答也应计入质量问题；“越早发出声音”并不总是更好。除 p50/p95 外，记录样本数、失败与未回应次数，避免把掉线和超时样本排除后得到偏好的数字。

复杂调查可以持续更久，但要及时说明会继续查，并允许用户接着说话或挂断。首次有用结果与最终完成仍单独报告，不能靠频繁承接语把指标做漂亮。

### 5.2 有效的优化顺序

- 把麦克风准备、鉴权与连接初始化尽量并行；在用户已进入通话准备页时预备稳定配置，不暗中开启麦克风。
- 音频优先走适合实时媒体的连接，使用回声消除、噪声处理和有上限的播放缓冲。避免把音频分片塞进聊天回合队列。
- 轻量口语互动直接使用已选上下文，需查询真实状态时才走后端。编码、测试、调研进入后台任务，不阻塞通话。
- 保持后端连接和稳定 prompt 前缀，缩小每次携带的无关背景；尽早返回完整、已核实的简短结果，不等报告全文完成。
- 在用户仍说话时，允许根据已明确的信息预取只读数据；部分转录变化后废弃过期结果，不能提前执行不可撤销动作。
- 不把严格的数百毫秒停止要求交给 prompt；客户端清掉已排队旧音频，并协同取消或更新相应输出。

这些方法与 GPT-Live 官方延迟建议一致，但每一项的收益取决于部署环境，应一次改变一个因素做比较。[后端延迟建议](https://developers.openai.com/api/docs/guides/live-delegation#reduce-backend-latency)

## 6. 对当前 Pipiclaw 的具体影响

### 6.1 可以直接复用的底座

- Desk 的工作上下文、持久记忆与频道绑定。
- 事件定义、preAction、持久唤醒与任务模板。
- 一次性任务、独立任务车道、预算、用户问题和报告。
- 原有工具、安全边界和内外部执行器。
- Web API 持久 conversation、响应记录、HTTP 后台请求和流式输出。

语音上下文应选择已授权的用户身份、desk、当前讨论对象、近期决策和任务事实，并在必要时检索。不能把整个 desk 的日志、所有会话或私聊内容无差别装进通话。

### 6.2 当前接线的四个缺口

**断连语义。** `src/webapi/routes/websocket.ts` 的 `onClose` 会取消该连接尚未结束的响应；HTTP 同步/普通流也有断连取消。已有 HTTP `background: true` 提供不同语义。首版应由可信的语音桥维持工作连接，或使用后台请求/持久任务完成交接；不应修改现有 WebSocket 语义让所有客户端行为变化。API 后台响应仍不等同于可在 daemon 重启后继续执行的任务。

**会话级结果订阅。** `src/webapi/service.ts` 会把运行时主动推送保存为独立响应；现有 WebSocket 主要跟随自己创建的 response 链，没有直接面向某个 conversation 的持久消息订阅接口。原型可以有明确间隔、记录游标的查询；真实通话要验证并补齐必要的会话结果到达机制，且保留读取授权与去重。此处是具体语音客户端的需求，不是追齐 OpenAI 协议的工程。

**连续语音与修改意图。** 现有 `response.steer` 可以转达回合中的补充，但不等于音频会话的连续语义。需要把部分转录、更正、委托 id、任务 id 和意图版本关联起来；旧版本结果不能覆盖新要求。原生语音没有必要机械照搬文字“一条输入等一个完整回答”的队列。

**请求接收结果不明。** 当前 Web API 没有显式的客户端幂等键协议。服务器接收请求后、客户端取得 response id 前断网时，桥接端的一份本地映射不足以保证安全重试；`metadata` 也不具有唯一性约束。原型不能在接收结果不明时盲目重发有副作用的请求。若要求自动恢复这类故障，后续设计必须补齐可核对的接收记录与去重边界，并验证崩溃窗口；不能把“先查询再重试”写成已经具备的保证。

上述判断对应 [WebSocket 生命周期](../../src/webapi/routes/websocket.ts)、[HTTP 后台请求](../../src/webapi/routes/responses.ts)、[推送记录](../../src/webapi/service.ts)与[请求参数](../../src/webapi/request-policy.ts)。它们是代码基线上的行为，未来实现前须重新核对。

### 6.3 首版需要的最小事实

语音桥可以保留有上限的会话事实：当前持久 conversation、允许使用的 desk、关联的任务、最新意图版本、已提交请求、已返回事实和客户端已播放范围。每类记录都有明确用途，避免引入一个新的通用工作状态系统。

网络重连后，先查询已有请求和任务再决定是否重发；请求不确定时不能再创建一份任务。后台动作完成、结果保存、音频生成、音频播放是不同事实；客户端播放完成也不保证人理解了内容。

有效工作要求应在通话中及时可靠保存，不能等正常挂断时才保存整场内容；否则掉线会丢掉已经口头答应的委托。需要区分用户原话、转录修正、桥接生成的请求和助手摘要，不能把摘要中的推测伪装成用户原话或扩大授权。

通话结束时可整理简短的决定、已交办事项及未决问题。其回写方式属于待设计的接线，不假定现有 API 已有导入通话记录的接口。临时工作状态仍属于任务等已有载体，持久事实沿用现有记忆整理流程；不直接写生成的 MEMORY.md，不手工写 journal。

### 6.4 保持现有工程边界

语音客户端优先作为 Web API 客户端接入，类似 TUI 的边界；不让客户端直接操作 desk 文件、读取服务端 key 或调用 runtime 内部类。确实需要新的原生 transport 时，再按架构表引入对应模块，而不是先扩展所有底层接口。

主动发现若需同时使用任务事实、记忆和外部变化，由 runtime 组合已有领域及注入端口；events 不能因此开始读写任务文件。一次性任务执行、委派结算和记忆维护继续由原所有者负责。

新发现流程的模型指导应放在经过维护的 playbook；长期职责与数据不能成为运行时任意重写系统指导的通道。信息源正文始终是数据，不能伪装为用户授权。

## 7. 建议的验证顺序

| 阶段 | 具体产物与体验 | 决定是否继续的证据 |
| --- | --- | --- |
| A：最小真实通话 | 一个用户、一个 desk、一条持久会话；支持说话、打断、查状态、交办及挂断后继续 | 中文可懂、关键参数正确、实际可打断、任务没有漏建或重复 |
| B：谈话与工作并行 | 用户追加和纠正时及时转达；结果回来选择口头摘要或文字详情 | 旧结果不会覆盖新要求，后台慢时仍能交谈，完成后不会乱报 |
| C：一个主动工作场景 | 发布准备：关注新阻塞、相关反馈和截止时间，按授权调查与准备结果 | 在用户询问前提供可用证据；没有变化不反复生成同类工作 |
| D：打磨入口与时机 | 钉钉入口、移动真机、重连、回到通话时的衔接与摘要 | 手机/桌面场景稳定，用户需要输入的事项能及时看到 |

语音交互可单独创造价值，不必等待完整的长期职责系统。主动发现也可以先用已有事件与有限的任务模板实验，确认实际收益后再决定是否引入新的职责实体。

### 7.1 必须覆盖的真实对话

- “查发布风险，先不要改代码。”说到一半更正范围，最后的工作行为正确。
- “把后天改成明天。”语音状态、后端输入与持久任务一致。
- 长任务运行中询问另一件小事，不被长任务队列拖住。
- 用户说“停一下”时旧声音停止，但原有任务不会被误取消。
- 用户明确取消时核对取消结果，不口头答应后继续旧工作。
- 结果到达时用户正在说话，系统等自然停顿再响应。
- 挂断/掉线后继续执行已经持久交办的任务；重连不重复创建。
- 用户开始下一次通话时，简短说明有关的新进展，允许换话题。
- 没有新变化时不重复主动建议；真实截止时间临近时不因摘要策略而错过。

### 7.2 测试与质量证据分层

确定性 e2e 证明鉴权、输入版本、任务落盘、断连、重连、重复请求、交付和事件游标等机制；用受控 provider 和明确事件构建时序，不断言模型说得是否自然。模型理解更正、何时插话、口语简洁度、中文识别和声音自然度属于行为评测及录音试听。

真实语音对比应固定录音、后端、工具、网络和播放配置，分别记录任务结果、工具行为、端到端音频延迟、非必要重叠、静默与会话故障。自然的语音不证明后端正确执行；后端成功也不证明结果已正确播报。[官方语音评测方法](https://developers.openai.com/cookbook/examples/audio/voice_agent_evaluation)

实施时遵循仓库的测试准入规则，优先延伸已有价值链；改动 runtime、记忆、委派或命令平面时运行 typecheck、unit、arch 和确定性 e2e，改模型指导时安排相关行为探针。此次仅新增调研文档，没有执行付费调用或将任何延迟目标标记为通过。

## 8. 仍需实测或补充证据的事项

- Grok Bot、Muse、Dots 的内部主动调度算法和端到端通话性能没有足够公开证据。
- GPT-Live 与 Grok Voice 在用户实际部署网络、中文技术语境和所用设备上的体验尚未比较。
- 钉钉内置 WebView 的麦克风、锁屏和后台音频表现需要真机验证；平台原生 Bot 通话入口尚未确认。
- 跨钉钉/Web API 的显式交付关联需要设计，不等于使用同一 desk 就自动共享会话或转投通知。
- 语音原型应实际测量持久交办、挂断、纠正和重新接入，之后再确定生产接口与模块落点。

本次材料已足够支持一个有限范围的语音验证，以及一个真实目标驱动的主动工作实验；尚不足以承诺任意网络下的秒级回答、通话体验领先，或无需任何适配即可接通钉钉原生电话。
