# 更少的角色，更完整的交付

> **读者**：正在组织多个执行者，希望减少交接损耗和重复岗位的人。
> **前置**：[智能体委派](../sub-agents.md)、[示例配置](../../examples/sub-agents/README.md)。

角色数量没有最优常数。值得缩减的是交接边界：让实现者交付一个完整改动，让验收者检查最终产物，让主 agent 负责目标与反馈裁决。

当前示例优先按能力与成本组织 `agents/`；`roles/` 保留专门作业与只读边界的参考。旧版“默认安装五个岗位角色”的推荐与一次性 review 已清理。实际条目、模型和权限参数以示例文件及其 README 为准。

## 什么时候值得独立配置一个角色

一个角色至少应提供一种持续价值：

- **执行边界不同**：例如目标 CLI 强制只读，或只负责 Git 提交。
- **能力或成本不同**：同类工作可由不同模型或执行器以不同代价完成。
- **上下文需要隔离**：一次大量检索只需向主 agent 返回少量事实。
- **经常使用专门方法**：流程复杂且常用，放进通用角色会干扰其他工作。

只有岗位名称不同、实际能力和约束相同的角色，不值得增加一次选择与交接。偶尔使用的方法可以在本轮任务里说明，或由 skill 指导；不必为每个工作阶段创建角色。

## 完整实现单元比固定流水线更便宜

实现者应在同一个上下文中完成直接相关的代码、测试、文档与必要检查。把文档留到 verifier PASS 之后再交给另一个执行者，会改变已验收产物，可能需要重新验收。

工作流由任务触发：

| 工作 | 合理的交接 |
|---|---|
| 很小的改动或明确事实查询 | 主 agent 直接完成 |
| 大量检索，但最终只需几个事实 | 隔离调查，再返回证据与未覆盖范围 |
| 目标明确的实现 | 完整实施与自查，再按风险独立验收 |
| 高代价设计取舍 | 一项能改变后续选择的调查，再决定实现 |
| 独立报告或数据产物 | 按完整产物委派，不因岗位目录额外拆分 |

reviewer 用于寻找缺陷与提供裁决材料；`purpose=verify` 用于核验任务完整的 DoD/Verification。不是每个任务都需要把两者串行调用。

## description 管选择，任务描述管本轮目标

角色 description 应说明适用场景、执行边界、能力与代价。正文只保留跨任务稳定的工作纪律；本轮范围、输入、约束和通过条件由委派描述提供。

避免把岗位写成必须经过的流程。例如“planner 总是先做完整规划”会制造第二个目标解释者；有价值的调查应回答一个明确问题，提供能区分方案的实验或证据。

交付摘要应服务于下一步决策：结果、证据位置、未验证项、剩余风险和可接续入口。完整 stdout 与产物保留在 artifacts，不必全部复制到主上下文。

## 权限、方法、模型和时限分别判断

`mutates` 用于 lease 与审计，不能证明只读。拥有 bash 的内置角色仍可能写文件，外部角色依赖目标 CLI sandbox 与运行账号；真实边界见[授权与安全](../sub-agents.md#授权与安全边界外部角色)。

工具和模型按角色能力配置，方法按本轮任务选择，墙钟时限作为故障上限。不要同时改 prompt、模型和预算，再把结果归因给其中一项；任意缩短时限也可能让便宜的 run 变成昂贵的重试。

先用代表性任务比较完整交付：遗漏要求、无效交接、返工次数、总费用和完成时间。没有可复现改善时，不增加角色继承 DSL、固定全角色流水线或自动路由器。
