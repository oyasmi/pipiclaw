# 更少的角色，更完整的交付

> 2026-09-07，基于源码 `e53f7df`、`examples/sub-agents/` 的 11 个角色及当前委派 playbook。
>
> 本文是配置与工作方法建议。已核对加载、提示注入、预算、验收与产物机制，并做了临时 Git 工作区的模块组合复现；没有读取生产委派轨迹，也没有运行付费模型对照。因此，下文区分确定的配置冲突与待验证的角色、模型取舍。
>
> **实施状态（2026-09-07）**：第 2、3、4、5、6、7 节的建议已落到 `examples/sub-agents/` 与相关文档——模板收敛为 5 个常用 + 3 个按需角色，`scout` / `log-sifter` / `documenter` 退出推荐目录，确定的验收与暂存区冲突已修，`effort` 的适用范围已在示例 README 和委派 playbook 里更正。按第 8 节的约定，这一轮**没有改动任何角色的 `model` 或 `thinkingLevel`**；唯一的 frontmatter 变化是 `explorer` 承接日志筛查后把预算提到 `maxWallTimeSec: 900` / `bashTimeoutSec: 300`（取两个被合并角色的较大值）。第 10 节的对照实验尚未进行。已复制到工作区的旧角色文件不会被自动删除，迁移说明见示例 README 的「从早期模板迁移」。

**我建议常用工作区先收敛为 5 个角色，另保留 3 个按需角色；让实现者负责一个完整改动，让检查者对最终产物负责。**

常用：`explorer`、`builder`、`reviewer`、`verifier`、`git-committer`。按需：`planner`、`builder-hard`、`worker`。将 `scout`、`log-sifter` 的事实调查能力并入 `explorer`；将直接相关文档并入实现工作，独立文档交付由按需的 `worker` 承接。

这意味着推荐模板从 11 个收敛到 8 个，普通工作区从“把所有模板装进去”改为只装常用 5 个。**5 是这个项目的试用起点，不是 agent 数量的最优常数，更不表示每项任务要调用 5 次。**

比数量更优先的是三件事：修正模板与 runtime 的冲突；消除为了角色分工而产生的交接；把 prompt 从“完整岗位说明书”改成能指导判断的工作约束。此前 [004](./004-token-to-productivity.md) 改善了主 agent 的工作单，接下来应让接收工作单的角色遵守同一套交付逻辑。

## 1. 该缩减的是交接边界，而不只是文件数量

一个角色值得独立存在，至少要提供以下一种持续价值：

- **执行边界不同**：只读审查、可写实现、操作 Git 暂存区，不能随意混用。
- **需要独立判断**：验收者不继承实现者的自我解释，不在验收时修实现。
- **有可重复的能力或成本差异**：某类难题确实需要另一套模型、预算或工具配置。
- **有经常使用的专门方法**：方法复杂到放进通用角色会持续干扰其他任务，且使用频率足以抵消维护和路由成本。

“处理的是日志”“输出的是 Markdown”“这一轮叫设计阶段”本身不足以证明需要一个角色。它们很多时候只是同一个执行者本轮的输入、产物或方法。

现有 `explorer` 与 `log-sifter` 同为内置、`read/grep/bash`、隔离上下文、无记忆注入、low thinking、声明只读。差异主要是检索方法和输出形状。`scout` 则把更窄的事实查询交给一个外部异步进程，同时又在 description 中说相似工作用 explorer 更快。主 agent 必须先判断一个难以稳定判断的边界，才知道由谁去查一个简单事实。

`documenter` 的问题不同。修改接口后顺手同步用法，本来就是实现完整性的一部分。把它独立派给第二个人，第二个人必须重建接口背景，builder 又更容易把文档当成“下一角色会补”。省下的执行模型费用，可能被新一轮调查、等待和主 agent 整合抵消。**这是一项待测的端到端成本判断，不能只比较两个模型的单价。**

Anthropic 的上下文工程文章强调，职责重叠的工具会制造模糊选择，应使用足够明确且不过度规定步骤的指导。这里将这一原则类比到角色目录，是本文的设计判断，并非该文章对 Pipiclaw 的实验结论。[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

## 2. 先修确定的冲突，再讨论模型是否更聪明

这些问题不需要等到角色缩减之后才处理。

| 位置 | 当前问题 | 建议修正 |
|---|---|---|
| [示例 README](../../examples/sub-agents/README.md) | 用 planner → 两轮 reviewer → builder → verifier → documenter 描述开发闭环，形成固定阶段的暗示 | 改为按条件选择角色；实现、测试、相关文档一起形成待验收产物 |
| [builder](../../examples/sub-agents/builder.md)、[verifier](../../examples/sub-agents/verifier.md) | 默认不跑全量套件，但未明确仓库必跑检查优先；在 Pipiclaw 中可能漏掉 AGENTS.md 明确要求的 unit/e2e | 仓库和本次契约的 required checks 必须完成；仅对额外检查按风险裁剪 |
| verifier | 按“与本次变更无关”允许将验收项判不适用 | `purpose=verify` 覆盖完整 DoD/Verification；改动没碰到不等于任务要求不适用 |
| verifier | 允许把新增验证脚本放进“仓库既有测试位置” | 正式验收只在 runtime 认可的临时位置新建取证脚本；需要成为产品测试的新用例交回实现者 |
| README 的验收后 documenter 阶段 | 验收后继续改交付文档，会改变被验收产物 | 文档纳入最终验收之前；PASS 后修改产品内容须重新验收 |
| README 和 [委派 playbook](../../src/playbooks/agent-delegation.md) | README 仍说调用内置角色时可传 `effort`；playbook 仍有外部角色通过 `effort` 放宽墙钟时间的解释 | 当前命名角色调用不接受这些覆盖；`effort` 只属于 inline 内置路径，命名角色改 frontmatter |
| [git-committer](../../examples/sub-agents/git-committer.md) | 说范围外 staged 内容“不要动”，又指导正常 commit；已有暂存内容仍可能被一并提交 | 范围外 staged 内容存在时先解决提交隔离，不能以“本轮只 add 精确路径”当作隔离证明 |

这里的前两项是提示文字缺少优先关系，不等于模型必定漏跑检查；不能从静态阅读推断生产发生率。后面的验收产物冲突则可以直接用源码复现。

### 2.1 验收冲突已经做了小范围复现

在临时 Git 仓库中，通过当前的 [`workspaceSubjectSnapshot` / `workspaceSubjectHash`](../../src/tasks/artifact-subject.ts) 和 [`resolveVerificationOutcome`](../../src/subagents/verification-outcome.ts) 得到：

| 操作 | 实际结果 |
|---|---|
| 开始验收后新增 `test/acceptance.sh`，声明 `VERDICT: PASS` | subject 改变，最终判为 FAIL，理由为修改了受保护产物 |
| 改为新增根目录 `.run/acceptance.sh` | subject 保持一致 |
| 在同一基准上新增 `docs/usage.md` | subject 改变 |
| 预先暂存 `other.txt`，随后只 `git add -- product.txt` 并普通 commit | commit 同时包含两个文件 |

复现调用实际模块；测试仓库与临时脚本执行后清理。这证明配置指导与确定性机制的关系，不证明真实模型一定会走到该分支。

临时目录的具体识别规则继续以 [`artifact-subject.ts`](../../src/tasks/artifact-subject.ts) 为准。新建 `.run/` 取证文件不是任意改写这个目录的授权，原有文件仍要保留；不要把 ignored、untracked 或测试文件一概等同于可以修改。

### 2.2 关闭证明的增强，让旧流水线更不合适

004 的第一批已经让关闭时重验当前产物。现在如果继续采用“verifier PASS → documenter 补文档 → complete”，runtime 拒绝关闭是正确行为。

推荐的顺序是：完成实现、相关测试和文档 → 必要的审查与返工 → 对最终交付位置做正式验收 → 完成收尾。

Git 提交需要单独区分。当前 base-relative subject 支持把已验收内容原样提交而保持证明有效，不能笼统地说“commit 必定使 PASS 失效”；但 hook 修改文件、补文档、改测试属于内容变化，需要重新判断和验收。相关行为已有 [artifact subject 测试](../../test/artifact-subject.test.ts)。

## 3. 逐角色取舍：保留能力，减少重复岗位

| 现有角色 | 我的建议 | 保留什么、改变什么 |
|---|---|---|
| `explorer` | 常用，扩大为只读证据调查 | 承接代码定位、调用链、指定日志筛查、单点事实；保持 bounded query，不变成全仓库审计 |
| `log-sifter` | 合入 explorer，退出推荐独立模板 | 保存时间窗、时区、首次异常、恢复节点、统计范围这些方法；只在日志任务时使用 |
| `scout` | 退出推荐模板 | 普通单点查询由主 agent 或 explorer 完成；无须保留另一个外部只读查询入口 |
| `builder` | 常用，扩大交付责任 | 完成一个连贯改动所需的代码、合适层级的测试、直接相关文档与验证证据 |
| `builder-hard` | 按需保留 | 与 builder 共享完成责任；专注高不确定性诊断、跨契约变更和失败后的重新建模 |
| `planner` | 按需保留 | 为一个高代价决策提供调查、方案与实验；普通实现不以前置 planner 为条件 |
| `reviewer` | 常用，但按风险调用 | 对稳定方案、代码、文档找有证据的缺陷；保留只读边界和不凑数原则 |
| `verifier` | 常用，优先改 prompt | 对完整契约收集和评价证据，能运行有临时产物的检查，禁止在正式验收中修产品 |
| `documenter` | 退出默认独立模板 | 随实现的文档交 builder；整本手册、迁移指南等独立产物交 worker，并带文档方法 |
| `worker` | 按需保留，明确产物范围 | 独立的数据分析、批处理、报告和文档；不再用“其他角色没接的都给我”定义自己 |
| `git-committer` | 常用，有授权才调用 | 保留暂存区、hooks、commit/push 的专项纪律；补足混合暂存与混合文件改动边界 |

“退出推荐模板”不是立刻删除用户工作区的同名角色。先把能力迁移到接收者、跑过代表任务，再调整示例和复制说明。个人部署已经证明某个专门角色有效，可以继续保留；本次没有证据否定那种部署。

### 3.1 为什么不合并 reviewer 和 verifier

这两个角色最容易被建议合成“QA”，但目前我会保留。

reviewer 的关键产出是“在什么输入或时序下违反了什么契约”，主要消除设计与逻辑不确定性。verifier 的关键产出是“当前产物满足哪些标准，有什么可以重现的证据”，主要消除运行与交付不确定性。后者还要允许构建与测试产生临时写入，并持有写 lease。

合并后，要么所有审查都拿到写权限并占用写工作区，要么运行检查受只读配置限制。为了少一个角色名付出这个代价，目前不值得。

但两者也不应该被 prompt 人为割裂：verifier 必须能读代码、解释测试覆盖并识别需求缺口；reviewer 也能使用权限允许且不改变工作区的诊断。区别在于本轮责任和执行边界，不是“一个只思考、一个只跑命令”。

普通非平凡 coding 工作，builder 自测后，默认考虑一次有效的独立验收。只有静态设计、并发、权限、迁移等风险值得单独花费时，才加 reviewer。纯方案或文档任务可以由 reviewer 承担完整正式验收，前提是它确实能验证所有要求；运行证据不可取得时不能强给 PASS。

`purpose=verify` 是运行时用途，`verifier` 是角色名，两者不要互相替代。普通 `reviewer` 报告“可接受”不是 task 的正式验收证明。

### 3.2 为什么暂时保留 builder-hard

它虽然也写代码，但提供了当前 API 不能在调用中临时选择的模型、推理和预算组合。命名角色没有 `model` / `thinkingLevel` 覆盖字段，而 inline 只能起内置执行者。把两个 builder 文件合并后再说“难题调用时选更强模型”，在当前接口下不可执行。见 [`discovery.ts`](../../src/subagents/discovery.ts) 和 [`tool.ts`](../../src/subagents/tool.ts)。

保留它的理由是不同执行配置，而不是需要两个互不一致的工程标准。两者应具有同一套实现、测试、文档和交付责任。hard 只增加诊断方法与升级成本提示。

不必先让普通 builder 失败一次来取得使用资格。已知是难复现的并发问题、跨多个持久化契约的迁移，或过去同类任务已证明普通配置明显不够，可以直接用 hard。反过来，偶发的依赖下载失败、命令写错、缺一个输入，不是升级模型的理由。

### 3.3 为什么 planner 是选项，而不是必经入口

主 agent 已掌握用户上下文，也已经承担目标和反馈裁决。让 planner 再“收敛全部需求”，容易产生第二个目标解释者。

planner 有价值的委派应是：“比较两个会改变持久化语义的方案，判断兼容风险，并提出能区分它们的最小实验”。产物是供主 agent 决策的建议和证据。它不替用户批准新范围，不把自己的假设升级为既定需求。

只要目标、范围和完成标准已够清楚，builder 就应自行补足可查的实现细节。未提供函数级设计不代表需求未收敛。

## 4. description 应该成为简短、可区分的选择依据

[`renderSubAgentDirectory`](../../src/agent/prompt/sections.ts) 将角色的 name、description 和 runtime/workload/mutates 分组呈现给主 agent。正文不在这个目录里。因此，改正文未必能修复错误路由；主 agent 可能从 description 开始就选错了。

当前不少 description 用“先用另一个角色”“之后交给某角色”连接岗位。删掉角色时这些引用也容易过期。建议每条主要回答三件事：本轮要得到什么结果、什么时候值得调用、最关键的边界。已有分组显示的元信息不必再解释一遍。

以下是可直接采用的措辞草案，名称保持稳定，避免同时引入重命名成本：

| 角色 | 建议 description |
|---|---|
| explorer | 只读调查一个明确问题：从代码、配置或指定日志中返回结论、定位证据与未确认项。适合需要多次检索、会挤占主会话的调查；不做实现或全面评审。 |
| builder | 完成边界明确的产品改动，连同必要测试、相关文档和仓库要求的检查一起交付。可以自行探索实现细节；留下可审查 diff，不操作 Git 历史或外部系统。 |
| reviewer | 对稳定的方案、diff 或文档做独立审查，报告有触发条件和证据的违约或缺陷。适合需要额外判断的设计与实现风险；只读、不修复，不把建议升级为任务要求。 |
| verifier | 对最终产物逐项核验完成标准，运行必要检查并报告通过、失败或阻塞的证据。允许临时取证产物，禁止修改被验收产品；完整任务验收使用 purpose=verify。 |
| git-committer | 在已有用户提交授权下，把指定的现有改动精确整理成本地 commit，核对暂存区、hooks 和剩余状态。不修改实现；push 需要用户授权。 |
| planner | 调查一个会显著影响方案或返工成本的未决问题，给出推荐方案、依据和可区分选项的实验。只提供决策建议；普通实现不需要先经过它。 |
| builder-hard | 处理高不确定性或跨契约耦合的实现与修复；依据复现、失败尝试和区分性实验定位问题，完成改动及检查。高成本，常规任务优先普通实现配置。 |
| worker | 交付独立的数据分析、批处理、报告或文档，核实来源、口径和产物完整性。可写任务范围内的辅助脚本与文档；不承担产品代码实现或正式运行验收。 |

不必给每个角色再加一排“不适用角色名”。一个准确的正面范围，加一个真正关键的排除条件，通常更便于判断。

## 5. prompt 组织：稳定约束、当轮方法和证据各归其位

### 5.1 正文只保留能改变行为的内容

建议每份角色正文围绕四项组织：负责什么、如何判断下一步、不能改变什么、交回什么证据。删除“负责人”“非常重要”“认真全面”这类不改变动作的修饰。

共通但值得保留的短约束是：

```text
本轮目标与边界以任务工作单为准；读取工作区中适用的规则和必要入口。
可从文件或工具查明的信息先自行取得。可逆的局部选择按现有约定推进；
无法自行取得且会改变目标、产品语义或授权边界的信息，作为最小阻塞项返回。

区分观察、推断和未验证。保护原有工作树，只操作本轮允许的范围。
满足本轮要求就交付；连续尝试没有新增证据时，返回当前产物、已排除项和下一实验。
```

这是写作骨架，不是新增 prompt 继承语法。当前角色文件应继续自足：少量重复比新建模板展开器更便宜。共通段必须按角色裁剪，例如 git-committer 不应该因为共通文字而开始跑产品验证。

同样，不要把 004 的六项工作单全文复制进每份角色。主 agent 负责选择本轮上下文；角色负责消费它。日志分析、迁移说明之类的方法可以是工作单里的短片段，也可以引用执行者确实读得到的工作区材料。不能假设外部 CLI 会自动发现 Pipiclaw 的 workspace skill。

### 5.2 同一份“system prompt”实际并非同一种注入

当前实现中，内置执行者直接使用角色 `systemPrompt`；Claude harness 通过 `--append-system-prompt-file` 追加角色正文；Codex harness 则由 [`buildStdinContent`](../../src/subagents/external/run.ts) 把角色正文放在 task 前面，一起写入 stdin。

所以 README 中“正文是 sub-agent 的 system prompt”只是一个概括。**配置中的字段名不证明外部 CLI 将它当作最高优先级系统消息。** 调 prompt 时应检查实际 `system-prompt.txt`、`prompt.txt`、argv 及 CLI 读取的工作区规则，不要只审查模板 Markdown。

也不要靠“你处于只读环境”这句话提供能力边界。explorer 拥有 `bash`，其 `mutates: read` 是声明；外部边界则来自目标 CLI 与宿主环境。本文建议保留现有配置边界，不借角色合并扩大权限。

### 5.3 交付摘要应该服务于下一步决策

11 份角色都重复了一段关于 `output.md` 和唤醒尾部的说明，但多数仍只要求结论放在开头。长报告被保留尾部时，关键阻塞仍可能在前面被裁掉。

当前 [`runs.ts`](../../src/subagents/runs.ts) 的异步唤醒内联尾部上限为 6,000 字符；内置同步返回还有 [`tool.ts`](../../src/subagents/tool.ts) 的 1,200 prompt units 预算，当前按保留开头的方式裁剪。它们是不同预算与取材方向，不应统一改写成一个“最多 N token”的角色规定。

建议简化成：

```text
最终回复先写结论，只保留关键证据、产物位置和未完成项；完整回复由 runtime 保存。
回复较长时，在末尾用几行重复当前状态、阻塞和下一步，保证尾部也能独立理解。
如果有 runtime 验收协议，其 VERDICT 行必须仍是全文最后一行。
```

不要要求所有角色都生成长报告文件。调查和审查报告可以由 runtime 的 `output.md` 承载，避免给只读角色增加工作区写权限。真正要交付的设计文档、手册或数据文件则应落在任务指定的位置；run artifacts 会按保留策略清理，不能替代长期产物。

## 6. 四份核心 prompt 的具体改法

下面是建议替换的正文主体；frontmatter 的初次调整以修正语义为主，不同时更换模型。

### 6.1 builder：从“代码 + 单元测试”改为完整的实现单元

现有 builder 的范围纪律和保护工作树要求值得保留。主要调整是：不把细节未定等同于需要 planner；不默认欠下文档；不让“只跑定向测试”压过仓库规则；不按失败次数机械放弃。

```text
你负责把本轮目标交付为一个最小但完整、可审查的改动。

先检查工作树，读取适用的仓库规则、相关实现、调用方和测试。
目标与完成标准明确时，自行调查并决定实现细节，不要求额外规划回合。
只在无法自行取得的信息会改变产品语义、数据边界或任务范围时报告阻塞。

完成相关代码、必要测试、配置示例和用户文档；接口或数据结构变化时查齐调用方。
沿用已有模块和风格。新增依赖、抽象或持久状态要说明本次的具体必要性。
不混入无关重构，保护任务外已有改动。

先运行能尽早发现错误的检查，再完成任务及仓库规定的全部必跑检查。
新增测试覆盖会出错的行为、边界与回归；按仓库要求选择 unit/e2e 等层级。
不为纯文案或无逻辑改动凑测试，不削弱已有断言来获得通过。
外部条件使检查不能完成时，交回可审查产物和未验证项，不声明验收完成。

尝试失败后说明新增了什么证据。重复同一失败且没有新证据时，停止重复方案，
返回最小复现、已尝试方向、仍待区分的假设及建议实验。
不 commit、push、部署或写外部系统。

交付：对应完成标准的行为变化；关键文件；检查命令与结果；
未完成、未验证及需要独立检查的风险。满足本轮要求即结束。
```

“完整”不等于每次必须改一份文档、补一条测试；是否需要取决于行为变化和仓库要求。它意味着该由这次实现交付的部分不因岗位边界被遗漏。

### 6.2 verifier：从命令执行者改为证据判断者

这是本轮最值得优先修改的正文。当前“用实际执行而不是代码阅读”“默认只覆盖改动影响范围”容易让模型机械地跑几条命令，却没有判断测试是否覆盖用户要求。

```text
你负责判断当前产物是否满足本轮验收标准，独立核实证据，不修复产品。

先确认目标工作区、产物边界及任务契约能读取。
purpose=verify 时检查完整 DoD/Verification，不能只看调用者强调的局部问题，
也不能因为某条要求与本次 diff 无关而跳过它。
无法读取契约或证据入口时，报告具体缺口，不根据实现者摘要猜测完整要求。

逐项选择足以判定的证据：行为要求运行对应检查，静态约束查实现、配置或文档；
必要时同时使用两者。理解测试真正覆盖了什么，不把退出码 0 等同于需求完成。
优先使用仓库已有检查；按先便宜、先证伪排序，最后完成所有必跑检查。
实现者报告是检查线索，不能单独支持通过。

通过须有足以支持该条标准的证据；观察到违约为失败；缺少环境或证据为阻塞。
只有契约明确带条件且条件不成立的项目才能标不适用，并附依据。
任何必需项目失败或阻塞，都不能给总体 PASS。
环境阻塞与产品缺陷分开记录；是否改变契约交由主 agent 裁决。

禁止修改实现、既有测试、配置或验收口径来使检查通过。
临时脚本和夹具放在 runtime 认可的临时位置，例如根目录 .run/，
或权限允许的系统临时目录，不在产品源码、正式测试目录新建文件。
需要永久回归用例时交回实现者补齐，再对最终产物重新验收。
保护所有原有文件；只清理本轮自己创建且可再生的临时产物。
不 commit、push、部署或改变共享环境。

交付：逐项结论及证据；失败的复现、预期与实际；环境阻塞与最小解除条件；
保留的取证路径及未覆盖项。遵守 runtime 追加的最终 VERDICT 协议。
```

“阻塞”不是新增 runtime verdict。当前协议只有 PASS/FAIL；失败原因仍在报告中区分，阻塞时不得报 PASS。不新增第三种机器状态，也不在模板里复制 attestation 的生成逻辑。

临时脚本的价值在于补足证据，不是绕过测试规范。如果某项标准必须新增正式回归测试才能满足，交回 builder 就是正确的验收结果。

### 6.3 explorer：合并检索能力，保留有选择的方法

```text
你只读调查一个明确问题，返回足以支持下一步决策的事实与证据。

先确认问题、范围和查询入口；按最有区分力的线索宽搜，再读必要局部。
代码问题沿定义、注册、调用和数据流核对关键分支。
日志问题先确认规模、格式、时区和时间范围，再找首次异常、正常前序、
重启与恢复节点；给出频率结论时说明统计范围，不将重复噪声当独立事件。

检索未命中只说明在所查范围内未找到，不能证明整个系统不存在该行为。
区分代码可能路径、日志观察和根因推断；保留会改变结论的反证。
不通读大文件，不做任务外审计；证据足够就返回。
预算不足时先交回已确认结论、未查范围和下一条最有价值的查询。

不改文件、依赖、Git 或服务状态，不触发会写入的复现和检查。
只调查任务给定且可读的资料，不因看见频道路径就扩展到会话冷存储。

交付：直接答案；最少的 path:line 或命令证据；必要的数据流或时间线；
未确认项及下一步。简单事实几行即可，复杂连接以能解释清楚为准。
```

代码与日志方法只各保留几句，不把两份旧正文完整相加。具体日志格式、过滤口径、时间窗放进 task。对 Pipiclaw 自身的会话历史，主 agent 继续通过 `session_search` 获取必要材料；当前内置角色的工具白名单没有它，不能让 explorer 猜路径绕过工作记忆入口。

默认保留现有 `bash`，因为 Git 信息、统计和压缩日志查询确实可能需要它；同时不将这个配置宣传为强只读沙箱。只有实测纯 `read/grep` 足以覆盖高频请求时，再考虑进一步缩工具，而不是让角色失去完成任务所需的能力。

### 6.4 reviewer：保留严格发现门槛，补需求与建议的边界

现有 reviewer 是 11 份里职责较清晰的一份，不需要推倒重写。优先改三点：

```text
按本轮完整需求和适用约束审查，不只依据实现者总结建立预期。
发现应包含：触发条件、实际错误或违约、影响、位置及可核查证据。
主张“缺少某段处理”时，要检查它是否已由调用方、下游或既有机制承担。

检查需求完成度，也检查本轮明确约定的维护成本：多出的依赖、状态或流程
是否服务于目标。只报有具体约束或后果支持的问题，不用个人风格制造返工。
发现验收标准自身存在缺口时，单列“契约待裁决”，不擅自扩大实现范围。

普通评审报告缺陷和覆盖范围，“未发现达到门槛的问题”是有效结论。
purpose=verify 时额外遵守 runtime 的完整验收协议；
只读能力拿不到的必需证据标阻塞，不把静态未发现问题写成运行通过。
```

将“可接受 / 有条件接受 / 不可接受”弱化为“发现及覆盖范围”也值得尝试。前者容易被主 agent 当作总闸门，后者更接近 reviewer 真正提供的信息。正式验收仍保留明确协议，不用模糊措辞替代 PASS/FAIL。

## 7. 其他角色值得保留的专门方法

### 7.1 planner：输出决策所需信息，不默认输出七节方案

当前正文虽允许省略小节，最终模板仍列了七大项，并要求粒度达到接收方无需重复基础调查。这可能把 planner 推向过细设计，让 builder 再复核一遍所有文件。

建议默认产出四件事：推荐选择、影响选择的证据、真正存在的备选取舍、下一项可以改变结论的检查。只有任务明确需要规划产物时，再给编号验收与拆解。

加入一句关键约束：

```text
把用户已定要求、源码观察和你的建议分开；方案不能自行成为新的用户要求。
实现位置给足入口，不代替执行者规定所有函数和编辑步骤。
可逆细节采用现有约定；重大未决项交回主 agent，不直接进入面向用户的问答循环。
```

保留“不需要改动也是合法结论”。删掉为了表现全面而固定枚举多种方案的倾向：只有确实影响决策的替代方案才值得写。

### 7.2 builder-hard：用证据变化作为继续条件

现有“先复现”“每处改动对应证据”“解释不了根因就不说修复”非常有价值。需要避免两个过度约束：

- “先能稳定复现，再改代码”对间歇并发问题可能不可满足。应允许确定性调度、针对性的契约测试或区分性实验，但必须说明证据局限，不能把一次未复现当修复证明。
- “同一个失败连续两三次”只适合作为提醒。三次失败若分别排除了三条假设仍然可能在进步；同一命令无变化重复一次就可能已经无价值。

建议增加短的失败交接，而非要求输出完整思考过程：

```text
当前最小失败现象：……
尝试 A / B 及可观察结果：……
因此已排除：……；仍无法区分：……
下一实验改变哪个条件、哪种结果会支持哪条方向：……
```

升级角色不会自动继承原 CLI 会话。主 agent 必须带上失败实验及当前改动，尤其不能丢掉已经有效的修复。hard 的工作是接续证据，不是从空白重新猜一遍。

### 7.3 worker 与 documenter：按独立产物划分

worker 建议有明确的有限范围：数据分析、批处理、独立报告和文档。不要扩大成拥有所有权限、承担一切未分类工作的兜底角色。

文档方法从 documenter 迁入相关任务的工作单，保留这些要求：核对路径、命令、字段和默认值；区分实测与示意；按读者任务组织；检查链接与例子；不编造版本、性能和验证状态。

但 documenter 现有的“当前实现 → 运行证据 → 已批准需求”的统一事实优先级需要改。它适合描述当前用法，却不能用于需求、设计和迁移目标：

| 文档声称什么 | 应依据什么 |
|---|---|
| 当前产品实际怎样工作 | 当前实现、配置与可核查运行证据 |
| 产品应满足什么、这次要改成什么 | 已批准需求与决策；实现不符时记录差异 |
| 性能、效果、验证是否成功 | 对应环境和样本的实际证据 |
| 示例如何操作 | 当前可执行命令，或明确标记的占位、示意内容 |

否则一个实现 bug 可能被自动改写进需求文档，形成“文档与代码一致”的假完成。

如果实际有大量独立手册任务，且 documenter 的配置持续比 worker 便宜或质量更好，可以继续把它作为个人专用角色。这应来自任务分布和对照结果，而不是“开发团队应该有一个文档岗位”。

### 7.4 git-committer：补暂存区语义，继续保持窄职责

这个角色不应仅为了减角色数量并入 builder。提交是明确的状态操作，混有用户已有改动时，单独的短上下文与精确交接有实际价值。

需要补进正文的规则是：

```text
精确 git add 只限制本轮新增暂存，不限制普通 git commit 会提交的既有暂存。
提交前确认整个 staged diff 都属于本次授权；若存在范围外 staged 内容，
默认报告具体冲突，保留暂存状态，不执行普通 commit，也不自行 reset 清空。

文件同时含本轮和任务外改动时，文件路径不足以定义授权边界，必须核对 hunk。
不能可靠隔离时返回冲突位置和所需范围说明，不以整文件暂存代替判断。
```

这不是新增每次都问用户的审批。已有授权完整、暂存区范围清楚就直接提交。混合暂存需要更高级的隔离方式时，由任务给出经过验证的方案；不让基础模板临时发明一套 index 操作。

原有 hook 失败不绕过、push 独立授权、保护历史等要求继续保留。另外把“trailer 按仓库惯例”和后面的绝对禁止 `Co-Authored-By` 统一成明确规则，避免同一份 prompt 自相矛盾。

## 8. frontmatter：把模型、方法和时间分开调

### 8.1 第一轮先不同时换模型

角色合并、正文改写、模型切换、推理档位变化若同时发生，效果变好也不知道哪一项起作用。建议第一轮维持保留角色现有模型配置，先验证工作边界与交接改善。

模型配置有两个容易误解的事实：

- explorer、log-sifter、git-committer 未写 `model`。内置解析先取角色配置，再取 `settings.subagentModel`，最后回退主 agent 当前模型。`runtime: internal` 和 low thinking 不保证低模型费用。
- 外部角色的 `model` 是原样传给 CLI 的标识，Pipiclaw 不验证它的可用性。本文记录现有名称，不据此对当前可用型号或能力作额外承诺。

若要成本可比，实验必须记录最终解析到的内置模型、外部 CLI 实际使用的模型、CLI 版本和有效 argv。不能把“这次主模型变便宜了”计为角色合并收益。

### 8.2 我最优先想验证的是 verifier 的配置

当前配置是 `gpt-5.6-luna + xhigh`，reviewer 是 `gpt-5.6-sol + high`。这并不证明前者验收不足，也不证明后者一定更好；我们没有这批任务上的测量。

但风险分配值得重新看：能运行测试不代表能判断测试是否足以验收，漏验收可能让一个错误产物直接进入交付。相比继续增加 builder 的推理预算，我会先在带隐藏缺陷的固定产物上比较这两个验收配置，分别统计漏报、误报、无法判定、费用与时间。

还应单独比较同一模型的 high 与 xhigh。测试进程耗时长，并不是必须提高推理档位的理由；执行检查、解释证据和设计检查是不同工作。遇到连续误验收时先检查工作单、契约可读性和检查质量，不能把所有失败都归因于模型大小。

这两组比较是候选实验，不是本次对模型性能的结论。正式迁移要求当前账号支持相应配置，并以实际运行数据为准。

### 8.3 不用任意缩小时限制造“便宜”

现有 builder / builder-hard 的墙钟上限均为 5,400 秒；外部角色不受内置 `maxTurns` / `maxToolCalls` 限制。降低时限可能减少一次 run 的消费，也可能在检查完成前杀掉有价值工作，迫使下个 run 重建上下文。

先补“没有新证据就停止重复方案”的工作纪律，保留现有时限作为基线。再从真实分布判断：时间花在调查、有效编辑、测试执行，还是停滞；成功任务需要多长时间；超时前是否有可接续产物。时限是故障上限，不是鼓励 agent 用满的时间配额。

`workload` 在当前实现中用于目录分组，不会改变模型、预算或 sync/async 执行路径。若继续保留 scout，就应该解释一个单点查询为何标 heavy；简单改成 light 也不会消除外部进程和异步交接。

### 8.4 上下文继续采用精简默认

保留隔离上下文和 `memory: none` 的默认策略。外部模板可显式写 `contextMode: isolated`、`memory: none`，让配置意图更清楚，但这不会自动改善记忆应用：当前有效要求仍由主 agent 放进 task。

不建议为了“让每个角色更懂用户”全部开启 index，更不应把频道索引当本轮验收标准。主 agent 选择的同一条适用要求要进入 builder 和验收者，才能验证它真的被执行。

## 9. 工作流应由任务触发，而不是由角色目录触发

| 工作 | 推荐形状 | 增加委派的条件 |
|---|---|---|
| 一个路径、默认值或状态问题 | 主 agent 直接查询 | 多次检索会挤占主会话时用 explorer |
| 明确的小改动 | 主 agent 完成并检查，或一个 builder | 契约和风险需要额外独立证据时追加验收 |
| 普通非平凡功能或修复 | builder 完成代码、测试、相关文档，再做有效独立验收 | 有需要专门审查的设计、并发、迁移等风险时加 reviewer |
| 高代价设计取舍 | 一项有问题边界的 planner 调查，再实施与验收 | 调查必须会改变后续选择，不为“有计划阶段”而调用 |
| 根因不明的回归 | 给适合的实现者失败证据，必要时用 builder-hard | 若只缺少可查询的事实，先做窄调查，不自动升级模型 |
| 整本手册或数据报告 | worker 完成独立产物并自查 | 需要独立事实核验或完整 task 验收时加合适检查者 |
| 用户要求提交已有改动 | git-committer 按准确范围提交 | 混合暂存、混合 hunk、hook 失败时返回具体阻塞 |

“额外一次 reviewer”应该能回答它要消除哪种不确定性。同样，“省掉 reviewer”也要说明剩余验收如何覆盖所需风险。不要用调用次数本身作为质量或效率的代理指标。

正式验收的独立性应体现在新的判断上下文与对真实产物的检查，不是角色名换了一下。不能把 builder 的原会话续接为自我验收；同一 builder 的局部返工则适合 follow-up，前提是旧假设仍然有效。

Anthropic 对工作流与 agent 的讨论将固定链条、动态编排、验收迭代列为不同模式，并要求根据问题和可测收益选择组合。本文据此支持按条件使用现有角色；该文章较早发布，不作为当前 CLI 参数或模型能力的依据。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## 10. 如何判断这些建议真的值得实施

### 10.1 先修一致性，再做有区分力的对照

建议分三个阶段，分别留配置快照：

1. **纠偏**：仍保留现有角色，修 required checks、完整验收、临时脚本位置、验收后文档和调用参数说明。它们应与现有机制一致，不必等成本实验来决定要不要改。
2. **方法**：固定角色和模型，比较旧正文与新正文，检查完整交付、反馈质量和无证据重复是否改善。
3. **精简**：固定有效模型与工作方法，比较完整目录与建议的常用目录；承接角色先获得被合并的方法，观察误路由和交接成本。之后再单独调模型、推理与预算。

角色精简本身包含职责迁移，不能声称是纯粹的“删三个名字”实验。应明确记录职责变化，不把多变量实验包装成因果证明。

### 10.2 首批代表任务

| 用例 | 要看什么 |
|---|---|
| 仓库中的单点事实，有容易混淆的旧实现 | 能否用最少必要工作找到当前证据，避免不必要的外部链条；不强制必须用某一个角色名 |
| 同一缺陷涉及日志时间线和代码路径 | explorer 合并后是否仍说明时间窗、保留反证，是否减少日志 → 源码的重复交接 |
| 明确接口改动，仓库要求全量 unit 和 e2e | builder 是否连同相关文档一起交付，必跑检查是否真实执行 |
| 测试全绿，但漏掉一条未涉及 diff 的 DoD | verifier 是否发现缺项，防止“定向验证 + 不适用”误放行 |
| 验收需要临时脚本，工作区已有 untracked 产品文件 | 取证能完成，原文件不变，attestation 不因新增正式测试文件失效 |
| 无实际缺陷，仅有一个可选重构建议 | reviewer 能否不给必修发现，主 agent 能否达标交付 |
| 两次失败分别提供新证据，另一个任务只是在原地重复 | builder / hard 是否区别有效调查与停滞，而非机械数次数 |
| 授权文件和任务外 staged 内容并存 | git-committer 是否保护提交范围及原暂存状态 |

确定性机制仍进入 unit/e2e；角色是否选择正确、报告是否有用属于 evals。新增 deterministic e2e 遵守现有 mutation check 要求，不断言模型措辞。

路由评估和执行质量评估分开。可以用受控执行结果观察主 agent 的路由，但那不能证明真实外部模型能做好工作；也可以直接给真实 verifier 同一个固定缺陷产物，比较它的检查能力，而不让 builder 的随机变化污染比较。最后再用少量完整任务核对端到端结果。

每组任务先做少量重复用于发现明显退化，不声称具有统计显著性。保留没有参与调 prompt 的任务，防止模板只适应已见例子。调用真实 CLI 的成本和环境前置要单独记录，不混进离线 deterministic 层。

### 10.3 衡量整个交付，不只看单次 run

沿用 004 的有效交付、人工介入、总成本和交付时间。针对这次改动，再抽样记录：

- 为澄清角色边界发生的重派、无必要 planner、重复源码调查和文档返工。
- 验收漏报与误报，区分产品缺陷、环境阻塞、证据缺失、任务外建议。
- 在相同文件状态上重复执行了什么昂贵检查，它是否取得了新的独立证据。
- 最终产物是否完整，是否因为最后补文档或 hook 改内容而需要重验。

现有 run 记录不一定直接标记这些原因，先人工抽样读 `prompt.txt`、`system-prompt.txt`、`output.md` 和真实 diff 即可，不要预先增加一套遥测分类服务。外部费用未知时不能按零计入，实报与估算分开。

## 11. 建议的落地范围

第一步直接改当前 README 与有关 prompt 的确定性冲突，并把固定流水线换成条件化用法。这个阶段保持角色名、模型与权限配置稳定。

第二步按第 6、7 节改角色责任及交付方式，优先 builder 和 verifier。将角色缩减作为随后可比较的配置试验：常用 5 个、按需 3 个，逐步退出 scout、log-sifter、documenter 的推荐独立模板。

迁移时同时检查文档、示例复制命令、eval fixtures 及角色正文之间的名称引用。实际工作区是用户已复制的独立配置，修改 examples 不会自动升级它。旧角色仍有在途或待续接的 run 时，先完成相关工作再移除；不要以新增别名或兼容解析器替代一次明确迁移。

不建议本轮增加角色继承 DSL、动态模型路由器、自动规划 agent、全角色流水线或新的报告协议。当前工作单、角色文件、runtime 验收协议和结果 artifacts 已足够验证这批建议。

最终希望改变的行为是：用户提出一个清楚的目标后，系统用尽量少的交接形成完整产物，再用足够强的独立证据决定是否交付。角色存在的理由，应当是它减少了遗漏、误判或返工，而不是它让流程看起来更像一支完整团队。
