# 从扳手到车床：让 Pipiclaw 持续产出，而不是等你动一下

> **读者**：已经会用事件、任务和委派，希望减少重复交办与人工追赶的人。
> **前置**：[事件与任务](../events-and-tasks.md)、[智能体委派](../sub-agents.md)、[记忆](../memory.md)。

如果每次工作都要你提醒开始、重述背景、追问进度，再逐项核对结果，助手更像一把顺手的扳手。要让它稳定承担一类工作，需要把触发条件、背景和验收方法也交代清楚。

| 你反复在做什么 | 可以沉淀在哪里 |
|---|---|
| 判断什么时候该开始 | 事件的时间安排或 `preAction` 条件检查 |
| 解释项目背景和上次进展 | 工位记忆、任务说明与任务记录 |
| 核对是否完成 | DoD 验收清单、检查脚本与独立复核 |

下面四种做法，适合从一项已经熟悉、风险可控的重复工作开始尝试。

## 1. 能确定性检查的条件，先交给传感器

“每十分钟看一下 CI”会让模型反复判断有没有事。若条件可由命令直接判断，就用 `preAction`：退出 0 才唤醒助手，非 0 静默跳过，不产生模型调用。

适合的条件包括：告警超过约定时间仍未认领、CI 连续两次失败、数据分区尚未产出。传感器只检查条件，分析与后续处理交给助手。

下面是手写事件文件的示意。替换 `channelId`，并先编写、验证实际的检测脚本；这个脚本不由 Pipiclaw 提供。

```json
{
  "type": "periodic",
  "channelId": "dingtalk:dm:your-staff-id",
  "text": "检测到 master CI 连续两次失败。请读取失败日志，定位相关变更，给出初判与处理建议；不修改代码。",
  "schedule": "*/10 * * * *",
  "preAction": {
    "type": "bash",
    "command": "~/.pipiclaw/workspace/skills/sensors/ci-red-twice.sh"
  }
}
```

传感器也需要维护：明确采样频率、重复告警的抑制条件，以及什么时候删除事件。带 `preAction` 的周期事件最密每 5 分钟一次，规则见[事件动作门控](../events-and-tasks.md#事件动作门控action-gate)。

## 2. 先写出怎样验收，再交给它持续推进

准备把一项工作交给后台任务前，问一句：**什么证据能说明它完成了？**

| 工作 | 可复核的验收依据 |
|---|---|
| 周报 | 每个关键数字有可复现的查询，结论附原始来源 |
| 故障复盘 | 时间线节点有日志或监控证据，改进项有明确落点 |
| 数据修复 | 修复前后的一致性查询、影响范围与剩余差异 |
| 依赖升级 | 必要测试、关键接口对比，以及未验证范围 |

把这些依据写进任务的 DoD。能用命令检查的交给脚本；需要判断的写清评价标准，按风险安排独立检查。检查者的 `VERDICT` 是负责人的判断材料，不能替代真实产物，也不会自动关闭任务。

没有可靠验收方法时，可以先让助手调查或提出方案，保留人工确认。不要因为工作能定时触发，就直接授予它执行所有后续动作的权限。外部修改的范围、验证方法和停止条件应写入目标；CLI 权限与运行账号决定实际执行边界。

## 3. 把重复介入变成下一次的明确要求

周期工作使用**事件模板，每次生成独立任务实例**。模板保存共同目标与验收要求；下一实例的首步可参考上一实例的收尾记录和最后汇报。

例如，周报每次都要你纠正同一个统计口径：本次先确认正确结果，再让助手把口径整理成模板要求或检查脚本。任务可在汇报中提出改进，你确认后由聊天中的助手更新模板；修改不自动作用于已有实例。

每月可以交办一次回顾：

```text
检查本月周报任务的记录，找出反复需要我纠正或补背景的地方。
区分业务上的新决定与重复问题，提出模板或检查脚本的改进，先给我确认。
```

观察介入次数，也观察介入的原因。减少重复解释和纠错是收益；需要你作出的新业务决定不应被隐藏。新工作先只读、只提议，稳定后再逐步扩大执行范围。

## 4. 用工位组织长期责任，用频道接收要求

几个群都绑定默认工位 `default` 时，对话各自独立，记忆、任务和工作文件却是共享的。多建群不会自动分开背景。

当两个项目需要独立的术语、约束和任务清单时，可为其中一个创建工位，再把相关入口绑定过去：

```text
/desk new service-a
/desk bind service-a
```

先用 `/desk` 核对绑定。切换不会搬移旧记忆和文件，任务报告仍送到它指定的频道。同工位的私聊、群和终端都能管理任务；所有工位都适用的共同背景由管理员维护在 workspace 的 `MEMORY.md` / `ENVIRONMENT.md`。

零散请求不必各建工位。工位也不提供文件权限隔离；多个入口要同时修改同一仓库时，仍需约定写入范围或使用独立 worktree。具体边界见[并发与容量](../scaling-and-concurrency.md)。

## 从一项工作开始

选一项你能说清输入、产出和失败代价的工作，先完成一次，再把稳定部分写入任务或事件模板。让助手通过报告交付结果，通过具体问题请求决定；你用 `/tasks show <id>` 查看状态，用 `/tasks msg <id> <内容>` 纠偏，需要停止时暂停或取消。

运行几次后，对照记录看：哪些背景仍在重述，哪些检查总要补做，哪些外部动作还缺少可核实的结果。优先修正这些环节，比增加更多角色或更密的定时唤醒更有用。
