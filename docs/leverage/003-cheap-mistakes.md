# 放手的判据：让错误更便宜，而不是让它更少犯错

> **一句话**：[001](./001-from-wrench-to-lathe.md) 讲**出口**（可机检），[002](./002-context-ownership.md) 讲**入口**（可写清）。这篇讲最后一步——两样都齐了，你为什么还是不敢撒手，以及该往哪投钱把手撒开。
>
> **读者**：已经能把活交待清楚、也能验收，但仍然每次都想盯一眼的人。
> **前置**：[安全指南](../security.md)、[智能体委派](../sub-agents.md)、[设计哲学](../design-philosophy.md)。

## 不敢放手是对的，但归因通常是错的

你心里在算的其实是一个乘积：

```text
风险 = P(它做错) × 单次错误的代价
```

大多数人下意识去优化第一项——换更强的模型、把提示词写得更细、多加几句"务必小心"。但第一项有三个致命性质：**它有天花板、它不受你控制、而且你事前无法验证**。你只能事后统计，而"事后"意味着代价已经付过了。

第二项完全相反：**它是你的系统的属性，由工程决定，改一次永久生效，而且改完当天就能验证。**

> 一个能承受错误的系统，敢把正确率 90% 的事交出去；
> 一个承受不了的系统，98% 也不敢。
>
> **决定你自治边界的从来不是它有多准，而是它错了你有多疼。**

这个重心一移，该做的事情立刻变得具体：不再是调提示词，而是可靠性工程——运维和数据工程师的本行，只是这次的对象换成了 agent。

## 错误成本 = 可发现 × 可回滚 × 爆炸半径

三个乘数，任何一项接近零，整体代价就接近零；任何一项失控，另外两项做得再好也没用。

### 可发现：最贵的错误是没人发现的错误

一个当场炸掉的错误很便宜——你马上知道，马上改。真正贵的是那种**悄悄干成了、三周后才被发现**的：期间所有基于它的判断全部作废。

所以自治动作的第一要求不是"正确"，是**留痕**。项目里已经有三层痕迹可用：外部委派每次派发前写的审计事件（`runId`、角色、harness、完整 argv、工作目录、`mutates`、model）、`state/subagent-runs/` 的 run 记录、task 文件的 `History` 段。

值得注意的是审计的**顺序**：先写审计、写失败就不 spawn（见 [外部智能体的授权边界](../security.md#外部智能体的授权边界)）。这个"先记账、再动手"的顺序，也应该是你自己写任何自动化动作时的默认姿势——记账失败比动作失败更值得中止，因为它让后面所有错误都变成不可发现的。

### 可回滚：优先把自治投在能撤销的动作上

动作天然分两类，差别巨大：

| 可回滚 | 不可回滚 |
|---|---|
| 改代码、开 PR、改配置文件、建分支 | 发消息给别人、调用外部 API、删数据、发布 |
| 错了 `git revert` 一下 | 错了只能道歉或补偿 |

**把自治优先投在左列。** 这解释了为什么"让它自己改代码提 PR"是所有场景里最容易做成无人值守的一个——不是因为写代码简单，而是因为 git 让错误几乎免费。

右列的动作也不是不能自动，而是要**拆成两步**：让它一路做到"待发"——草稿写好、参数备齐、目标确认——然后停在那里等你按一下。你付出的是一次点击，换回的是全部不可逆风险。

### 爆炸半径：边界建在宿主层，不在提示词里

关于这一点，[security.md](../security.md) 已经写得很坦白，这里只提炼成一句你在放手前必须内化的判断：

- `mutates` 只用于审计、验收准入和写锁，**不是权限控制**；
- `workingDirectory` 只决定启动目录，**不是文件系统边界**；
- 外部进程**继承 daemon 的环境**，用的是它自己的认证；
- 工具白名单不等于只读——含 `bash` 的角色照样能写。

所以"我在系统提示里写了不许改线上"不是边界，那是行为约束。真边界只有四样：**独立的运行账号、容器、最小化的环境变量、目标 CLI 自己的 sandbox 参数**（例如 `codex exec --sandbox read-only`）。

放手前的检查很简单：**假设它今天完全失控，它的账号能碰到什么？** 那个答案就是你的爆炸半径，跟你写了什么提示词无关。

## 幂等不是可选项，因为恢复语义是 at-least-once

这条单独拎出来，因为它是自治系统和人工操作最本质的差别。

事件和任务的投递语义是 **at-least-once**：进程在动作执行中退出，重启后 runtime 会重新投递租约过期的记录；错过的 one-shot 会补执行。这是刻意选的——真实的 exactly-once 是虚构的（见 [设计哲学第 3 条](../design-philosophy.md)）。

代价是：

> **不幂等的动作 + 自动重放 = 你睡觉的时候它把同一件事做了三遍。**

人不会重放，系统会。所以凡是有外部副作用的自治动作，三件事至少做一件：

1. **稳定的操作标识**——用一个由内容或周期推导出的确定 ID，重复提交被对方去重；
2. **先查真实状态再动作**——不要依赖"我上次做过了"这种记忆，去问真实系统"这件事做了没";
3. **把"做"和"记"合成一次**——同一个事务里完成，避免做完没记上、重启后重做。

第 2 条最通用，也最符合"[记指针不记快照](./002-context-ownership.md#记指针不记快照)"：**别让它相信自己的记忆，让它去查。**

## 你以为的刹车，可能不是刹车

一个具体且容易踩的坑：**`/stop` 只停当前主回合，不会杀掉已经派发、正在独立运行的委派 run。**

停一个在跑的委派必须显式 `/subagents cancel <runId>`（这条命令不经过模型，模型卡死或不可用时依然能用）。这是有意的设计——detached 的外部进程本来就不该被一个聊天回合的中断连带杀掉——但如果你以为 `/stop` 是总开关，你在最需要它的那一刻会发现它不是。

由此得到一条大家肯定不会主动做、但极其值钱的建议：

> **在放手之前，先真的按一次刹车。**

像消防演练一样跑一遍：派一个无害的长任务出去，然后试着停它。确认三件事——**用哪条命令能停、停下来之后状态是什么、有没有留下需要收拾的半成品**。没演练过的刹车等于没有刹车，而你不会想在真出事的时候第一次读文档。

## 顺带纠正一个优化目标：稀缺的是注意力，不是 token

人会本能地省 token：少派委派、不让它多探索、能一轮说清就不要两轮。这个本能在这里是**错的优化目标**。

算一下数量级就清楚了：你的一小时 vs 一次外部 run 的花费，通常差两个数量级。**真正稀缺、且不可再生的是你的注意力。**

于是判断标准应该改成"这样做会不会少打扰我一次"：

- 宁可让它多跑一次自查，也不要让它把一个不确定的结果丢给你判断；
- 宁可花钱请一次独立验收，也不要自己重读一遍产出——**独立验收是花钱把你的注意力买回来**；
- 宁可让它多探索十分钟，也不要为了省事自己去查那个它能查的东西。

成本可见性在 `/usage`（按 `taskId` 聚合）。看它是为了发现**失控的循环**，不是为了省钱。

## 放权按错误成本分级，不按信任感分级

最后把上面合成一张可以直接照做的表。注意分级依据是**动作的性质**，不是"我觉得它靠不靠谱"——后者是情绪，会随最近一次成功或失败漂移。

| 动作类型 | 例子 | 放权姿势 |
|---|---|---|
| 只读 / 只提议 | 巡检、分析、给方案、找根因 | **立刻放手**，不需要任何铺垫 |
| 可回滚 + 有痕迹 | 改代码、开 PR、改配置文件 | 配 DoD + 独立验收后放手 |
| 不可回滚但影响只在你自己身上 | 发到你自己的频道、写你自己的文件 | 放手，控制频率即可 |
| 不可回滚且外部可见 | 发到团队群、调外部 API、改线上、发布 | **永远留人工闸门**，让它做到"待发"为止 |

其中最重要的一条判断是关于闸门的位置：

> **闸门要设在最后一步，不是每一步。**

很多人的做法是"每一步都来问我"——结果它什么也推不动，你还得全程在场，形状又变回了 001 说的那把扳手。正确的做法是让它一路跑到**不可逆动作之前**，把一个完整的、你看一眼就能判断、按一下就能执行的东西摆在你面前。

**审批点的位置，比审批的次数更能决定产出。**

## 反模式速查

| 反模式 | 为什么伤产出 | 换成 |
|---|---|---|
| 靠调提示词来"让它别出错" | 优化的是有天花板、你还验证不了的那一项 | 投资降低错误成本，改一次永久生效 |
| 在提示词里写"不许动线上" | 那是行为约束，不是边界 | 独立账号 / 容器 / 最小环境 / CLI sandbox |
| 有外部副作用却不幂等 | at-least-once 重放会把同一件事做多遍 | 稳定操作 ID，或先查真实状态再动作 |
| 以为 `/stop` 是总开关 | 最需要它的那刻才发现它不是 | 放手前先演练一次 `/subagents cancel` |
| 为省 token 而少委派、少验收 | 优化错了目标，稀缺的是注意力 | 用"会不会少打扰我一次"来判断 |
| 每一步都要你点头 | 它推不动任何事，你全程在场 | 闸门设在最后一步，前面全部放开 |
| 按"我觉得它靠谱了"来放权 | 情绪会随最近一次成败漂移 | 按动作是否可回滚、可发现来分级 |
