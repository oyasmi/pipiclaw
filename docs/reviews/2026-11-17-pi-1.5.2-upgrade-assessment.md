## 意见

**建议升级，作为低风险的维护升级安排进下一次发布；没有发现必须修改生产源码、测试或迁移数据的阻断点。** 收益主要是工具参数校验、供应商兼容、会话边界和终端输入修复。它不是一次能直接带来明显端到端提速或降低 token 账单的升级。

先行评估在隔离副本把四个直接 pi 依赖一起精确升级到官方 npm `1.5.2`，原样通过类型检查、架构检查、1,035 个 unit 和 72 个确定性 e2e。该阶段主工作区只新增本文。用户随后授权正式升级，实施记录见文末；源码和测试均未改动，用例数量净增 0。

“低风险”限定于已检查的代码和离线机制。真实供应商、OAuth 服务、实体终端以及某个部署的自定义网关配置仍需发布前定向验证。

## 上游新增了什么，本项目能获得什么

主要更新在 2026-11-09 发布的 1.5.1；2026-11-10 的 1.5.2 主要补 Anthropic OAuth 客户端版本标识，以及 pi 交互模式下原 cwd 消失时的继续/分叉和失败导入清理。

| 变化 | 对 Pipiclaw 的实际作用 | 价值 |
| --- | --- | --- |
| pi-schema 拒绝非有限数字，修复相对根 `$id` 与本地 `$ref`，补 TypeBox BigInt/Undefined/复杂类型推导 | 关闭上次升级评估已确认的校验缺口；普通 TypeBox 工具定义可继续使用 | 直接可靠性收益，最明确 |
| OpenAI-compatible 的空工具列表改为默认省略；增加非 null assistant content、prompt cache key 等兼容选项 | vLLM 0.20+ 等网关更兼容；旧代理有配置回退方式 | 相关部署受益，也有兼容注意点 |
| Anthropic/OpenCode thinking 签名、Sonnet 5 temperature、根部 schema 定义保留、掉流重试分类等修复 | 减少指定供应商的 400 和内部代理不必要失败；主会话及内部代理使用同一 pi-ai 路径 | 直接但取决于供应商 |
| 输出上限增加输入计数误差余量，Azure 上下文和长上下文价格元数据修正 | 减少过早误判 overflow 和无谓压缩，预算/费用估算更准确；极长单次输出上限可能更低 | 收益与行为变化并存 |
| AgentSession 修复输入预处理与树导航竞态、运行/压缩中的 reload 拒绝、分支 thinking 记录、队列图片处理 | 本项目使用真实 AgentSession，可获得底层保护；自身资源锁和上下文故障隔离仍需保留 | 直接可靠性收益 |
| pi-tui 修复短粘贴标记退格后的编号、光标标记泄露、HTML 注释显示、Alacritty 链接识别 | 本项目直接使用 Editor、Markdown、TuiMainScreen，输入和显示可直接受益 | 小到中等 |
| 新模型和 provider，如 Claude Fable 5.2、Qwen Token Plan Individual 中国端点 | SDK 模型选择范围扩大；不会自动更换 Pipiclaw 默认模型，也不改变外部 coding CLI 的模型能力 | 可选收益 |
| Anthropic OAuth 使用更新的 Claude Code 版本标识 | 使用 Anthropic OAuth 的部署获得上游兼容修正 | 1.5.2 特有的小修复 |

以下不能计为“只升依赖就得到”的收益：

- **Anthropic message threads。** SDK 仅在具备 `sessionId`、缓存未禁用、端点支持时启用；默认只对 Anthropic 官方端点开启。Pipiclaw 的主会话、内部代理和记忆 sidecar 自建 Agent，当前未给 Agent 传 `sessionId`；AgentSession 构造也不替宿主补它。离线请求探针证实：1.5.2 不传 id 时不发送 `thread`，显式传 id 才发送 `thread: { type: "create" }`。当前升级不会自动从全量上下文请求切换为线程续传。即使以后接入，主要减少请求上传量，token 计数与缓存规则没有因此消失。
- **空闲缓存保温。** pi 默认由 `streaming` 改为 `idle`，但 Pipiclaw 不走 `createAgentSession()` 的 CacheWarmer 装配，也未向 AgentSession 注入 `cacheWarmer`。升级不会自动启动后台保温请求或产生这部分费用。
- **跨请求记住 strict 工具超限。** 新机制依赖请求的 `sessionId`；当前主 Agent 路径没有该 id，不能把“后续每轮省一次 strict 拒绝”计为现有接入的收益。请求内原有降级不等于跨请求记忆。
- **退出前等待 OAuth 新令牌落盘。** 上游新增 `ModelRuntime.settleCredentialWrites()`，并接入 `AgentSessionRuntime.dispose()`；Pipiclaw 的 SessionHost 仍直接调用同步 `session.dispose()`，没有走新增的等待路径。认证文件真实路径锁修复可受益，但不能声称此次升级已完整解决 Pipiclaw 的退出时令牌丢失问题。
- **pi 自带 read/grep/edit/bash 的大文件和平台修复。** Pipiclaw 使用自己基于 Executor/FileStore 的实现；不能把这些上游工具的内存改进算成本项目文件工具的提速。`GrepOperations.readFile` 不再用于上下文行这一 breaking change 因而也不影响当前接入。
- pi auth、Mermaid 交互呈现、缺失 cwd 分叉选择器、扩展更新报告和 p2 功能主要属于 pi CLI/应用，本项目有自己的命令和传输。

## 兼容性与剩余风险

### 1. 修复了此前的校验缺陷，不需要重写 schema

对实际发布包走 `parseToolCallArguments()` → `validateToolArguments()`：

| 输入 | 1.5.0 | 1.5.2 |
| --- | --- | --- |
| 无界 number 的合法 JSON `{"amount":1e999}` | 接受，得到 Infinity | 拒绝，指出 `expected number, got Infinity` |
| `{"amount":42}` | 接受 | 接受 |
| `{"amount":"42"}` | 转为数字 42 | 转为数字 42 |
| 根 `$id: "schemas/tool.json"`，属性引用 `#/$defs/Num` 的合法参数 | 拒绝 | 接受 |

虽然上游 changelog 将非有限数字描述为代码构造值的问题，`1e999` 也可以经 JSON 解析抵达该缺陷；这次实际发布包确已修复。Pipiclaw 已有的任务预算有限正数校验、网页长度归一化仍应保留，不能把领域边界交给 SDK 代替。

这组探针针对已知风险，不是全部 JSON Schema 语义的等价证明。当前所有项目测试原样通过，没有发现普通 TypeBox 工具必须迁移到 pi-schema builder 的理由。

### 2. 旧版 LiteLLM/自定义网关需要看配置

变化的触发条件是：OpenAI-completions 请求没有当前工具，但历史含工具调用/结果。1.5.0 发送 `tools: []`；1.5.2 默认省略该字段。离线截获请求证实，加 `compat.requiresToolsWithToolHistory: true` 可恢复旧行为。

这不是所有网关请求都会变化。正常主回合有工具时不触发；无工具的压缩或裁剪后的内部代理请求更值得关注。若部署依赖要求空数组的旧 LiteLLM，应在该模型的 `models.json` 配置兼容项后再升级。本次未检查用户实际部署配置，不据此假定其使用某种网关。

### 3. 输出预算更保守，作用范围不限 OpenRouter

修复动因是 OpenRouter 输入计数偏大，但代码落在共享 `buildBaseOptions()`/`clampMaxTokensToContext()`，Anthropic、Bedrock 也使用该夹限；不能解释成“只影响 OpenRouter”。

在 200,000 context、请求输出上限 128,000 的离线探针中，估计输入 80,000 时输出上限由 115,904 降到 108,000；输入 160,000 时由 35,904 降到 32,768。接近窗口耗尽时仍有固定余量分支，输入 180,000 时两版同为 15,904，并非统一硬性限制为 32K。

普通短回答通常不触及这些上限。极长代码生成、长 thinking + 输出可能更早触及上限，需用部署模型做定向验证。该机制不会直接让正常回答更便宜或让模型能力提高。

### 4. 发布包模型目录既有新增，也有删除和元数据改变

比较两版 npm 的内置聊天目录：**1,592 → 1,643，新增 70、移除 19、修改 104**。这只是打包时快照，运行时刷新或用户自定义目录可能不同。

移除示例：`openrouter/inception/mercury-2`、`openrouter/inception/mercury-2.5`、`openrouter/inception/mercury-3`、`openrouter/minimax/minimax-m1`、`openrouter/minimax/minimax-m2`、`openrouter/minimax/minimax-m2.1`、部分 Fireworks 模型。还有既有模型的 context、输出上限、价格和路由元数据变化；例如 Vercel Qwen3.8-27B context 从 1M 缩为 262,144。

项目硬编码默认 `anthropic/claude-sonnet-4-5` 仍存在且元数据未变。正式发布前应核对实际部署的默认、备用、内部代理和记忆模型引用；目录变动不能仅检查主模型。完整清单在隔离副本 `audit-evidence/probe.json`。

### 5. 没有发现会话/持久化格式迁移要求

区间没有改动上游 SessionManager 实现；当前 canonical context、context edit、部分写入隔离、备用模型、重启恢复、任务/记忆/委派和命令链均通过原 e2e。私有 `_baseToolsOverride` 仍存在，当前重载适配继续可用，但私有字段耦合仍不是稳定接口保证。

不要因为 SDK 增加 reload/导航保护就移除 Pipiclaw 自身的资源互斥和故障恢复保护。上游的局部保护不能取代宿主的跨模块一致性。

## 成本、收益与实施建议

**仅升级依赖的代码成本很低：预计只需改 package.json 和 package-lock.json，不需要 schema、会话、任务状态或磁盘布局迁移。** 本次隔离验证已经证明现有代码无需适配。若实际部署的模型引用仍在且无特殊网关，正式修改、复跑门禁、目标供应商冒烟和发布记录可按约 1–3 工时估算；这是工程预算，网关故障或认证问题会增加成本。

收益以减少特定失败和关闭校验缺陷为主，大小取决于部署：常用 Anthropic/OpenCode、OpenRouter/vLLM 或 TUI 的用户更容易获得价值；如果主要调用外部 Codex/Claude CLI，SDK 路径很少，紧迫性较低。不会因升版本本身增加固定订阅成本，也没有证据承诺某个百分比的延迟或 token 费用下降。

建议正式升级范围：

1. 四个直接依赖一起精确锁定 `1.5.2`，提交最小 lock diff；保留当前 TypeBox 和自有工具实现。
2. 核对部署的四类模型引用；旧 LiteLLM 确实需要空工具数组时才为相应模型加兼容项。
3. 保留现有测试并复跑项目门禁；对实际默认供应商验证一轮工具调用、后续回合、压缩和取消，使用 OAuth 时验证续用。长输出是常见需求时补相应冒烟。当前没有这些真实服务的验收 run id。
4. 按普通维护发布升级，不同时更换默认模型或网关。把 `sessionId`/消息线程、缓存保温、退出时 credential drain 作为独立接入工作；它们需要会话生命周期、压缩/备用请求隔离及关闭机制的专门设计与验证，不能为扩大此次收益顺手接入。

因此应升级，但优先级是正常维护，理由是已有兼容验证支撑的可靠性收益和低适配成本，而不是版本号更新或尚未接入的新功能。
