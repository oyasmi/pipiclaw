# 第二项推进建议：按需发现与 Codemode

日期：2026-11-17。状态：研究与讨论稿，尚未实施产品功能。对应 [Pi SDK 接入复盘的能力候选](./pi-sdk-integration.md#能力候选)；基线为完成认证接入的 `b66286f`。

## 建议

把第二项拆成可独立验收的两个试验：**先验证少量工具的按需发现，再给资料查询引入受限 Codemode；两项各自成立后才验证组合。** 保留现有直接调用、shell/skill 与委派路径，由同一个模型按任务选择；首轮仅在显式开启的试验配置中使用。不要为普通文件操作强制增加脚本，不预先承诺全局提速。

Codemode 负责把确定的查询、分页、过滤和汇总放进一次脚本执行，按需发现负责减少尚未使用的工具定义。二者解决不同问题，Codemode 本身还会增加常驻提示成本。当前外部 CLI 已覆盖的自动化流程与本地 shell 批处理应作为有效对照，不能把基线人为限制成逐个文件、逐页调用。

## 核对范围与离线证据

核对官方安装包 `@earendil-works/pi-coding-agent@1.5.2`、公开工厂和类型、对应发布标签，以及本项目工具工厂、SessionHost、事件观察、任务活动判定、Web 返回格式和评测工具。上游工作区 HEAD 已超出 v1.5.2，因此实现判断采用安装包及发布标签，没有混用未发布能力。

本轮在 `/tmp/pipiclaw-codemode-plan-20261117/` 创建了临时探针，使用真实 Pipiclaw 工具工厂、真实 SDK AgentSession 和 QuickJS；模型流由脚本生成，fetch 禁止真实网络，auth.json 只含临时合成 key。未读取部署凭据、未调用真实模型或业务服务。它验证机制和定义体积，不证明模型会正确选择工具或生成脚本。

为便于比较，按需发现仅延迟 `event_manage` 和 `subagent_inline` 两项；这些是 schema 较重的候选，尚未证明它们在实际部署中低频。Codemode 使用 `mode: on`、`models: false`、`inlineBudget: 0`，脚本仅可达已启用的 `read`、`grep`、`glob`、`web_search`、`web_fetch`。测量未包含拟新增的结构化输出 schema 和产品指导，因此不是最终发布体积。

默认 web 关闭、聊天工具带媒体能力的结果：

| 配置 | 首轮工具数 | 首轮字符 | 首轮提示单位 | 两个延迟工具都加载后 |
| --- | ---: | ---: | ---: | ---: |
| 当前直接声明 | 25 | 23,314 | 3,342 | 3,342 单位 |
| 仅按需发现 | 24 | 17,188 | 2,500 | 3,429 单位 |
| 仅受限 Codemode | 26 | 24,828 | 3,569 | 3,569 单位 |
| 两项组合 | 25 | 18,702 | 2,727 | 3,656 单位 |

提示单位是项目的确定性长度度量，不是供应商 token。按需发现首轮工具定义少约 25.2%；组合少约 18.4%；Codemode 单独增加约 6.8%。这都不是总请求 token 或账单变化。开启 web 后，对应首轮单位为 3,539 / 2,697 / 3,784 / 2,942，趋势相同。加载操作会积累；两个工具都使用过之后，发现工具自身仍有开销。稳定缓存下的费用收益还会进一步缩小。

其他实测：

- 一个脚本经真实工具读取三个合成 JSON 文件，在沙箱中筛出 id `[57,58,59]`。读取约 6 万字符的中间数据，最终只输出筛选结果及验证字段；本地 shell 同样可以完成此任务，所以这只是数据流验证。
- 同一脚本尝试读取临时 app home 的 auth.json，被现有真实路径守卫拒绝；试图调用 `write` 被沙箱工具白名单拒绝，没有产生目标文件。脚本看不到事件工具，`models` 未暴露。SDK 发出 4 组带 `parentToolCallId` 的子调用事件，父结果保留有界 `nestedCalls` 元数据。
- SDK 原生词法搜索对两条中文查询未命中英文工具描述；改用 `schedule recurring event` / `inline delegate agent` 即命中。它支持中文分词，但不自动跨语言翻译。真实模型可能主动用英文搜索，不能把这四条输入当作实际用户发现失败率。

探针脚本和 `evidence.json` 保留在上述临时目录。探索时的失败暴露了脚本接口细节：工具返回值需按真实声明处理，访问不存在的 `tools.x` 属性会报错，检测应使用 `"x" in tools`。这些都未通过修改 SDK 或放宽产品边界来规避。

## 使用方式与适用工作

用户仍用自然语言提出目标。模型保留直接工具入口：简单操作直接调用，确定的批量查询/分页可以发起 Codemode，低频管理能力通过工具发现加载。无需用户编写 JS 或输入新的斜杠命令。

| 工作 | 推荐执行方式 | 可能的收益 |
| --- | --- | --- |
| 查一个文件、改几行代码、跑测试 | 现有直接工具或 bash | 避免额外脚本与修复成本 |
| 对若干已知来源执行独立查询 | 直接并行或 Codemode 都可 | Codemode 的区别在结果过滤；不保证减少模型轮数 |
| 下一页依赖上一页游标、按明确字段筛选统计 | Codemode 候选 | 多页工作可在同一脚本完成，减少中间结果进入上下文和逐页模型决策 |
| 比较多份资料的语义、判断方案取舍 | 查询可脚本化，推理仍由模型完成 | 返回来源与相关片段，不能用粗糙关键词筛选冒充读懂全文 |
| 临时角色委派、事件管理 | 搜索加载后由模型直接调用 | 首轮省 schema；不把这些状态操作塞进脚本 |
| 已有稳定 skill/CLI 的业务流程 | 继续使用原路径并作为对照 | 避免为相同能力维护第二套实现 |

第一类真正值得试的 Codemode 场景是“多源资料查询与有确定规则的数据整理”，例如按用户给定的字段筛选版本记录、翻页获取明确条件的条目、批量读取后输出带来源的结果。当前尚无现成 MCP 工单接口，不能把它当成已经存在的产品场景或搭建 MCP 的前置任务。

## 试验 A：少量工具按需发现

从两个重 schema 候选开始，核心文件工具、普通委派入口、任务报告/提问/等待能力继续直接可见。正式候选需结合实际使用场景确认；如果主要问题是 inline 角色几乎不用，应先与现有 `subagentInline` 开关比较。

采用 SDK 的 `tool_search` 与 `deferred`，复用会话分支的工具加载记录。模型用自然语言/英文关键词或准确工具名查找，匹配项从下一次模型调用起有完整 schema，随后仍按原工具执行。不要每轮清空已加载工具来追求漂亮的冷启动数字，那会重复发现并扰动缓存。

需要补齐以下项目接线：

- 工具工厂仍是唯一实现来源。通过公开 ToolDefinition 注册元数据；`baseToolsOverride` 从 AgentTool 合成定义时不会保留 exposure，在对象上随手加字段不足以实施延迟发现。
- SessionHost 初始化、工具重建和 `/reload` 采用一致的活动集策略。现有 `initialActiveToolNames` 与 `setActiveToolsByName(全部工具)` 会把延迟工具重新声明，必须处理。恢复只允许当前 profile 实际具备的工具，不能让历史 loadout 绕过任务会话、一次性请求或配置关闭的限制。
- 已注册、模型已声明、脚本可调用是不同集合。playbook 仍应能说明可发现的能力；`/context` 和测量记录应报告实际发送的声明，不能继续用全部 currentTools 当成模型开销。
- 为发现入口提供短而明确的查询指导及少量双语关键词；先复用现有 playbook 目录提供机制入口，不新增另一份长工具手册或语义搜索服务。

预期收益限于未使用工具的会话、冷缓存和较紧的上下文。必须测到“发现后正常完成用户目标”；只看到 schema 变小不足以验收。

## 试验 B：只读业务操作的 Codemode

复用公开 `createCodemodeExtension()` 和官方沙箱，使用 `mode: on`，保留模型直接调用能力。关闭 models 接口；首轮不接分类器、生图、内部 worker 或外部 CLI。先接主聊天会话，再用任务会话做一次边界验收；内部 Agent 当前是裸 Agent，单独接入成本与必要性需后评。

沙箱只允许实际启用的五个查询/读取工具。`bash`、`write`、`edit`、记忆写入、任务控制、事件、委派、媒体发送和作业管理都留在模型直接调用路径。这里的只读指业务效果；网页缓存、SDK store 和输出溢出文件仍属于 runtime 的正常持久化，不宣称进程文件系统零写入。

两项组合时有一个必须显式处理的边界：SDK 的 `deferred` 工具始终可由脚本调用，无法同时标成 `model-only`。公开 Codemode 工厂也没有工具白名单选项。探针已验证可在公开扩展注册入口包装 ToolDefinition，过滤 `prepareLoadout.callable`、执行上下文的 tools，并在 executeTool 边界核对允许集合。这样事件/inline 工具仍可被模型发现，却不会进入脚本目录和执行入口；不访问 SDK 私有字段、不维护沙箱分叉。也可加公开 `tool_call` 的父调用检查作为守卫，不能只在提示中写“请只读”。

在能判定业务收益之前，至少处理三件事：

1. **可编程结果。** 当前大多数工具没有 outputSchema，脚本收到的是 content 的文本，拿不到 runtime details。优先为 web_search 提供明确的结果条目，为 web_fetch 提供文本窗口、下一 offset、来源/时间和截断状态。它们来自已有领域数据，content 仍供模型阅读，details 仍供 runtime 使用；不能把 details 整包暴露。图片和错误分支也要有完整合同，不能只为文本成功分支声明 outputSchema。文件工具先保留原有文本和截断上限。
2. **有限执行。** 候选初始预算：每脚本最多 16 个子调用、同时 4 个、宿主 30 秒时限、约 2,000 输出 token 上限，必要时由部署者调到 60 秒。它们是待试验校准的值。宿主必须执行上限，不能依赖模型自己写 options 行。取消、参数校验、路径/网络守卫和任务资格检查继续经过原工具链；只允许查询工具不等于允许绕过守卫。
3. **观察与错误语义。** 既有日志补 parentToolCallId 关联；用户侧显示中文进度，避免直接展示脚本和 SDK 英文错误。参数/语法错误让模型自行修正，真实守卫拒绝继续可见，父子错误避免重复通知。脚本失败不回滚已完成操作，取消不能留下新的迟到调用。子调用要纳入调用额度与原活动判定，容器不能重复计数；明确纯发现/空脚本不会假装完成了任务工作。

SDK 只把父脚本输出交给模型，nestedCalls 是有界执行元数据，不是完整原始结果仓库。脚本必须输出下一步推理所需的来源、片段、遗漏/截断提示；不能让结论只存在于脚本私有 store。首轮不另建完整中间数据归档系统。网页内容继续视为不可信数据；抽取后不能被当成新的系统或长期授权指令。

## 如何判定值不值

保留四种实验配置：A 当前路径、B 仅发现、C 仅受限 Codemode、D 组合。先分别比较 A/B 与 A/C，只有必要时跑 D。固定模型、thinking、工具权限、相同场景/seed、验收和输入快照，交错执行减少缓存/服务抖动干扰；冷启动与暖会话分开报告。不得禁止基线使用 shell、原有并行或现成 skill 来制造收益。

候选场景组成：动态分页统计、多来源筛选两个优势场景；简单代码修改/本地处理、中文事件需求、已有委派路径、跨多轮加载后的会话四个对照。优先复用现有 C-research、E-schedule、A-route 和相应安全场景；当前 C-research 的小型三文档阅读只能当对照，不足以证明大结果过滤的收益。确有缺口时新增一个数据处理家族并配正/负/等价控制，不以增加 case 数量为目标。

建议先做每场景 1–3 次的诊断采样，候选明确后再扩到配对多次比较。小样本只能筛选方向，不能声称统计显著。试点的暂定推进门槛：

- 用户目标完成与来源完整性不退化，守卫/取消/任务控制越界为 0；发现不到、脚本修复、截断误判均单列，不能靠最终答复看似合理算成功。
- 优势工作中，总体模型费用或端到端时间至少有一项观察到约 20% 的改善，且另一项没有明显恶化；普通工作中避免超过约 5–10% 的系统性退化。上述是产品筛选阈值，不是本轮已测收益或显著性结论。
- 同时报告实际请求输入与缓存 token、计费/未知费用、脚本生成和修复轮次、子调用数、首个进度与总耗时、嵌套原始返回量与模型可见返回量。只统计最后输出长度会漏掉脚本本身和额外发现的成本。

机制层验收覆盖真实 session → nested tool → guard/取消 → 事件/持久化/恢复路径；新 e2e 先做 mutation，优先扩展已有相关链。质量层使用既有 eval 工具，付费前跑 oracle controls；评测 trace 要保留真实父子关系，允许直接和嵌套的有效完成方式，不以“必须调用 codemode”充当质量标准。

## 讨论时优先确定的取舍

建议先确定两个产品选择：**第一批 Codemode 是否以多源资料/分页整理为目标；按需发现是否先只覆盖两个重工具。** 我的推荐均为是。暂不采用 codemode-only、全部工具延迟、脚本内委派、全量工具结构化重写或新 MCP 接入。

如果实际工作主要是外部 CLI 编程，且很少在 Pipiclaw 内做上述查询，就只完成发现能力的验证，把 Codemode 保留为按需试点；无需为了使用 SDK 功能改造整套工具系统。
