# 工具执行与委派完成延迟排查

日期：2026-11-04。范围：当前 checkout、锁定的 pi SDK 1.4.0、本机近期运行记录，以及离线机制复现。本次交付是排查和实施建议，未修改运行逻辑、配置或运行中的 daemon。

后续范围决定：用户要求仅使用官方发布的 SDK，分段调度已从 spec067 删除。下文保留排查时的观察与建议，当前实施和验收以 [spec067](../specs/067-execution-latency/design.md) 为准。

## 结论

1. **目前已经支持工具并发，并且实际任务在使用。** 同一模型回复中的普通读取、搜索、抓取和委派调用默认并发；一批调用只要含 `bash`、`write` 或 `edit`，SDK 就将整批串行化。不同模型回复之间有结果依赖，不能自动合并执行。
2. **正常外部委派使用进程退出回调，task 完成通知走主动唤醒。** 正常路径没有统一的数秒轮询间隔。task 的通知合并窗口是 50ms，本机一个任务的实际恢复间隔约 95ms。
3. **确认存在恢复路径缺口：重启后接管的外部进程，后续只在 deadline 再检查。** 它在重启之后提前完成，也可能一直显示运行中、持有写锁和并发名额，直到最长运行期限到达。已用真实子进程离线复现。
4. **后台 shell job 确有固定检查间隔。** 默认 10 秒扫描；模型主动 `job poll` 则每 3 秒检查。它与外部 sub-agent 的正常退出回调是两套机制。
5. **较复杂任务的主要放大项还包括结果等待边界。** 并发工具整批完成后才进入下一次模型请求；聊天完成事件要排在当前回合之后；task 正在执行的步骤也不会因委派完成而立即收到新输入。内部委派最多同步等待 120 秒，会使这些边界更明显。

## 一、当前执行链路

### 普通同步工具

模型回复 → SDK 准备/校验调用 → 执行工具 → 返回结果 → 下一次模型请求。

SDK 的 `executeToolCalls` 根据整批工具决定串行或并发。并发分支先顺序完成准备，再通过 `Promise.all` 启动执行；每个工具完成时可以发出 `tool_execution_end`，但是写回模型上下文的结果和下一次推理，要等待整批结束。工具完成到下一次模型调用之间没有定时扫描。

不能简单取消 `Promise.all` 后立即进入下一轮模型调用：模型协议中的工具调用与结果仍须完整配对。应通过缩短同步调用、及时派发长工作或改进调度边界来降低等待。

定位：`node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js` 的 `executeToolCalls`、`executeToolCallsParallel`；默认模式在同包 `agent.js` 的构造器中。主会话和内部子智能体均未覆盖该默认值，见 [session-host.ts](../../src/agent/session/session-host.ts)、[worker.ts](../../src/subagents/internal/worker.ts)。SDK 的工具包装器保留 `executionMode`。

### 外部委派，daemon 全程存活

派发并持久化 pid → 工具立即返回已派发 → 子进程 `close` → 等启动元数据探测结束 → 清理残留进程组 → 解析产物/可选 Git 摘要 → manager 持久化结果并记账 → 通知消费者。

- 绑定 task：将结果写入任务日志，然后调用 `onTaskInput` → `taskLane.notify()` → 约 50ms 后扫描 → 空闲且可执行的任务开始下一步。
- 聊天发起：立即写 durable dispatch 并尝试入频道队列 → 队列执行完成事件 → 主 Agent 推理。

定位：[external/run.ts](../../src/subagents/external/run.ts)、[external/settlement.ts](../../src/subagents/external/settlement.ts)、[runs.ts](../../src/subagents/runs.ts) 的 `settle` / `announce`、[bootstrap.ts](../../src/runtime/bootstrap.ts) 的 `onTaskInput` 接线、[task-lane.ts](../../src/runtime/task-lane.ts) 的 `notify`。

完成通知的文本推送使用独立的 fire-and-forget 通知路径。它出现了，不代表主 Agent 已经完成下一轮推理。

## 二、发现与优先级

| 优先级 | 发现 | 增加的等待 | 建议 |
| --- | --- | --- | --- |
| P1 | 接管外部 run 后缺少及时完成检测 | 可接近剩余最长运行期限 | 为接管中的 run 增加有界周期检查；仍由 manager 完成结算 |
| P1 | 后台 job 依赖 10 秒扫描 | 通常 0–10 秒，加扫描/调度耗时 | 完成文件变动主动触发检查，扫描保留为恢复保障 |
| P1 | 并发批次/正在运行的步骤阻挡已完成结果 | 取决于最慢工具或当前步骤余下耗时 | 优先避免长同步委派占住普通工具批次；评估在模型请求边界注入完成输入 |
| P2 | 频道队列满后靠 30 秒扫描重新投递 | 容量释放后仍可能再等约 0–30 秒 | 容量释放时主动重试对应频道的待投递事件 |
| P2 | 一项串行工具使整批独立读取串行 | 独立调用从耗时最大值变为耗时之和 | 采用以写操作为屏障的分段执行，或提供明确的独立只读调用路径 |
| P2 | Git 摘要缺少执行时限；短 run 收尾等待探测 | Git 路径无明确上界；正常版本探测超时 1 秒 | 给可选摘要设执行时限；缩小诊断探测对结果发布的依赖 |

### 1. 重启接管后的完成检测缺口：已复现

[runs.ts](../../src/subagents/runs.ts) 在 `restore()` 时检查一次外部进程；若仍运行，就通过 `scheduleExternalRecovery()` 将下一次检查安排在 `deadlineAt`。`get()`、`list()` 只读内存，任务扫描的 `retryTaskSettlements()` 也只重试已经终止而未记入任务的记录。全局日常维护负责保留期清理，不会补上及时完成检测。

所以这一条链成立：

1. 外部 CLI 仍存活时，旧 daemon 消失。
2. 新 daemon 接管并确认进程存活。
3. CLI 在 deadline 前完成，旧进程的 `close` 回调已经不存在。
4. 新 daemon 直到 deadline 才再次检查并通知任务或聊天。

离线复现使用真实 Node 子进程、真实磁盘记录和两个独立 manager 实例。初始 manager 只创建可恢复的启动记录，不安装任何退出结算回调；随后停止其观察并由新 manager `restore()`。子进程收到受控输入后写入合法 Claude terminal 产物并退出。deadline 缩短到 1.5 秒，避免等待生产级时限。

结果：子进程已退出时，新 manager 仍为 `running`，未发 wake；**退出后约 1500ms，到 deadline 才变为 `completed` 并发 wake**。这证明 manager 接管后的机制缺口；完整进程崩溃的修复验收仍应走现有 daemon e2e。

影响同时覆盖：task 恢复、聊天结果回收、运行名额和写锁释放。若配置的最长运行时间为一小时，提前完成的 run 就可能无谓等待其剩余时间。

建议给接管 run 增加周期观察；后续用户裁决该路径属于冷链路，检查周期采用约 10 秒，deadline 继续承担超时执行。观察必须复用现有身份判断、产物解析和 manager 幂等结算，防止观察重入。收到 terminal 文本只能触发检查，不能据此在进程尚可写入时释放写锁。当前文件预算已超限的 `runs.ts` 应按职责抽取观察逻辑，不增加架构例外。

现有 [external-run.test.ts](../../test/e2e/deterministic/external-run.test.ts) 的 A18 确认崩溃后接管和 `/stop` 保留进程，但在进程仍存活时结束，未检查“接管后自然完成并及时唤醒”。应扩展这条链，释放 held 子进程并观察结果进入 provider，保持用例数不变；删除新的完成观察后必须变红。

### 2. 后台 job：完成检测存在 10 秒粒度

[manager.ts](../../src/jobs/manager.ts) 的 `SWEEP_INTERVAL_MS = 10_000`，运行期间批量检查 `.exit` 文件及进程状态。完成时间若与扫描相位无关，单纯相位等待的理论均值约为 5 秒；这不是生产统计。`poll()` 的检查粒度为 3 秒，单次最多等待 30 秒。

建议监听运行中 job 的完成文件所在目录，原子 rename 的 `.exit` 出现时主动调用既有 reconcile 路径，并通知正在 poll 的调用；周期扫描继续覆盖漏事件、重启和异常退出。当前 job 通过 `Executor` 启动，事件观察必须尊重其宿主 I/O 边界，不能默认所有实现都能在 daemon 本地直接 `fs.watch`。本地执行器可走主动通知，其他实现保留可用的探测路径。

### 3. 完成已被检测，主 Agent 仍可能暂时拿不到

**工具批次屏障。** `Promise.all` 必须等最慢调用结束。假设同批一个读取用 20ms、一个抓取用 40ms、一个长同步内部委派用 90 秒，则读取结果已完成，模型仍要等该批结束才能继续。内部委派的 [grace.ts](../../src/subagents/grace.ts) 默认同步等待上限为 120 秒，多个委派共享本回合 deadline；这不是每次结束后再额外等待 120 秒。

**聊天回合屏障。** [ingress.ts](../../src/runtime/ingress.ts) 的完成事件进入频道串行队列。新结果不会抢占正在运行的回合，延迟还包含当前回合的模型/工具工作及收尾。结果在事件回合真正开始时才合并；[wake-coalescing.ts](../../src/runtime/wake-coalescing.ts) 已经做到首个结果不额外等待聚合窗口。

**task 步骤屏障。** `TaskLane.maintain()` 遇到 `live.driving` 直接跳过；当前步骤发给模型的 brief 是步骤开始时构造的。步骤中途到来的完成结果保存在任务日志，后续步骤读取。步骤结束时有立即重评，正常情况下无需等下一次周期扫描，但步骤内还有很长工作时，输入的可见性仍受边界影响。

实施顺序建议：先使长内部委派能尽快返回派发结果，让主 Agent 继续处理独立工作，再在需要时进入已有 task 等待；保持小型同步委派的直接返回收益。随后评估复用 SDK 模型请求边界，将已持久化的新结果作为受控输入送入正在推进的 task。输入确认、重试、停止、跨重启去重必须一起设计，不能单纯追加一个内存事件就认为已消费。行为变化需要真实模型 dev probes。

### 4. durable dispatch 的 30 秒等待属于重试路径

[durable-dispatch.ts](../../src/runtime/durable-dispatch.ts) 的 `dispatch()` 写入后立即调用 `drainRecord()`。30 秒周期主要负责队列拒收、未完成记录和恢复重试，正常首次投递不等它。

频道事件队列上限是 5。队列满了，事件退回 pending；当前缺少“容量刚释放，立即重试这个频道”的通知，所以可能再等到下一次 30 秒 tick。真实 handler 失败还有指数退避（30 秒起，最长 10 分钟），这是另外一种情况。

建议在频道释放容量时触发有界、合并的 pending drain，并继续尊重 `nextAttemptAt`、存活 lease 和 poison-pill 计数。task 绑定 run 正常通过 lane 直接通知，不经过这条聊天 wake 队列。

### 5. 可选收尾工作仍在结果发布的关键路径

[external/run.ts](../../src/subagents/external/run.ts) 的退出回调先等待 `launchMetadataPromise`。版本探测生产实现超时 1 秒且成功结果有缓存，对持续几分钟的 run 通常早已完成；非常短的 run 仍可能被它拖住。进程身份探测自身没有执行 timeout，属于需要补上界的异常路径。

写入型 run 完成后，[settlement.ts](../../src/subagents/external/settlement.ts) 等待 Git 摘要；[workspace-summary.ts](../../src/subagents/workspace-summary.ts) 的 `git status --untracked-files=all` 没有 timeout，读取全部未跟踪文件，大仓库或慢文件系统会延长完成到通知的时间。`.catch` 只处理失败，不限制等待时间。

应给可选 Git 子进程设置执行期限；读取型 run 已经跳过此项。结果、记账、租约、任务输入的持久化顺序仍由 manager 保持。运行归档当前只是向异步 appender 入队，未发现它会固定等待整份日志落盘，因此不把它列为正常路径的主要瓶颈。

## 三、并发能力的验证与改进边界

| 调用形态 | 当前行为 |
| --- | --- |
| 同批多个 `read` / `grep` / `glob` / `web_search` / `web_fetch` | 默认并发执行，全部完成后再请求模型 |
| 同批多个外部 `subagent` | 并发执行派发流程；派发返回后，外部进程继续并发 |
| 同批多个内部委派 | 可以并发，但批次仍可能等待同步 grace 内的结果 |
| 任意批次包含 `bash` / `write` / `edit` | 整批串行，包括其中的读取和派发 |
| 多个 `bash async` | 工具启动流程串行，启动后的后台进程可并发 |
| 写入同目录或父子目录的委派 | workspace 写锁拒绝冲突派发，不会排队等待 |
| 不同 task / 不同频道 | 可并行，受各自上限及共享资源约束 |

串行声明分别位于 [bash.ts](../../src/tools/bash.ts)、[write.ts](../../src/tools/write.ts)、[edit.ts](../../src/tools/edit.ts)。它们保护同批写入顺序和文件完整性，直接删除声明会重新引入读改写覆盖风险。

离线使用当前 SDK 的真实 `runAgentLoop`、脚本模型流和三个耗时 20/40/160ms 的工具执行体：

| 场景 | 实测最大同时执行数 | 批次总时间 |
| --- | --- | --- |
| 三个默认并发工具 | 3 | 约 167ms |
| 第三个声明为串行 `bash` | 1 | 约 224ms |

并发场景中，`read` 在约 27ms 发出完成事件，但三个 `toolResult` 在约 166ms 一起进入上下文。这同时验证了已有并发能力和批次屏障。数字仅是离线机制样本，不是生产提速比例。

工具调度若进一步优化，可使用明确的写屏障，例如 `read A, read B, write C, read D, read E` 按“两项并发 → 写入 → 两项并发”执行，保留写操作前后顺序。这需要 SDK 调度能力或受测试覆盖的适配；当前 SDK 的 `executionMode` 只有整批串行开关，Pipiclaw 没有现成配置可直接开启分段模式。

两个独立 shell 命令要并发，应有明确的调用方独立性约定或隔离工作目录，不能靠简单的命令前缀白名单猜测读写。子智能体写锁也不覆盖主 Agent 自己的文件工具。

另一个旧任务在委派仍运行时调用了按时间等待，先后开启了额外步骤。当前系统提示已要求只剩等待时结束回合，所以这属于应以行为 probes 检验的决策质量问题；不应通过添加更多定时“检查一下”事件来掩盖。

## 五、建议实施顺序与验收

1. **先补可关联时间线并修复接管检测。** 关联 `desk/taskId/runId/dispatchId/toolCallId`，记录外部 terminal 输出被观察、进程退出被观察、结算完成、输入落盘、通知发出、队列入队/拒绝、步骤开始、provider 请求开始和首个输出。将“结果已完成”与“已消费”分开计时。SDK 的工具 start 事件发生在调用准备之前，并发批次还要等其他调用准备，所以现有卡片耗时包含准备阶段，不能直接当作工具执行体的耗时。
2. **让后台 job 完成主动触发 reconcile。** 保留低频扫描；用完成文件出现的受控时点验证恰好一次结算和通知，覆盖原子 rename、重启、取消和停止。
3. **补频道容量释放通知。** 扩展现有队列满/合并唤醒链，在容量释放后观察 pending 被消费；故意移除通知后变红。失败退避继续有效。
4. **缩短批次中的长同步等待。** 优先处理内部委派与其他工具共批造成的阻塞，再评估 task 步骤内的新输入注入。保持独立工作可推进，避免每个并发结果多开一轮空推理。
5. **再做工具分段并发和可选收尾限时。** 按真实追踪选择收益最高的路径；不靠整体取消写入保护换取局部 benchmark 数字。

修复 runtime、task、委派或命令链路时执行 typecheck、unit、arch 和确定性 e2e。优先扩展已有高价值场景，保持用例数不增长；新增机制断言应附 mutation check。改变委派同步策略、提示或等待决策后计划受影响 evals，使用配置的模型跑相关 dev probes，并独立保留失败证据。

关注指标：完成到检测、检测到输入落盘、输入到下一次 provider 请求、请求到首个输出的 P50/P95；批次宽度和最慢调用占比；每个 task 的模型往返数；完成后仍持有的 run 名额/写锁时间。不能仅凭工具卡片显示完成到用户看到最终答复的总间隔判断通知慢。
