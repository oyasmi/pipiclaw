# pi 0.84.3 → 1.2.0 升级评估

日期：2026-10-13。Pipiclaw 基线：`b61465fbcb576f843a7f136ea6988459331939d2`，包版本 `0.9.4-beta.2`。

## 结论

建议升级到精确锁定的 **1.2.0**，但不能只改四个依赖的版本号。已经实测发现两个主会话接入问题：首次请求丢失全部工具声明，以及备用模型收到重复用户输入。它们属于 SDK 语义变化，单元测试无法充分发现。

改造集中在现有 SDK 接入层，无需重写任务、记忆、委派、钉钉传输，也无需迁移到 `pi-durable`。新增 OpenAI OAuth 必须补齐设备 ID 接入后才能作为可用功能提供。MCP、codemode、虚拟模型、缓存预热应另立功能变更，不与基础升级混合。

本次只在主仓库增加评估文档；依赖与兼容性试验位于隔离副本 `/home/oyasmi/projects/.pipiclaw-pi120-audit-N3cWXT`。该副本是验证原型，不是完成上线与所有供应商认证验收的发布分支。

## 必须处理的接入问题

### 1. 主会话的工具声明与持久化上下文不同步

接入点：`src/agent/session/session-host.ts` 的 `createSessionRuntime()`。

目前手动 `new Agent()`，给 `initialState.tools` 赋完整工具集，却没有把历史消息初始化为 SessionManager 的投影。新版 Agent 根据 tools 生成一条仅在内存中的初始 system 消息。agent-loop 以为这套工具已经声明，后续消息只记录提示 sections；AgentSession 在 provider 请求前从 SessionManager 重建上下文，内存中的初始工具声明就消失了。

实测：Agent 的执行工具有 **23 个**，provider 收到的 JSON **没有 tools 字段**。任务和记忆 e2e 因此大量失败。独立请求探针可复现，不能用“模型能返回文字”作为升级验收。

隔离副本的修复：构造 AgentSession 时明确 `initialActiveToolNames` 为 Pipiclaw 的工具名单，构造完成后调用 `session.refreshContext()`。这样第一轮声明以持久化上下文为基线，实际请求恢复全部 23 个工具。正式实现也可直接采用上游 SDK 工厂的初始化模式：Agent 初始 tools 为空，messages 来自已有 session，再由 AgentSession 装配工具。

这条规则应同时覆盖启动、`/new`、fork、会话切换与任务/聊天绑定，因为它们都经过同一个构造函数。不要另加平行的会话恢复机制。

### 2. 主会话 fallback 的内存裁剪失效

接入点：`src/agent/turn/turn-pipeline.ts:buildFallbackDeps()`；语义定义在 `src/models/fallback.ts`。

当前备用模型切换前只把 `[user, assistant(error)]` 从 `agent.state.messages` 的尾部移除。新版 AgentSession 会重新加载持久化历史，该赋值不影响下一次请求。再次 prompt 后，备用模型实际收到同一条用户输入两次。

原 A22 只检查切换及答复，因此仍会通过。延伸该用例，直接检查备用模型 request body 中这条输入的次数，实测 **期望 1、实际 2**，证明是机制问题。

隔离副本改用 `buildSessionProjection()` 找到失败的一对消息，校验投影长度与 user/error 尾部后，为其追加 `appendContextEdit(entryId, null)`，再 `refreshContext()`。不重写 JSONL，不抹掉历史费用，不删除审计记录。修复后 request body 只出现一次输入。

正式实现建议把这段 SDK 投影操作收敛到 `agent/session/session-adapter.ts`；保留“只允许首个请求失败的一对消息，执行过工具的多步失败不盲目重跑”的已有规则。恢复、压缩、reflect 对 raw branch 与 projected context 的用途要明确：context_edit 是模型上下文修改，不是删除历史事实。不要把“模型不可见”自动等同于“记忆审计不可见”。

内部子代理使用裸 Agent，没有 AgentSession 的 canonical projection；`subagents/internal/provider-retry.ts` 中的内存裁剪不能机械地一起改成上述方法。

### 3. 类型检查：三处文件、四条诊断

直接换依赖后，`npm run typecheck` 报错：

- `session-host.ts`：JSON 约束使连续 isRecord 类型收窄错误地只剩 toolResult，比较 user 被判不可能。对读取出的 message 先按 unknown 做运行时检查即可，保留对异常持久化数据的防御。
- `test/agent-session-tool-images.test.ts`：AfterToolCallContext 的 AgentContext 已不含 systemPrompt，移除测试夹具中的旧字段。
- `test/turn-recovery.test.ts`：ToolCall.arguments 的 `object` 改成 `JsonObject` 或 SDK 的对应内容类型。

当前生产代码中的工具 details 没有引发成片类型错误。没有必要通过 `as any` 全面放宽类型。

### 4. 两个 e2e 夹具需跟随真实协议变化

- `inbound-media.test.ts` 的图片仅有 10 字节 JPEG 文件头，原测试依赖 SDK 不解码它。新版处理用户图片时会校验/规范化图片并剔除损坏输入。换为完整的 1×1 PNG 后，provider 确实收到 image_url，原机制断言保持。
- `system-prompt.test.ts` 的工作目录尾部已由普通文本改成 `<cwd>…</cwd>`。更新对应结构定位，继续检查 Pipiclaw 提示所有权、runtime boundary 在最后及频道隔离。实测边界仍在末尾。

没有新增 unit/e2e 用例；延伸既有 fallback 用例，数量净增 **0**。把旧的内存赋值作为目标故障运行时，新增的输入次数断言已变红，满足该断言的 mutation check。

## 条件迁移与进一步接入

### OpenAI 的新 ChatGPT OAuth

`src/models/provider-login.ts` 目前只传第三个 interaction 参数。新 `ModelRuntime.login()` 还接受第四个 `LoginOptions`；该登录要求 `getDeviceId()` 返回本安装稳定的 UUID。

离线调用现有形式，立即报错：`Sign in with ChatGPT requires a device ID (UUID) for this installation`。它发生在网络登录前，已确认不是账户或网络问题。

如果升级后让 `pipiclaw auth login` 展示新 openai/oauth 选项，必须持久化一个 Pipiclaw 安装 ID，并传入 `getDeviceId`；可以同时传 `agentName: "pipiclaw"`。不应每次生成不同 UUID，也不应转而读写 `~/.pi`。该功能尚未进行真实 OAuth 完整登录验收。原 openai API key 与 openai-codex legacy 并没有因此要求统一迁移。

Pipiclaw 多处调用 compat `streamSimple` 并只通过 API key 接口解析认证。新增使用 auth headers、baseUrl 覆盖或虚拟路由的供应商/扩展时，应评估通过 `ModelRuntime.streamSimple` 或注入完整请求认证结构，而不是假定字符串 key 覆盖所有认证能力；这是接入新能力的工作，不是此次 mock API key 试验已经验证的结论。

### Azure 配置

只有使用原内置 provider `azure-openai-responses` 的部署需要迁移到 `azure`：认证 provider key、models.json provider key、Pipiclaw settings 中的模型引用，以及 sub-agents 角色中的模型引用都要一起检查。

**API 标识 `azure-openai-responses` 和 AZURE_OPENAI_* 环境变量保持原名。** 不能全局字符串替换。历史会话内也保存 provider/model identity，需要验证恢复选择；不要手改所有历史 JSONL。当前主代码未硬编码旧 provider ID，不能据此推断部署配置也没有它。

### 目前没有要求重写的 API

- 普通 Agent、AgentTool、AgentSession、SessionManager、ModelRuntime/ModelRegistry，以及 compat/providers/all 导入仍可用。
- Pipiclaw 没使用被移除的 AgentHarness、harness/*、pico3、experimental server/client；不需要改用 pi-durable。
- 没有 shouldStopAfterTurn/prepareNextTurn 的生产 SDK 钩子使用；`runtime/turn-run.ts` 的同名本地 finishTurn 是 Pipiclaw 自己的函数。
- 提示边界扩展只读取新事件两种分支共有的 systemPrompt，不需要给 custom run 强加 user-only 条件。
- TUI 使用 ProcessTerminal 和 TuiMainScreen，没有自定义 Terminal 或脱离 TUI 渲染 Editor，新的 setProgramStatus 与光标标记不构成当前的必改代码。
- 私有 `_baseToolsOverride` 在 1.2.0 仍存在，当前工具重载适配可继续工作。它仍是私有耦合，不能把“当前存在”当成永久兼容承诺。

## 升级的实际收益

### 现有功能可获得的收益

1. **长任务更稳。** 大工具结果可以在下一次 provider 请求前压缩；错误尝试的上下文省略可以持久化；压缩取消、fork 边界、消息排序与末尾换行修复直接关联持续工作的稳定性。
2. **供应商兼容性与错误恢复改善。** Anthropic thinking 签名回放、OpenAI Responses 未完成工具调用、Mistral 分片/长生成超时、OpenRouter reasoning 参数、strict schema 支持判断与降级、瞬时错误识别均有修复。后者也能改善内部子代理使用的 retry classifier。
3. **模型目录、能力和费用元数据更完整。** 区间加入新的 Claude/GPT 等模型与正确的 effort/上下文限制；修正缓存写入、长上下文价格与 fast tier 费用。Pipiclaw 的模型选择和 usage ledger 可从供应商返回的修正数据受益。具体部署是否可用仍取决于认证与供应商。
4. **reflect/压缩输入更轻。** `serializeConversation()` 不再携带 thinking。Pipiclaw 的 reflect 与压缩输入预算直接调用它，因此隐藏推理不再参与这些序列化输入；模型可见文本和工具行为仍保留。不能据此承诺固定比例的 token 节省。
5. **依赖更容易统一。** coding-agent 移除 shrinkwrap 后，本次锁文件中 core/ai/tui 各只有一份 1.2.0，旧锁各有顶层与 coding-agent 内部副本。整个 lock 的包条目从 538 到 412；同时新增 pi-mcp、pi-codemode，没有引入 pi-durable。数量变化也包括这次依赖重新解析，不是纯 SDK 性能指标。
6. **TUI 基础组件修复。** Markdown/Text/Box 缓存与长文本渲染、按键解析、终端响应碎片处理等可作用于本项目使用的组件；全屏专有功能并非当前 TuiMainScreen 都能获得。

## 验证记录

直接升级的 typecheck/build 不通过。修复三处类型适配后，unit 在仓库副本位于普通项目路径时 **952/952 通过**，但主请求丢工具仍导致 e2e 失败。因此 unit 全绿不足以判定升级安全。

最初副本放在 /tmp，playbooks 只读边界用例因此触发默认临时目录写权限，出现 1 条环境失败。移到 `/home/oyasmi/projects/` 后，同样的 952 个 unit 全绿；原版本的相关 8 个 playbooks 测试也通过。没有改守卫或弱化测试来消除这条环境差异。

修复工具同步并延伸 fallback 断言后，一次完整 deterministic e2e 为 **52 通过、3 失败 / 55**：重复输入、伪图片、旧 cwd 标记。分别处理后，fallback 以及图片/提示针对性检查通过。最终全套结果在下方记录。

另做一个 0.84.3 → 1.2.0 的磁盘兼容探针：旧 SDK 写真实 JSONL，包含 user、assistant、thinking_level_change；新 SDK 成功重开，消息和 high thinking 保留，header 版本均为 3。这证明了该样本的前向读取，不等价于所有历史压缩分支、跨版本 crash 或降级安全已验证。

## 建议的正式升级边界

先做一个以 SDK 兼容为目的的变更：四个依赖精确 1.2.0、更新并提交 lock、修复构造与 fallback、调整类型和既有 e2e 夹具；把新 OpenAI OAuth 的可用性处理明确纳入范围。保持 Pipiclaw 的任务、票据、委派结算与传输所有权。

正式发布前，用快照副本运行旧聊天/任务 session、真实供应商流与认证 smoke，重点验证常用 Anthropic、OpenAI、OpenRouter/自定义代理，以及使用时的 Azure。继续执行 typecheck、unit、arch、build、deterministic e2e 与仓库其他要求的检查。

保存应用数据快照再灰度切换；升级后新写的 system/context_edit 等记录不能假定被旧 SDK 以相同语义回放。回退应同时考虑恢复升级前 session/应用状态，不能只降 npm 版本。新功能另行验收，避免把“底层依赖升级成功”误当成所有上游 CLI 功能已经进入 Pipiclaw。
