**R1 · P1：合并完成唤醒时，旧 dot 的内容绕过准入进入新 dot**

位置：[turn-run.ts:215](../../src/runtime/turn-run.ts#L215)、[wake-coalescing.ts:21](../../src/runtime/wake-coalescing.ts#L21)、[durable-dispatch.ts:329](../../src/runtime/durable-dispatch.ts#L329)。

单条 synthetic event 在 `runEventTurn` 入口会核对所属 dot。但合法主事件通过检查后，`admitTurn` 以 `isCoalescableWake` 为条件调用 `absorbPending`。这个条件只检查完成唤醒的 id 形状和没有 `internalWake`，没有检查候选的 `dot`。outbox 只按同一个 `channelId` 聚合。

可复现顺序：

1. 频道从 `e2e` 换绑到 `lab`。
2. outbox 中保留同一频道的旧 `e2e` 完成唤醒，以及新的 `lab` 完成唤醒。
3. 先消费合法的 `lab` 唤醒。
4. 旧唤醒被吸收，文本直接拼进 `lab` 的请求；它自己的准入分支没有执行，随后记录还被标记完成。

真实 runtime 探针输出：

```json
{"boundDot":"lab","modelRequests":1,"oldDotResultInModelRequest":true,"staleOutboxDeleted":true}
```

影响包括跨 dot 上下文污染、旧结果驱动新 dot 执行动作，以及该污染进入新 dot 的持久会话。即使采用 v1 已确认的共享权限策略，这仍然违反运行时明确承诺的归属检查。

建议：合并条件必须要求候选有 `dot` 且等于主事件所属 dot，并满足当前绑定准入规则。把这条规则封成纯判断供单条准入和合并复用，防止两条路径再次分叉。无 dot 的旧记录也不能被合并。丢弃不匹配记录时单独完成，不能把其正文带入当前回合。

验收：扩展现有 DOT-3 或 wake-coalescing 场景，同时放入合法主唤醒、旧 dot 唤醒和无 dot 唤醒；观察 provider 请求正文与 outbox 状态。删除合并谓词中的 dot 条件后必须变红。保留“只有一条合法唤醒回合”的断言，避免修复退化为完全关闭合并。

**R2 · P1：陈旧锁的 rename 后核对无法保持互斥**

位置：[file-lock.ts:130](../../src/shared/file-lock.ts#L130)。

`reclaimStale` 先把当前锁路径 rename 到旁路，再检查搬走的 token 是否仍是先前看到的陈旧锁。如果搬走的是另一进程刚取得的活锁，再尝试 `link` 回去。这段期间，正式锁路径已经不存在。

受控的真实子进程顺序：

1. A 读到陈旧锁，在 rename 前暂停。
2. B 回收陈旧锁，成功获得新锁，继续持有。
3. A 恢复，把 B 的活锁搬到旁路。
4. C 看到锁路径空缺，成功获得锁。
5. A 发现 token 不符，尝试恢复 B 的锁，但路径已被 C 占据；`EEXIST` 被忽略，旁路文件被删除。

实测 B、C 两个不同 pid 均返回 `kind: "acquired"`，且都尚未释放。探针仅在 A 的系统调用边界暂停和恢复，独占创建、读取、rename、link 都执行真实文件操作。

影响：`memory.lock`、`dot-json.lock`、任务锁和 TUI 会话区锁都依赖这个实现；从进程异常退出后的恢复，可能演变为并发写坏共享状态。原有“别删除别人的锁”测试没有覆盖两个回收者基于同一旧快照并发回收的情况。

建议：采用能证明互斥的持锁/回收协议。可以评估由内核托管生命周期的锁；若继续用文件协议，创建、回收和释放必须共享一致的协调规则。仅在 rename 前再读一次 token，或 rename 后再次核对，都不能消除检查与动作之间的窗口。修复应明确支持的操作系统和文件系统条件。

验收：保留并扩展现有跨进程锁测试，使用可控 IPC 构造上述顺序；整个过程最多一个进程进入临界区，且仍能在持有者被杀后恢复。该问题值得单独保留回归场景，不能只靠正常竞争的重复压力测试。

**R3 · P1：绑定提交前启动 watcher，错过 dormant dot 的过期一次性事件**

位置：[dot-runtime.ts:205](../../src/runtime/dot-runtime.ts#L205)、[dot-runtime.ts:264](../../src/runtime/dot-runtime.ts#L264)、[watcher.ts:511](../../src/events/watcher.ts#L511)。对应设计 D5、D6 的顺序。

`bindNow` 先 `activate(dot)`，激活在服务已启动时立即启动 watcher；然后才分配会话区、写入绑定表并更新内存。watcher 启动扫描会恢复已经到期的一次性事件，此时新频道还没有绑定，`isBound` 返回 false。事件被跳过并写入错误标记，不再有后续定时器。

复现：在没有绑定的 `news` 中放入一条投递给 `dm_u` 的过期 one-shot；由另一个合法持有者暂时占住 `dot-json.lock`，让绑定停在分配阶段。watcher 先完成扫描，再释放锁让绑定提交。结果：

```json
{"bound":true,"dispatched":0,"recoveryErrorMarker":true}
```

绑定成功后，运行中的 watcher 不会因为绑定表变更重新加载这个事件；文件只有错误标记变化，watcher 只关注 `.json`。因此应在重新激活时恢复的提醒，可能要等下一次完整重新激活才有机会恢复。

建议调整设计：把“准备目标 dot”和“允许后台服务产生工作”分开。完成目标可用性检查、会话区分配和恢复准备后，先提交绑定并发布内存状态，再启动新 dot 的 watcher/扫描。已经激活的目标也需要定义绑定变化后的待恢复处理。绑定提交后的服务启动失败，应作为已提交绑定的降级状态处理，不能对用户谎报整个绑定未发生。

验收：扩展绑定的确定性集成场景，用真实 watcher 和受控 registry 锁观察过期 one-shot 的入队次数为 1；绑定写盘失败时为 0。仅断言 watcher 的 `start` 被调用，不能证明此链路正确。

**R4 · P1：休眠后在途加载还能注册 cron，重新激活可能有两个 watcher 执行**

位置：[watcher.ts:123](../../src/events/watcher.ts#L123)、[watcher.ts:316](../../src/events/watcher.ts#L316)、[watcher.ts:467](../../src/events/watcher.ts#L467)、[dot-runtime.ts:226](../../src/runtime/dot-runtime.ts#L226)。

`stop()` 关闭现有 fs watcher、timer、cron 并清空集合；它没有等待或取消已经开始的 `handleFile`。`handleFile` 在 `await readFile` 后没有检查本实例是否仍然启动，就能调用 `handlePeriodic` 注册新 cron。

实测：暂停 periodic 文件的读取，调用 `stop()`，再放行读取，等待该次加载完成：

```json
{"started":false,"scheduledCronsAfterStop":1}
```

动态休眠会把这个 watcher 从 `DotRuntime.watchers` 删除，之后没有引用负责再次停止它。dot 重新激活时会新建另一个 watcher。旧 cron 此时也会看到绑定恢复，有机会与新 cron 一起执行 preAction 或产生工作。即使下游实例 id 去重挡住部分重复创建，preAction 和 history 仍可能重复；文本事件的 occurrence 时间也不能假定一定相同。

该异步停止缺口原本就存在于 watcher；058 引入进程内反复激活/休眠后，其影响扩大为持续存在的孤儿调度器，属于本次集成必须补齐的生命周期契约。

建议：为每一代 watcher 增加取消/世代标识，在异步加载完成后、注册定时器前、产生外部动作前复核；跟踪在途操作，提供可等待的 drain。`DotRuntime` 需要在丢弃实例前等待其停止完成，再 flush 最终 history。单纯把 `started = false` 放在入口不够，因为操作可能已越过入口。

验收：用受控读取完成“start → 文件加载暂停 → stop → 加载恢复”的场景，断言没有遗留调度；再覆盖重新激活后的一次真实触发，观察 preAction/dispatch 各一次。不要用固定 sleep 猜测窗口。

**R5 · P1：迁移外层 dispatch id 后，旧的 wake claim 拒绝合法恢复**

位置：[migrate-to-dots.mjs:631](../../scripts/migrate-to-dots.mjs#L631)、[migrate-to-dots.mjs:679](../../scripts/migrate-to-dots.mjs#L679)、[runs.ts:466](../../src/subagents/runs.ts#L466)、[manager.ts:823](../../src/jobs/manager.ts#L823)、[wake-claim.ts:24](../../src/shared/wake-claim.ts#L24)。

迁移会把 outbox 的 `record.id`、`event.dispatchId` 从频道形式改为 dot 形式；job 和 run 记录中的 `wakeClaimDispatchId` 没有同步改写。`event.internalWake.dispatchId` 也保留旧值，虽然当前 consumer 使用的是外层 id，暂未因此直接失败。

当旧进程已经认领完成唤醒，但尚未完成任务激活或最终消费时，持久化 claim 是正常的恢复状态。迁移后新的 dispatch id 与旧 claim 不相等，`beginWakeClaim` 拒绝恢复；consumer 把它视为不可验证并完成丢弃。

用完整可被真实 manager 恢复的 job record 复现：

```json
{
  "verifyProblems": [],
  "migratedDispatchId": "job:news:job_claim:done",
  "persistedClaim": "job:dm_u:job_claim:done",
  "claimAccepted": false,
  "claimAfterIdRepair": true
}
```

对照只修正持久化 claim id，真实 manager 即接受相同的唤醒，排除了 fixture 无法加载等干扰。run 使用相同的 claim 规则，也有同类缺口。

建议：列全恢复协议中所有引用 dispatch id 的字段，逐字段做结构化迁移，并保持 `wakeConsumedAt` 等已消费事实。不要通过清空全部幂等标记“修好”恢复，否则可能重复消费。`--verify` 至少校验迁移后的 outbox、owner claim 和 producer 预期 id 的关联一致性。

验收：扩展现有“完整迁移”用例，放入有效、已 claim 未 finish 的 job/run 和对应 outbox，迁移后实际调用 owner 的恢复/认领接口。当前迁移夹具中的部分 job/run 只有少数字段，文件搬到了新位置不能证明生产 parser 能接管它。取消 claim 字段迁移后，该断言必须变红。

**R6 · P1：迁移缺少对仍存活的 detached 工作的前置约束**

位置：[migrate-to-dots.mjs:168](../../scripts/migrate-to-dots.mjs#L168)、[migrate-to-dots.mjs:178](../../scripts/migrate-to-dots.mjs#L178)、[migrate-to-dots.mjs:398](../../scripts/migrate-to-dots.mjs#L398)、[launch.ts:66](../../src/jobs/launch.ts#L66)。涉及 D20 的运维设计。

脚本只识别程序名为 Pipiclaw 的进程。停止 daemon 后，设计上允许继续运行的后台 job、外部 agent 和 wrapper 仍然存活；它们已经把旧的 artifact、exit marker 等绝对路径放进进程参数或 shell 脚本里。迁移磁盘上的记录无法修改这些正在执行的路径。

复现使用与 job wrapper 相同的关键机制：子进程持有输出文件，等待受控输入后向旧路径写 `.exit.tmp`，再 rename 为 `.exit`。daemon 不在运行，迁移获准执行；目录迁走后放行子进程，结果如下：

```json
{
  "migrationAccepted": true,
  "wrapperExitCode": 2,
  "exitMarkerAtNewPath": false
}
```

shell 报错为旧目录不存在；迁移后的 `--verify` 在释放这个进程前返回空问题列表。实际外部工作也可能丢失最终状态、写出新的旧布局目录，或保留仍指向旧 artifact 的恢复参数。已经打开的输出 fd 能继续写，不代表之后按路径创建的状态文件也能写。

建议为这次一次性升级采用明确的后台工作静止前置条件：旧版本中先等待或显式取消运行中的 job/外部 run，确认 wrapper 已退出，再停 daemon 和执行迁移。脚本读取持久化 run/job 状态，并结合可验证的进程身份拒绝仍有活动工作的迁移；对无法确认的状态输出明确诊断。不要把检查范围扩大成按名字任意杀进程，也不要静默替用户取消工作。

验收：在迁移测试中放入真实阻塞中的本地 wrapper，确认脚本在移动任何目录之前拒绝，数据字节不变；退出并确认结果持久化后再迁移成功。该前置条件及失败恢复步骤应同步进入 D20 和部署文档。

**R7 · P2：生产端丢弃与准入端丢弃，对任务等待状态的处理不一致**

位置：[runs.ts:689](../../src/subagents/runs.ts#L689)、[manager.ts:740](../../src/jobs/manager.ts#L740)、[turn-run.ts:479](../../src/runtime/turn-run.ts#L479)。

实施记录已经识别“被抑制的完成唤醒仍需兑现 work 等待条件”，因此 run/job 的 `suppressWake` 会通过 `redeemTicket` 恢复任务。但是，如果生产时频道仍绑定，唤醒已持久化，消费前才换绑，准入分支只 `markCompleted`，没有执行等价的资源确认与等待兑现。

复现使用真实 manager 注册 run、通过 `resolveTicket` 建立 work 等待，再由真实 `settle → dispatch` 生成 outbox；受控延迟队列消费，换绑后投递旧唤醒，再绑回：

```json
{
  "taskStateAfterRebind":"parked",
  "ticketKind":"work",
  "runSettled":"completed",
  "wakeEnqueued":true,
  "providerRequests":0
}
```

任务不会立即读取已经完成的结果，而要等原 work backstop。内部 run 没有单独 deadline 时，等待可能很长。这不是永远无恢复，因为 backstop 仍有效，但与生产端抑制时的恢复行为不同，也会产生错误的“等待超时”信息。

建议：统一资源完成的业务收尾语义，使其独立于聊天投递是否成功。可由 origin dot 的 owner 在验证资源归属后幂等完成兑现，或者记录可重试的收尾事实。准入拒绝路径不应创建当前频道的新 runner，也不能只信任 wake 文本就恢复任务；仍必须经过 owner 验证和 `redeemTicket`。

验收：把上述顺序补入现有 DOT-3/structured wake 链，绑回后在 backstop 之前即可推进，并验证没有向新 dot 调用模型、没有重复记账。保留暂停、已消费、错误资源归属的既有行为。

**R8 · P2：路由元数据写失败后，内存缓存阻止后续重试**

位置：[conversation-meta.ts:82](../../src/dingtalk/conversation-meta.ts#L82)。

`set` 先更新内存，再尝试落盘。写失败后，相同频道的相同元数据再次到达，会被 `sameMeta` 提前返回。当其他频道也没有元数据变化时，即使磁盘已经恢复，这条路由也不会落盘。

复现：暂时阻断 `state/dingtalk/` 的创建，调用 `set`；修复目录后用同一值再次调用，再重建 store：

```json
{
  "diskRecovered":true,
  "persistedAfterSecondSet":false,
  "presentInCurrentProcess":true,
  "presentAfterRestart":false
}
```

影响是当前聊天可用、重启后后台投递却找不到路由，故障与原因相隔较远。旧实现每次 `set` 都写，新实现增加的去重优化引入了这个恢复缺口。

建议把“内存内容相同”和“内容已成功持久化”分开：失败保留 dirty 状态，后续相同 `set` 也重试，成功才清除。还应明确集中式元数据文件损坏时的恢复策略；当前读取失败后缓存空表，下一条新消息会把该空表加单条记录写回，扩大原文件损坏的影响。

验收：扩展现有 metadata 持久化场景，验证故障解除后相同值会落盘，重建 store 能读取；不要只检查原 store 的缓存。

**R9 · P2：跨频道 corpus 使用目录顺序截断，造成检索盲区**

位置：[session-corpus.ts:329](../../src/memory/session-corpus.ts#L329)。

会话区按名字排序，先逐个读取固定的 context/log，再读取其他 session。累计文档超过 `maxDocuments * 2` 时停止，最后仅取末尾 `maxDocuments`。一个较早排序的会话区足以让后续频道完全不被读取；`maxFiles` 也只限制额外 session 文件，不限制每个会话区的三个固定文件。

实测：`dm-1/log.jsonl` 放 10,001 条文档；`group-1/log.jsonl` 只放一条较新的目标记录。使用默认 5,000 文档预算：

```json
{"returned":5000,"groupNeedleFound":false,"conversations":["dm-1"]}
```

这直接影响 D12 的“检索整个 dot”：未命中可能只是另一个频道耗尽了预算。多频道共享后，原有单频道截断方式的缺陷被放大。大文件还会在检查总量前整份读取、解析，最终结果上限没有约束读取峰值。

建议先明确预算语义：按实际时间的新近内容、频道公平份额或查询驱动扫描来分配，超限时返回扫描范围/截断提示。读取应有实际字节或文档预算，避免只在完成一个大文件后检查总量。时间比较需正确处理时区和缺失时间，不能依赖目录名顺序代表新近程度。

验收：扩展现有跨会话检索用例，加入不均衡历史量，断言后面频道的最新相关内容仍可检索，或明确返回未覆盖范围。保留全局资源上限，不能用取消预算修复漏检。

**R10 · P2：缺失的已绑定 dot 不会出现在 `/dot` 列表里**

位置：[registry.ts:98](../../src/dot/registry.ts#L98)、[commands.ts:50](../../src/dot/commands.ts#L50)。

`listDots` 只枚举磁盘上存在的目录；`buildDotList` 只遍历枚举结果，没有补入绑定表引用的缺失 dot。因此普通消息会说“本频道绑定的 dot 不可用”，`/dot` 却没有这个 dot 的行，甚至可能回复“暂无 dot”。

用绑定指向 `missing-dot`、磁盘只有其他 dot 的 fixture 验证，列表没有当前 dot，`currentRowFound=false`。这与 D4 明确保留“已绑定但不可用”状态的设计不一致。

建议列表使用“磁盘 dot 名 ∪ 绑定引用名”，为缺失项生成 `missing` 状态并显示绑定频道。生成诊断行不应创建目录。不可用原因可以留在部署者诊断中，用户文案继续遵守 053。

验收：扩展现有 list/registry 异常场景，覆盖目录被移走后的列表与当前标识；不必为每条文案新增测试。

**R11 · P2：模型工具协议仍把 dot 级列表描述成当前频道的工作**

位置：[subagent-manage.ts:67](../../src/tools/subagent-manage.ts#L67)、[subagent-manage.ts:139](../../src/tools/subagent-manage.ts#L139)、[job.ts:70](../../src/tools/job.ts#L70)、[record.ts:10](../../src/jobs/record.ts#L10)。

manager 已经按 dot 共享，`subagent_list` 和 `job list` 会返回其他频道的工作；描述仍是 “this channel's delegation runs” / “Completion wakes this channel”。run 列表/详情的模型可见文本没有标注发起频道；`JobSnapshot` 直接没有 `channelId`。虽然某些 run `details` 里有完整记录，项目契约明确规定模型读 `content`，不能依赖 `details` 补足模型知识。

因此频道 B 看到 A 的工作时，工具给了 B 一条不成立的等待承诺。可能诱导模型等待不会发到 B 的完成通知，或在缺乏来源判断时操作其他频道的工作。这里已确认协议与实现不一致；本次没有把模型可能误操作作为已复现事实。

建议：所有相关列表和 show 统一显示发起/投递频道，并区分当前频道、其他频道、当前未绑定的投递目标；工具描述改成 dot 级可见范围，明确唤醒回到发起频道。可继续保留 v1 允许同 dot 管理全部工作的能力，无需在此引入权限体系。用户命令 `/subagents` 也宜补上对应的来源标签。

验收：优先扩展现有内容结构检查；模型行为评测则覆盖“A 的工作在 B 可见，但 B 不应承诺等自己的唤醒”。避免只测试把 channel 一词替换成 dot。

**设计上建议进一步打磨的决策**

**A. 将“后台工作完成”“业务状态推进”“向频道投递”分别定义清楚。** D7/D8 与实施记录已经出现不同表述：任务整体冻结，但资源结算可兑现 work；完成唤醒可永久丢弃，但有的丢弃路径承担业务收尾。R7 是这种职责耦合的直接结果。建议用一张状态/副作用表统一生产端抑制、outbox 准入拒绝、投递失败、重复消费四种情况：资源结算和记账归 owner；任务只通过 `redeemTicket` 推进；频道投递是有绑定条件的独立动作。对需重试的收尾单独持久化事实，避免把“通知已处理”同时用作“业务已处理”。

**B. 保留 dot 的共享信任域，同时给共享事实增加适用主体。** 同 dot 的默认会话上下文分别维护，`session_search`、记忆、任务和工作文件则共享。用户文档宜明确这个共享范围。v1 不设 admins 是已确认取舍，本报告没有把“缺少 ACL”重新定为实现缺陷。值得本次修正的是归因：同一 dot 服务不同人、群时，“我是谁”“我的偏好”应带上主体，不能自然地覆盖为整个 dot 的统一身份。reflect 提示仍有 “this channel's durable memory” 和单一 “the user” 的措辞；记忆元数据只有 `source: user|agent|migrated`，不能说明来源主体。短期可在描述和 reflect 素材中保留明确的人/频道归属，禁止无主体地泛化个人偏好；结构化 provenance/scope 可另行演进，不必重建频道记忆目录。评测至少比较两个发言者的冲突偏好是否被正确区分。

**C. 调整 dot 内任务调度的吞吐与公平性。** 当前 [TaskDriver:413](../../src/runtime/task-driver.ts#L413) 每个 dot 一轮只选一个任务，默认全局预算是 4 次派发、最大睡眠 15 分钟。同一 dot 的多个空闲投递频道也只能先启动一个；若没有回合结束或其他来源 nudge，其余准备好的任务会等待下一轮，调度没有因为 ready backlog 安排立即续扫。以前“一频道一个候选”的粒度换成 dot 后，吞吐含义发生了变化。建议保留 dot 间轮转，同时允许在全局预算内向同 dot 的不同空闲频道派发；同频道仍受串行队列约束。有剩余可运行工作时安排短间隔续扫，绑定恢复后主动 nudge。将此作为明确的调度策略测试，避免为了吞吐取消公平性或制造忙循环。

**D. 缩短全局绑定事务占用时间，保留记忆事务的正确性。** [DotRuntime:242](../../src/runtime/dot-runtime.ts#L242) 的全局队列包住整个 bind，包括旧 runner 的 `dispose` 和可能触发的 reflect 模型调用。一个频道的慢 reflect 会阻塞所有频道的换绑。建议把绑定提交和必须串行的生命周期状态变化留在短事务，把旧 runner 清理按所属 dot 追踪并收尾；仍要保证该频道后续消息不会复用旧 runner。记忆方面，跨整个 reflect 持锁虽然可能让其他频道的 `memory_save` 等很久，但直接缩小锁范围会引入旧快照覆盖；本次宜先补等待可见性与取消/超时诊断。采用两阶段 reflect 需要另加版本校验和冲突重算协议。

**E. TUI 的后台能力需要显式呈现。** D13/D18 接受 TUI 不运行 task driver 和事件 watcher，且创建的工作投递到永不写入绑定表的 `tui`。因此这些工作即使 TUI 正在打开也不会自动推进。普通 `task_create` 成功结果和调度 playbook 没有表达这个限制。建议在 TUI 的能力上下文和创建结果中给出可执行下一步：从钉钉创建，或明确配置已绑定的投递目标；不要让用户把“已创建”理解为“已安排执行”。无需为此在 TUI 新建第二套后台服务。

**F. 删除 project 与旧安全配置的退役，应分别评估。** 删除 project 概念符合已确认方向；但 [security/config.ts](../../src/security/config.ts) 仅警告并忽略旧 `projectAccess`，会使原来显式采用项目边界的部署切换到 workspace/home/temp 默认范围。设计用本机“未配置此键”解释了本机不变，不能据此推出所有部署不变。公共发布前宜对非空旧配置拒绝静默扩权，给部署者转换规则或明确处理入口；本机确认无该配置时不受影响。此项是配置迁移策略建议，不要求恢复 `/project`。

**G. 明确运行中损坏、修复和注册缓存的契约。** `DotRuntime.resolve` 使用缓存的 dot record，TUI 可写 `dot.json`，`/dot list` 又直接读盘。目录或记录运行中改变时，列表、准入和检索来源标签可能看到不同代状态。建议确定哪些改动必须停 daemon，哪些可以刷新；即使暂不支持热修复，也应提供一致的诊断和重载方式。`bindingTable()` 返回的浅拷贝仍共享 binding 对象，当前调用方未修改它，适合用只读类型或深拷贝收紧内部边界，但这项无需单独新增单测。

**H. 清理 spec 的过期表述，避免验收互相矛盾。** 设计开头“明确不含”与 §6 仍有“多进程同时写同一个 dot”/“TUI 与 daemon 同时服务同一个 dot”的排除表述，而 D6、D18、决策记录和 INV-6 已允许这种共享。D20 又说迁移来的 TUI 任务“在 TUI 打开之前一直挂起”，实际打开后同样没有驱动器。建议以 D6/D18 的最终决策统一全文。`DotCommandContext.senderId` 目前只是未被调用方传入的占位，未来 admins 接入还需要传递真实 actor；本次可先让换绑日志记录操作者，增强可追溯性，不改变 v1 授权策略。

**建议的修复顺序与回归方式**

| 顺序 | 改动包 | 必须证明的结果 |
| --- | --- | --- |
| 1 | R1：统一唤醒准入与合并范围 | 合法结果能合并；旧 dot/无 dot 正文不进入请求 |
| 2 | R2：修正跨进程锁协议 | 多回收者下仍只有一个持有者；异常退出后可恢复 |
| 3 | R3/R4：绑定提交与 watcher 生命周期 | 未提交绑定不产生工作；停止后无新调度；重激活只执行一次 |
| 4 | R5/R6：迁移协议与停机前置条件 | 已 claim 的工作可恢复；活动 wrapper 未退出时零移动拒绝 |
| 5 | R7/R8：业务收尾与持久化重试 | 绑回后及时推进；磁盘恢复后路由能持久化 |
| 6 | R9/R10/R11 与本次选定的设计优化 | 跨频道检索范围可解释；异常绑定可见；模型理解来源与唤醒目标 |

修复应遵守既有模块归属：准入组合在 runtime；锁机制在 shared；watcher 取消和 drain 在 events；binding 提交顺序在 DotRuntime；任务恢复仍由 owner 验证并经 tasks 的状态接口；迁移协议留在独立脚本，不把旧布局兼容代码放回运行时。

单测优先扩展最接近的场景。迁移完整场景、DOT-3、wake-coalescing、跨会话检索、metadata 测试都有可扩展位置；R2 的多进程回收竞争和 R3/R4 的动态生命周期是独立故障模式，确有需要时可为其保留新的用例，并报告 case-count delta。e2e 只观察 provider 请求、持久化状态、调用次数和顺序，模型是否正确理解共享身份、来源与默认 cwd 则放在行为评测。

每个新增/扩展的机制用例要先定义目标 mutation，例如删除候选 dot 检查、取消 watcher 世代校验、漏改 claim id，再确认能变红。用可控 IPC、文件 I/O gate、provider hold 制造时序；不以随机压力测试或固定等待替代。

完成 runtime、memory、delegation、command-plane 修复后运行 `npm run check` 和 `npm run test:e2e`；改动评测框架时再运行 `npm run test:evals`。模型可见说明发生变化时，重新 plan 并执行受影响 dev probes，保留失败证据。

**评测与迁移验收仍需保留的边界**

实施记录保留了 12 个 dev probes 的首次失败、修正夹具后的 11/12，以及 M-extract-01 在同构建上追加三次通过的结果，这种保留失败证据的方式是有价值的。但 3/4 不能单凭重跑判为已证明没有提示词回归；没有配对基线时，“模型波动”应作为解释假设保留。后续模型行为验证应围绕多主体记忆、跨频道工作来源和默认工作目录，而不只是重复当前成功路径。

G6 中真实副本的完整迁移、`--verify`、恢复接管和 TUI 核对，实施记录已明确尚未完成，并由用户决定自行执行。本次审查没有代替用户实施真实迁移。R5/R6 修复后，应在用户选择的映射下完成一次副本演练；副本上的 daemon 保持不连接真实钉钉。`--verify` 应增加恢复状态关联和未完成迁移标记检查，避免“目录看起来正确”被当作“工作能够继续”。

达到可合入状态的建议条件是：R1–R6 均关闭，并有故障注入能使对应回归测试失败的证据；R7–R11 有修复或明确的版本处置记录；全文不变量与最终实现一致；检查全绿；模型行为和真实数据演练的未完成项如实保留。当前六项 P1 尚未修复，现有全绿结果不足以替代这些条件。
