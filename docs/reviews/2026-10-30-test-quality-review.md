## 成本与可靠性调整

- **记忆压缩准备数据**：同样的 150 条真实记忆一次批量写入；索引从重建 150 次减为一次，不缩小样本、不跳过真实压缩逻辑。
- **WebSocket**：真实 Fastify 协议处理器加真实 LiveResponse，服务端口代替完整 runtime。保留 32/33 边界、非法参数零准入、错误码、连接到期和取消；到期场景仍走真实 loopback WebSocket，并等待服务端 close，避免把客户端关闭误当作取消完成。真实 SDK、socket/TCP、steer、delivery 继续由原确定性 e2e 检查。
- **进度通知**：用真实同步文件内容/mtime 支撑可立即完成的异步 fs 端口；时钟推进能够完成一次 poll，不再靠每次 50ms 等待猜测 I/O。保留一次真实事件循环机会观察未处理的拒绝。
- **串行队列**：用进入/释放屏障替换延时长短竞争，明确检查同 key 阻塞和不同 key 能先完成。
- **进程接管**：保留真实 detached 进程、身份检查、持久 deadline、提前到达的 timer、真实 TERM/KILL、lease 和去重回执。只在此单测把真实 kill helper 的 grace 设为 10ms；host-process 仍负责终止机制，产品默认 5s 未改。删除依赖延时写标记的推断，等待真实 child exit 并检查进程组消失，随后才接受完成证明。
- **资源清理**：read/edit、FileStore、line-index、bash、frontmatter 和任务日志 fixture 真正删除自己分配的目录；job fixture 跟踪并停止 manager、清理 fake spill 分片。三套离线配置为每次运行分配独立 fallback app home，并在 global teardown 清理，避免不同 checkout 或后续运行共享陈旧状态。
- **Web API harness**：结束时等待 dispatcher 关闭，shutdown 出错也关闭 provider、恢复 offline 环境并清理 home。把最后一轮维护请求纳入 unmatched 检查，避免后台 502 被默默忽略。
- **运行池**：对同一份最终用例交错比较 forks / threads；threads 没有稳定收益，因此撤回该尝试，保留原默认 forks，不提高 worker 数。e2e 与评测工具链也保留原进程模型。

以下高成本覆盖保留：真正 SIGKILL 后的关闭/归档提交恢复、投递确认缺口、任务输入重放、外部进程接管、压缩边界反思恢复，以及唤醒失败重放。这些分别约束不同持久窗口，不能用同进程对象重建或一次普通问答替代。

## 故障变异与 live 控制

变异在独立副本进行，逐次恢复源码并核对内容；普通工作树未注入故障。最终十项均由目标用例检出，不把编译失败算作证据。

| 故障 | 失败证据 |
|---|---|
| read 越界改抛普通 Error | 原有分页用例的 RecoverableToolError 类型断言失败。 |
| 包装器不转换可恢复拒绝 | tool-details 的正常结果路径实际抛错。 |
| WebSocket 流上限改为允许第 33 路 | 完成 32 路后，返回错误码不再是 stream limit，协议断言失败。 |
| 放宽进度通知上限 | 实际收到 7 次通知，期望 6 次的断言失败。 |
| 同 key 队列不再等前序 | 第一项仍被屏障挂起时，第二、三项已经进入，顺序断言失败。 |
| 活动 session ref 写错 session id | 创建新会话的 ref/header 身份断言失败。 |
| 压缩使用普通删除上限 | 同样 150 条输入只删掉 3 条，压缩场景要求的 8 条断言失败。 |
| 未跟踪文件只记录名字/哈希长度 | 同名文件改内容后指纹仍相同，comparability 断言失败。 |
| 实际 TERM/KILL 改为 signal 0 | 进程仍活着，预期的持久完成回执未到达，20s 诊断等待失败；没有把状态变化当成进程退出。 |
| SDK 最终工具集误注入 job | 子代理真实 provider 请求包含 job，合并后的 e2e 断言失败；该变异另经完整 typecheck，编译通过。 |

两次尝试只放宽允许名单，仍被其他工具构造/角色约束挡住，没有形成预期的 provider 泄漏；保留其绿色记录，不计入上表的检出数。最终注入点位于 SDK 工具集赋值处，确实穿透到 provider 请求。初次 WebSocket 变异靠 watchdog 检出，随后将等待改成“32 路完成”，直接断言错误码，避免用超时充当主要证据。

三个修改过的 live 文件另做离线正反控制，未调用真实模型：

| 控制输入 | 旧测试 | 新测试 |
|---|---|---|
| 实际 desk 下错误出现 immediate 事件 | 通过（查了旧 workspace 路径） | 失败；正常不产生事件时通过 |
| 创建回复前任务已经正常归档 | 失败（强制 outcome 未设置） | 通过，继续核对归档日志 |
| 回复换一种合法措辞，实际答复已落盘 | 失败（强制包含“已经收到”） | 通过，核对实际交付内容落盘 |

这些控制只证明测试判定已修复，不是供应商兼容性或模型行为质量通过。生产 prompt、playbook、工具指导和评分器均未改，本轮没有新增付费探针，也没有覆盖之前评测证据。

## 验证与计时

基线与候选各顺序运行三轮；e2e / evals 包含各自的 pretest 构建。记录 npm 命令墙钟时间及整个子进程树累计 user+system CPU 秒，CPU 秒不是峰值内存。Node 22.21.0、Vitest 3.2.7、6 个可用 CPU，依赖相同。样本少且共享机器负载会变，范围和原始记录一并保留，不能把中位数差值解释成确定的加速比例。

首次把基线放在 `/tmp` 时，已有 playbook 守卫按设计拒绝该目录；该轮失败保留后，将基线和候选一起移到用户 cache 的同级目录重新计时，没有绕过守卫。探索性的 threads 三轮结果也保留：第二轮与一次 15s 聚焦验证重叠，且之后又合并文件、增强进程退出证明，因此全部探索单测样本不纳入最终单测统计；e2e 与 evals 没有该重叠，且之后只有单测与注释修改，三轮结果继续有效。

最终同配置单测三轮全部 964/964；确定性 e2e 三轮全部 70/70；评测工具链三轮全部 68/68，无 pending。最终单测另对同一候选交错运行 forks→threads / threads→forks，再补原默认配置一轮，保留全部数据。
