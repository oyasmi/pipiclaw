# 个人研发工作流的设计取舍

2026 年 10 月的设计聚焦审查讨论了如何在一个人的多个仓库和交互入口之间持续工作；11 月的深度审查沿这一方向补齐了落地缺口。这里记录有助于判断后续变更的边界，当前功能和操作入口见[架构文档](../architecture.md)与[用户文档](../README.md)。

## 工位、任务、频道与工作目录

| 问题 | 设计取舍 |
| --- | --- |
| 用户如何少搬运上下文？ | 工位积累项目记忆、任务、事件和文件。任务负责推进一项结果，聊天负责交办、纠偏和接管。聊天空闲时无需重复推进任务。 |
| 临时切换频道或工位时，工作和通知怎么办？ | 工位仍有有效后台工作时可继续推进。出站消息仍按工位和频道归属检查，原频道换绑时暂存，切回或显式接管后补发。个人助手保留任务相关的可见进度及失败通知；用户可以从消息找到对应任务。 |
| 如何避免不同工作污染同一个 checkout？ | 工位提供工作状态归属，checkout 是可被多个工位或执行者使用的写入资源。托管 worktree、写委派租约和核验读租约覆盖协作路径；shell 和外部 CLI 的实际权限仍由执行边界决定。并行改动时用独立工作树隔离真实文件，核验时核对工作树和版本。 |
| 交付后如何再利用结果？ | 历史检索已覆盖任务归档，长期记忆留给可复用的事实，精炼后的可复用流程可成为技能。已结束作业保留 7 天、已结算委派及管理产物保留 30 天，是对临时诊断和长期清理的固定窗口取舍。需长期引用的交付证据宜存入任务说明、报告或明确的工作文件。 |
| Web API 应支持多大范围？ | 以本地 TUI 和真实客户端所需的交互为界。新增客户端可沿现有传输契约接入，客户端特有的编解码和交互状态由客户端维护。 |

[Spec 065](../specs/065-personal-delivery-focus/design.md)记录固定保留期、保留通知、按能力分派和 Web API 范围的用户裁决。后续已落地的切换与治理细节分别见[任务与事件](../events-and-tasks.md)、[并发与容量](../scaling-and-concurrency.md)和[运行时恢复复盘](./runtime-recovery.md)。

## 仍值得研究的方向

- **受托守望。** 若真实需求反复要求捕捉某个确定的状态变化，可以在现有事件传感器上验证持久水位和带变化摘要的触发。先以历史记录观察命中和噪声，再判断是否推送。现有传感器覆盖的任务可作对照。详见[主动性设计调研](../refer/personal-agent-proactivity-design-notes.md)。
- **把重复排障变成技能。** 对已有验证产物并在多次任务中出现的过程，评估从归档生成候选技能的价值，用户可以核实后保存。验证它是否在新工作中减少重复探索，以及能否保留适用条件、输入和验收证据。
- **独立的移动端或语音客户端。** 只有具体工作流需要更好的交互时再利用现有 Web API 验证；语音可以先独立验证实时交互与复杂任务移交。详见[主动工作与实时语音调研](../refer/personal-agent-proactivity-and-voice.md)。
