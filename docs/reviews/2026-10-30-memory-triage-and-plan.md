# 记忆管理问题分诊与低复杂度修复方案

日期：2026-10-30。基线仍为 `e265956`；本轮复核代码并制定方案，没有修改运行逻辑。发现及原始验证见[深度审查报告](2026-10-30-memory-management-review.md)。本文件替代原报告中较宽泛的实施建议，原有缺陷证据保留。

三批实现及保留边界见 [2026-10-31 实施记录](2026-10-31-memory-implementation.md)。以下内容保留为实施前的取舍依据。

## 决策

**修复确定、局部且收益高的问题；给少数高影响问题增加保守保护；仅为正常长对话和会话切换补足已有机制。暂不建设完整事务、语义遗忘、事实溯源或新的检索系统。**

原报告把“影响可能很大”与“应该用较完整的机制解决”联系得过紧。影响等级不能直接决定实现规模。尤其应调整以下三点：

- R4 确认了失败后重复新增，没有证明项目需要为整个反思提供跨文件、跨模型重试的 exactly-once。先抑制完全相同内容的重复，保留失败后可能重跑的语义。
- R7 中常驻 `user/feedback` 超预算是现有取舍；workspace 前言未计预算是局部缺陷，应分开处理。
- R10 的 `expires` 当前是反思前的清理条件，尚不是读取 TTL。把它改成 TTL 会改变多处读语义，这次不做。

取舍的长期收益也要计入：新增持久状态、模型输出协议、恢复分支、配置项和测试矩阵，都会持续产生维护成本。以下方案优先复用现有数据、队列、锁、游标和待整理文件。

## 逐项分诊

成本是相对估算，包含实现和必要验证：S 为局部改动；M 为多个现有入口需要共同调整；L 为增加持久协议或明显扩大状态空间。没有生产频率统计，因此使用触发条件判断机会，不给问题编造概率或量化 ROI 分数。

## 第一批：局部修复，先取得确定收益

### 入口名称与文件范围：R1、R2

`memory/` 域统一使用已有 `isValidMemoryName`。`getMemoryEntryPath`、读取、删除、替换不能各自允许不同的名称规则。通用域拒绝非法名称，工具适配器把可自行纠正的参数错误转为 `RecoverableToolError`，命令返回中文原因和下一步，不把普通坏参数升级成用户必须处理的故障。

列举与单条读取使用 `lstat` 排除条目符号链接，避免名字合法但读到外部文件。这里不引入 realpath 缓存、递归目录扫描或新的沙箱。拥有同一 OS 账号的人恶意替换整个目录不属于专用记忆入口能提供的隔离保证；安全文档原有边界继续成立。

名称去重只改变字符串算法：按完整后缀长度给基础名称留位，去掉截短后可能留下的末尾连字符，再拼后缀。不能通过禁止 60 字符名称、截掉后缀、减少可用名称或添加另一个随机名称格式来绕开现有契约。

### 显式保存与自动写入的一致语义：R5、R6

采用现有 `source` 字段，不新增 `confirmedBy`、所有者、证据列表或多层权威模型。显式 `memory_save` 替换后设置 `source: user`、清除观察期，保留原 `created`、更新 `updated`。这把 `source` 明确为当前事实的保存来源，而非永不变化的首次发现来源。

内部 update 操作可以携带显式来源，只有用户保存适配器构造该来源；反思模型的输出 schema 不增加可提升权限的字段。自动更新原本就是 `source: user` 的条目时，**不能因为目标的 source 是 user，就误认为这次操作获得了重新授权**。

在 store 的内容写入处统一检查归一化 description 的墓碑：自动 add/update 都服从阻挡；显式保存的 add/update 只有在成功写入后才撤销对应阻挡。复用已有哈希，不做近似相似度封禁。保留当前“遗忘不会抹去 journal 与原始会话”的产品边界。

### 背景搜索与 workspace 裁剪：R9、R7 的局部部分

搜索继续使用现有词法打分。将前言作为一个文本块，无 H2 时检索全文，H2 块用“标题 + 正文”参与匹配，避免增加新的索引或检索服务。逻辑放在 memory 域；除非其他调用者也需要相同语义，不改全局 `splitH2Sections` 的行为。

workspace 裁剪把前言和省略提示一起纳入 units/chars 上限；普通 H2 段落继续整段保留，超大前言使用已有裁剪函数和可行动的读取指引。不要对最终文本直接一刀截断，把普通段落、路径或省略指引切成半句。

这批不顺带改 `user/feedback` 的优先策略，不新增保存长度配置，也不引入按模型动态调预算。修改涉及常规排版或省略提示时，测试验证范围与预算，不钉字面文案。

## 第二批：局部保护，接受有界的不完美

### R4：抑制精确重放，暂不提供整个反思事务

自动 `add` 在分配名称前比对已有事实和本批已接受的事实。只有归一化后的 description、实际 type、规范化边界后的完整正文都一致，才视为重复并跳过；正文不能仅做有损哈希或模糊匹配后覆盖。复用现有读取和内容归一化，不新增持久化指纹。

自动重复不能修改已有用户条目的 source、正文、日期或观察期，也不能冒充新的 `touch` 证据。description 相同但 details 不同，不按精确重复丢弃。显式 `replaces: "none"` 继续表达有意并存，不把后台去重强加到该入口。

审计日志与业务提交分开：游标成功提交后，审计失败只记固定事件 warning；不能把已经提交的业务当成反思失败重新执行。边界工作同样避免因为非关键审计写入失败而迟迟不提交处理进度。journal 失败仍保持窗口可重试，不能靠提前推进游标来消灭重复。

**验收只承诺相同内容不会因自动重放而继续生出 `-2/-3`。** 不承诺模型换一种说法时能去重，不承诺多个文件同时生效，也不承诺同一输入绝不再次调用模型。原报告的 R4 因而应标为“缓解、仍有残余风险”，不能关闭成“事务问题已解决”。

不为这件事新增写前日志、物化模型操作计划、事务目录、版本链、回滚机制或每条操作的收据。故障后变体重复、部分成功仍可能发生；原始会话和事实文件可用于排查与人工修复。这是本阶段明确接受的代价。

### R8：少执行一次自动删除，优于建立替代依赖协议

继续保留模型现有 `add/update/delete/touch` 输出。采用一次反思内的保守顺序：

1. 完成现有策略检查；任何新增/更新被拒绝，就取消本次全部自动删除，不猜哪些删除与它有关。
2. 先应用已接受的新增、更新和 touch。store 仍可能因墓碑、密钥或缺失目标跳过内容写入；此时也取消本次自动删除。
3. 只有内容写入全部通过且实际完成，才应用获准删除；写入中抛出 I/O 错误时自然不能走到删除步骤。
4. 审查日志记录取消删除的原因。显式 `memory_forget` 和 `/memory forget` 继续正常工作。

对同批“更新目标随后又删除该目标”等冲突操作做简单目标集合检查，不能声称这种输出完成了保真合并。精确重复的自动 add 已等价存在时，可作为已满足，不让 R4 的去重永远阻止清理。

可以调用现有 store 两次完成两阶段应用，即使多生成一次索引也可接受；不用为避免这次小规模文件工作引入通用事务框架。代价是某个无关 add 被拒时，合法的过期删除也会延后。对于几十至几百条的记忆规模，这比永久丢事实更划算。

这不保证模型提出的合并语义一定正确，也不保证删除阶段中途故障能整体回滚。它只消除“已知替代写入失败，旧内容仍照删”的确定性问题。原报告建议的 replacement 图、依赖操作组和新模型协议暂不实施。

### 顺手完成的可观测性边界

仅随上述代码改动补齐必要诊断：拒绝和自动删除的原因、因部分写入取消的删除、非关键审计失败；journal 的模型输出复用已有 `redactSecrets`。不额外保存模型拒绝候选全文、不做全量日志重放或历史内容清理，不新建一个指标平台。

## 第三批：只保留一项适度的机制调整

### R3：用现有 entry 游标处理正常长窗口

原先 50,000 字符单条用户消息的探针证明了函数问题，但不能直接证明日常入口会接收这种消息：当前用户输入上限是 12,000 字符。本轮补查了正常多消息情形：8 条用户/助手消息，最长用户消息 7,027 字符，序列化后 56,949 字符，中段唯一事实同样被裁掉。这支持优先修复多轮累积路径，没有生产发生率结论。

建议在 `source-window.ts` 中选择**未处理范围中最早、连续、预算内的完整交流前缀**，而非在 reflect 内对整个历史取头尾。依据清洗后实际序列化大小决定预算，避免把工具结果、bootstrap 或 thinking 的体积与真正发送文本混淆。

正常路径遵守以下约束：

- 一批以完整的用户交流边界收束；不能把用户事实单独切出后，因本批没有助手文本而当成“无实质交流”跳过。纯工具/元数据可按已有策略处理，含文本的孤立用户输入需要保留待处理。
- `throughEntryId` 指向这批实际处理的末端；未选入的后缀不提交。下一次从该 entry 后继续，不新增字节偏移字段。
- idle 每次调度最多处理一批，避免长时间持锁或突发无限模型调用。`lastReflectAt` 在本次增量全部完成后才刷新，使未完成批次可在后续 tick 继续，不必每小批再等 20 分钟；文档明确该时间表示最近一次完成整理的时间。
- lifecycle 不把只处理一批当成整个 durable revision 已完成；压缩及 `/new` 的待整理文件在全部 entry 处理完之前保留。关闭时只做有界尝试，剩余源数据或已有工作继续可恢复。
- 三类调用者使用同一选窗逻辑，不把分批算法复制到 idle、lifecycle、boundary 三处；共享原有工位队列和文件锁。

还有一个不能省略的顺序约束：维护状态对一个 conversation 只有一个 `lastReflectedEntryId`。旧待整理文件尚未完成时，新的 idle 或 shutdown 反思不能先推进到新 session 的 entry，再让旧文件据此寻找进度；旧 entry 集合里没有这个 id，会导致旧批次重头处理。后台处理应按同 conversation 的工作顺序进行，旧边界工作未完成则本次不执行新的直接反思；活跃聊天仍正常进行。这个约束复用现有队列即可，不为解决它引入每 session 的第二组游标。

**单个完整交流本身超出预算暂不做持久化细分。** 保留现有采样作为例外，并在已有审查日志中明确记录源范围、原始大小和存在省略，不能把这种样本报告为完整覆盖。它仍可能错过中段事实；R3 的这部分保持开放。不能用“不推进游标且永远重试相同超大输入”代替处理，以免堵住后面的所有记忆。

持久化字符偏移、每条消息分片 id、续传和跨分片语义拼接的复杂度目前不值。需要这些能力的证据应来自真实场景，不能只靠一个可构造的最大输入。

### R11：让 `/new` 复用现有 `.memory-work`

冷热 `/new` 都在切换 active 指针前，读取旧会话的持久化分支并保存待整理范围。优先使用同步可取得的已就绪快照；没有 runner 时用轻量 session 读取，不能为了整理创建完整 runner、解析模型凭据或等待会话初始化。

把 `enqueueBoundaryReflectWork` 中“保存指定 entries”的小段提取为 memory 域内的共同函数，压缩入口只负责选择被压缩的前缀，`/new` 保存旧会话尚未整理的范围。沿用现有工作文件字段、内容哈希 id、`.done` 与恢复调度，不增加第二套任务目录或 marker。旧的 new-session 内存 Promise 反思路径应被替代，不能新旧两套同时执行。

只等待本地快照写入，不等待工位记忆锁、模型调用、旧频道队列、`ensureSessionReady` 或卡住的 compaction。保存失败时不提交新的 active 指针；旧会话尚未被切走，用户收到可重试的本地存储错误。保存成功而随后新会话创建失败时，额外整理一个仍活跃的旧快照也可接受，不需要撤销协议。

原会话指针仍须在新 session 文件落盘后提交；旧 runner 仍在成功切换后退休。为原 generation 加一套“冻结—提交—解冻”事务不是本次目标；快照末端之后尚未完成或被停止的输出不纳入“已完成旧交流全部保存”的保证。

这两个问题一起评审，是为了只维护一份预算选窗规则和一套已有边界工作。**不是要求第一批局部修复等待它们完成。** 如果实现开始要求修改 session 文件格式、引入独立调度器或通用恢复框架，说明方案越界，应先交付前两批并收窄第三批。

| 暂缓项 | 当前不划算的原因 | 值得重新投入的证据 |
| --- | --- | --- |
| R4 完整事务与模型输出重放 | 新增持久协议、恢复分支和故障矩阵；现有复现主要是变成重复记录 | 轻量保护后仍出现实际不可接受的部分提交、重复或恢复事故；不能只因“理论上还存在”重开 |

| 结构化所有者、证据链、用户确认模型 | 增加模型输出与存储字段，仍无法仅靠引用证明事实为真 | 多人共用工位下出现可重复的归属错误；先用现有 eval 验证提示与事实描述的不足 |
| 活跃会话 revision / 失效摘要 | 改变每回合注入和缓存；删除文件仍不等于抹掉模型历史 | 跨频道纠正后继续误用旧索引成为经常性问题 |
| 锁外推理与版本校验 | 用版本竞争、重算和取消逻辑换取低延迟，增加并发状态空间 | 真实显式保存/遗忘等待已影响使用；先区分模型耗时与队列积压 |
| 历史搜索日期分页、向量检索、重排 | 日期过滤可能有用，但不是这次确定性缺陷的必要修复；向量服务成本更高 | 真实查询频繁落在扫描范围外，或修复 R9 后词法改述仍明显不足 |
| 断电级墓碑事务、长期压缩/GC、自动迁移 | 尚无故障或容量证据，误删防重放记录反而可能出错 | 实际持久性目标、体积或运维问题；按独立问题设计，不顺带实施 |

暂缓不表示这些问题不存在。R4 全面一致性、R3 超大交流中段覆盖、R7 常驻索引硬上限均有明确残余风险；对外不能宣称它们已完全解决。R10 维持现状时，在 `docs/memory.md` 明确“观察期到期后，在下一次反思前清理”，不承诺精确墙钟失效。

## 复杂度预算与实施停止线

本轮允许新增小的内存计算和函数返回值，修改内部操作类型，以及复用现有文件；不新增持久化字段、目录种类、依赖、后台服务、配置开关、模型权限字段或兼容读取路径。必要的类型或函数拆分放进原有 domain，不为满足形式上的行数目标创建通用框架。

新增的确定性规则应能直接说清楚：名称合法、后缀留位、显式保存提升来源、自动写入服从精确遗忘、精确重复不再新增、替代写入失败则不自动删、游标不跨过未选入的正常交流。这些规则不需要一个可配置的策略引擎。

`.memory-work` 的写入数量会因 `/new` 增加，但这是已有状态生命周期的复用。它仍是运行时素材快照，不承诺分布式队列语义，也不变成另一份记忆数据库。

实施中如果发现必须增加长期持久协议才能完成某项，就把该项从“局部修”改为“部分修/暂缓”，保留证据和残余风险，不以完成整张审查清单为理由扩大范围。

## 验证与交付顺序

| 批次 | 验证重点 | 交付边界 |
| --- | --- | --- |
| A：R1/R2/R5/R6/R9 与 workspace 预算 | 实际命令拒绝越界、最大名称算法终止、替换后用户保护、update 阻挡与重新授权、背景正文可检索、最终预算 | 可独立合并；不等后续恢复机制 |
| B：R4 有限缓解、R8 保守保护 | journal 故障后相同内容不重复；相同描述不同正文不误删；store 拒绝或写入失败时原事实仍在；合法独立删除仍可执行 | 明确标注 R4 未完全关闭；不宣称事务原子性 |
| C：R3 正常窗口、R11 边界复用 | 多轮中段事实实际送达 provider、每批游标连续、孤立用户输入不被跳过、冷热 `/new` 持久化与恢复、被阻塞旧 runner 不拖住切换 | 保留单交流采样边界；不宣称单轮超大内容完整覆盖 |

优先扩展现有 `memory-store`、`memory-manage`、`memory-search`、`memory-reflect`、`memory-reflect-job`、`memory-lifecycle` 和 e2e memory/compaction 链。unit 中验证完整输入矩阵，e2e 只证明真实入口、故障恢复、provider 输入和磁盘副作用，不重复矩阵，也不测模型措辞。

名称死循环的回归验证必须可由独立进程终止；崩溃恢复使用独立 daemon，不能把同进程 restart 当作 SIGKILL 证据。确需增加永久 case 时按仓库规则说明既有覆盖为何不足、报告数量变化并做 mutation check；不能为追求零增长把无关风险硬塞进同一个 scenario。

每批产品变更运行 `npm run typecheck`、`npm run arch`、`npm run test`、`npm run test:e2e`。R8 的保守删除与 R3 的分批会影响行为，实施时先计划相关 eval，完成可执行控制检查，再用可用的本地配置模型定向运行，记录 run id 与失败归因；没有执行就不判质量通过。优先复用 `M-extract-01`、`M-overflow-01`、`M-correction-01` 及合并/遗忘相关场景，新增场景须证明既有探针未覆盖。

本轮只是分诊方案，未执行上述修复，也未重跑上一轮完整测试或真实模型评测。新增证据仅为正常尺寸多消息的序列化/裁剪验证，不涉及生产数据或模型调用。
