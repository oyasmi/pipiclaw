# 2026-10-30：围绕工位与任务的设计聚焦审查

审查对象：`69acd35` 及当前工作树，包含尚未提交的任务交付、归档恢复和未知费用修复。本文只新增审查意见，不修改运行机制，不改变已经接受的权限或隔离边界。

> **用户裁决（2026-10-30）**：采纳 R1；不采纳 R2，任务进度、失败等频道通知保留，产品没有另一名人类负责人承担这些通知。R3 采用固定窗口调整：作业记录与输出由 24 小时延长到 7 天，委派记录与运行时管理产物由 7 天延长到 30 天，不实施本文提出的引用保护或证据转存协议。边界问题本轮暂缓，`subagent_inline` 保留默认暴露；推进完整交付的委派教学、Web API 范围和个人研发产品定位。具体范围、做法与验收以 [spec 065](../specs/065-personal-delivery-focus/design.md) 为准；下文保留原审查分析，不作为未经裁决的实施清单。

## 判断

desk 与 task lane 的价值，在于把工作的连续性从对话中拿了出来：**工位保存一组工作的积累，任务负责一项结果的推进，频道提供交办和接管入口。** 这是适合个人长期使用的结构，应当继续巩固。

接下来的重点应从“让更多机制可以工作”，转向“让用户少解释、少追赶、少处理机制本身”。最值得投入的不是再增加一种自动化，而是三个闭环：

- **交办闭环**：说清结果后，任务独立推进；用户无需在聊天与执行者之间搬运上下文。
- **接管闭环**：知道什么在发生、哪里需要决定，换入口后仍能找到和接管工作。
- **积累闭环**：过几天仍能找到产物、复核证据，下一项相似工作能利用已验证的积累。

当前代码对第一个闭环已有比较扎实的支撑；第二个仍受原频道和底层通知牵制；第三个的证据保留与发现入口还没有完全跟上任务的重要性。

本文将**代码可确认的残留**、**现有设计的取舍**与**需要使用证据才能决定的删减**分别标明。没有把静态推演冒充真实部署事故，也不以文件数或代码行数证明某个功能应该删除。

## 一、产品的中心应当进一步明确

建议以这句话约束后续设计：

> Pipiclaw 帮助一个人，把目标持续转化为有证据、可接续的交付；钉钉和终端让这个人随时交办、查看与接管，执行器利用他已经拥有的模型和算力资源。

这会带来几个具体取舍。

**用户的主要对象是任务与产物。** run、job、step 和 session 是完成工作的机制，遇到问题时可以展开查看，平时不应成为用户必须管理的一支“组织”。

**工位是一段稳定的工作积累。** 默认工位降低入门门槛，其他工位按需建立。它不必演化成带人格、角色、模型策略和权限继承的第二套部署单位。

**任务负责人可以自己做，也可以委派。** 创建任务的理由是需要持续推进，而非必须组建团队。一次等待、一个持续调查也可以成为任务，不必为了证明“有团队”拆出多个岗位。当前 `items` 已经可选，应该保留这种简单性。

**杠杆应按完整交付衡量。** token、并发 run 数和工作项数量只是投入与活动。对个人更有意义的是：完成一项可用成果需要多少主动关注、重复解释和返工。订阅执行器的费用未知时，也不能用已知美元小计代替全部资源消耗。

这些并非重建理念；[现有设计哲学](../design-philosophy.md)与[交付成本的讨论](../leverage/004-token-to-productivity.md)已有基础。建议让默认行为和介绍文字更一致地服务于它们。

## 二、应优先处理的具体残留

### R1：聊天仍收到“空闲时推进任务”的旧指令

**性质：明确的模型指导冲突；修复成本低。**

[`buildTaskDigest`](../../src/agent/turn/task-digest.ts) 在每轮聊天的任务议程中仍写着：用户消息涉及任务，**或者本轮没有别的事做时**，可以行动。与此同时，[负责人手册](../../src/playbooks/task-lead.md)明确要求聊天只管理、转达，不替任务执行。

这不是说任务已经实际重复运行，而是模型同时收到了两种行动方向。聊天还拥有普通文件工具，旧指令可能使它读取、修改任务说明，或替后台负责人做实施与检查，重新出现两个推进者。

**建议**：议程保留为识别用户所指任务、展示待答问题的背景。去掉空闲时主动推进的授权；任务相关行动明确落到查看、转达、暂停、恢复和取消。用户要改变工作，由聊天将要求送入任务，由任务执行。

**验收**：在任务正在执行、聊天收到无关请求或简单确认时，聊天不替它编辑说明、实施代码或关闭任务。优先改写已有行为场景，不为一句文案新增字符串断言。

### R2：任务已经接管委派，底层通知仍直接打扰用户

**性质：明确存在的旧通知路径；默认体验与新分工不一致。**

[`SubAgentRunManager.emitNotice/announce`](../../src/subagents/runs.ts) 仍把任务内委派的进度、卡顿和完成通知送到频道；`announce` 在判断是否回到任务之前就发送完成通知。[默认配置](../../src/config/settings.ts)为 `delegation.notices: live`，[bootstrap](../../src/runtime/bootstrap.ts)只按通知等级过滤，没有区分任务内委派与聊天临时委派。[通知正文](../../src/subagents/commands.ts)以 run id 为中心。

因此，一个由负责人正常处理的失败或十分钟安静，也可能直接要求用户检查、取消执行者。用户已经把项目交给负责人，却又被拉回底层调度。`SILENT_CONTEXT` 只屏蔽任务回合输出，不能屏蔽这条带外通知路径。

**建议**：保留 run 的状态、产物、卡顿检测和对任务的通知；任务内普通执行动态默认交给负责人处理，在 `/tasks show` 与 `/subagents` 中按需查看。聊天直接发起的临时委派维持可见回执。任务需要决定、负责人无法继续或运行时自身故障时，发任务级通知。

任务与运行时同时无法正常处理故障时，仍要有确定性的告警，不能把所有故障都藏到沉默的负责人后面。无需增加一套复杂通知偏好，先按现有 `taskId` 区分通知受众。

**验收**：任务内部一次失败、返工、再次完成，不要求用户逐个管理 run；任务被暂停或需要用户决定时仍及时通知，并能通过任务 id 行动。

### R3：任务的寿命已变长，所引用证据的寿命仍按临时执行设计

**性质：代码可确认的保留策略缺口；尚未在真实部署注入复现。**

任务可以无期限等用户，也可以长期暂停。结算时，[委派](../../src/subagents/task-settlement.ts)和[作业](../../src/jobs/manager.ts)向任务记录写入输出路径及尾部摘要。但是：

- 作业结束 24 小时后会清理输出；条件只要求已向任务记下结算，不要求负责人已消费并保存必要证据。
- 委派结算 7 天后会清理运行时管理的产物，包括 `output.md`；条件同样只要求任务已记账。
- 任务记录中的路径不是输出的完整副本。委派另有有界历史摘要，执行者自行创建的其他文件也不一定清理，但这不能保证原始证据完整存在。

可推演的用户路径是：任务提问后，执行者返回较长结果；用户过几天才回答，负责人恢复时拿到了结算记录，却读不到完整输出。任务本身成功恢复，不等于工作能完整接续。

**建议**：把临时执行诊断与任务接续所需证据分开。先采用最小策略：活动任务仍需要的结果不因 run/job 的固定 TTL 自动消失；任务结束前，把交付与验收依赖的必要输出保存到本任务的持久产物位置，再允许清理临时输出。不要无限保留全部 stdout、events 和进程日志，也不必新建通用产物服务。

这里应明确“记账完成”“负责人已处理”“必要证据已保存”是不同事实。不能仅用 `taskAccounted` 或 `taskLogged` 推断后两者。

**验收**：扩展现有保留期测试，覆盖任务等待用户超过 TTL 后恢复、完整输出仍可获取的路径；任务结束后的临时诊断仍能回收。跨模块机制用确定性时钟证明，不等待真实天数。

## 三、沿 desk 与 task 方向继续前进的设计问题

### D1：工作归属已经独立，继续工作的资格仍绑定原频道

**性质：明确、合理但现在需要复审的设计取舍。**

[`isFrozen`](../../src/runtime/task-control.ts)要求任务的报告频道仍绑定原工位、对应 transport 仍开启。[工位运行时](../../src/runtime/desk-runtime.ts)的激活与休眠也由绑定决定。任务的投递频道创建后不可修改，当前管理面没有接管投递地址的入口。

例如，从钉钉交办项目后将该群切到另一个工位；即使终端仍打开原工位，原项目也不会因为有人可以管理它就恢复执行。用户换了交互入口，却间接改变了工作的存活条件。

冻结有重要价值：防止把旧工位的内容发到已经换用途的对话。**不建议直接删掉绑定检查或自动把消息转给另一个频道。**

**最小改进**：先提供同工位内显式接管任务投递地址的能力，并让冻结说明直接给出恢复路径。接管时重新验证目标频道、适用权限和待发送消息，确保旧问题、旧报告不会误投；具体命令形状另行设计。现有冻结默认可以继续保留。

只有真实使用证明“换入口导致停工”频繁发生，再考虑让工位有独立于绑定的运行意图。不要一次加入默认主频道、订阅列表、自动故障转移和路由规则。

**验收目标**：用户能在仍有权管理该工位的另一个入口接续项目，无需删除重建任务，也不需要把旧频道重新切回去；切换不会泄露或重复执行旧工作。

### D2：后台独立之后，代码目录的写入归属更重要

**性质：已有明确边界，不是新发现的安全漏洞；新并发模型提高了它的出现频率。**

当前每工位可以有三个执行中的任务，聊天也可同时工作。[委派写租约](../../src/subagents/workspace-lease.ts)保护声明为写的 run，明确不覆盖主 agent 的 `write/edit/bash`；多个任务负责人属于后者。不同工位也可能配置相同的实际 cwd。[并发文档](../scaling-and-concurrency.md)已经如实说明。

过去主要是多个频道同时写，现在一个用户在一个频道里交办两件事，就可能制造共享 checkout 的并发写入。进度、测试和最终 diff 可能混入另一项工作的结果，抵消并行带来的收益。

**建议的方向**：为个人默认路径形成可理解的约定——一棵可写 checkout 同一时间由一项工作负责；需要并行实现时使用明确的独立 worktree。工位是积累范围，checkout 是写入资源，不能把工位并发数当成目录写入安全。

先收敛标准工作流：任务执行期间，聊天对同一项目的变更交给该任务；第二项写工作等待或明确使用另一目录。若以使用证据推进代码保护，应按逻辑任务识别负责人，并让它派出的执行者沿用归属；不能给负责人和子执行者各加一把互斥锁，造成自锁。

不主张在这一轮实现通用 shell 写入分析、文件事务或自动 worktree 合并。这些都无法用很小的机制成本覆盖任意外部 CLI。约定能降低冲突，却不是物理隔离；效果需要用实际并行编码样本验证。

### D3：任务已成为生产中心，成果发现仍偏向聊天

**性质：结构性缺口；不等于应让任务自动写记忆。**

[`ChannelRunner`](../../src/agent/channel-runner.ts)只给 chat 启用记忆生命周期与维护活动记录；[`session_search` 的语料](../../src/memory/session-corpus.ts)枚举 `conversations/`，不包含 `tasks/.sessions/`。[任务工具集](../../src/tools/index.ts)排除 `memory_save`。这些限制有明确好处：避免把任务中的试探和临时结论变成长期事实。

代价是：任务越安静地在后台完成，聊天里留下的工作证据越少。最终报告可能存在于频道或任务记录中，但“上周那个迁移为什么这样做”的完整依据，不能指望仅靠聊天搜索找到。

**先解决发现，再考虑学习**：任务说明、最终交付、必要证据和归档记录仍为真相源。已知 id 用现有 `task_log`；未知 id 时，先补足归档任务按目标和标题发现的路径，复用现有任务文件与文件搜索，不急于把全部任务会话混入记忆语料或建立向量库。

对于确实跨任务复用的经验，先比较人工指定保存与现有聊天反思的效果。如果重复解释仍显著，再尝试一次有界的任务收尾摘要作为现有反思流程的候选输入。只保留结果、适用范围和证据，不自动学习失败尝试，不把执行者自述当用户偏好，也不自动上升为全工位规则。

周期任务已有 `previous_occurrence`，应继续利用，不再造第二套周期学习机制。

### D4：工位的状态组织很简洁，连接真实项目的路径还不够直接

**性质：面向程序员的入门摩擦。**

[`DeskRecord.cwd`](../../src/desk/types.ts)已经支持外部绝对目录，但声明为手工编辑；[`/desk`](../../src/desk/commands.ts)只有 list/new/bind。普通用户可以在对话里使用仓库绝对路径，但要把工位长期关联到项目，仍需了解状态目录与 cwd 的区别、编辑服务器文件并理解生效时机。

**建议**：在现有工位管理入口中完成一次明确的项目目录设置与展示，提供清楚的生效边界；不要引入另一种 project 对象。设置前检查目录、正在执行的工作以及与其他工位共享的情况，避免悄悄改变在途任务的 cwd。保留默认工位即可聊天的路径，不要求人人先建工位。

价值是让新用户更快得到第一项真实代码交付。优先级高于角色市场、可视化流程编辑器或更多 transport。

## 四、应收起、冻结或有条件删除的能力

| 对象 | 判断与建议 | 证据与限制 |
| --- | --- | --- |
| `subagent_inline` 默认暴露 | **优先从默认路径收起，保留为显式高级能力；取得使用证据后再决定删除** | [工具](../../src/tools/subagent.ts)要求模型临时选择 system prompt、工具、模型、effort、context、thinking 和 mutates；[开关](../../src/config/tools.ts)却默认开。已经配置通用执行角色时，它增加第二套配置决策与模式选择。尚无使用统计，不能断言没有独特价值；收起前须保证首次委派或无角色场景有合理路径。 |
| 角色的上下文配置与分类 | **下次修改时收窄，不急于重写配置格式** | [`contextMode` 与 `memory`](../../src/subagents/discovery.ts)有组合规则，内外执行器默认不同；`workload` 主要进入[提示目录分组](../../src/agent/prompt/sections.ts)，不是调度预算。若 description 已足以选择能力，弱分类可删；上下文应只表达实际注入内容，保留外部角色默认不传记忆的边界。不要为了统一字段丢掉 `paths` 等现有有效用法。 |
| “每个阶段一个岗位”的团队用法 | **从默认教学与示例推荐中退出；已有收敛方向应继续** | [现有 leverage 文档](../leverage/005-fewer-roles-better-handoffs.md)已经主张完整交付和少交接。建议继续按能力、成本和执行边界选少数角色；planner → builder → reviewer → verifier → writer 不应成为固定流水线。独立检查按风险发生，`VERDICT` 继续只是判断材料。 |
| Web API 的通用模型服务方向 | **保留 TUI 所需的服务端与会话能力，冻结追求协议完整性的扩张** | [Web API](../webapi.md)同时支持显式会话、独立请求和 `previous_response_id` 等上下文路径；[`requestTools`](../../src/agent/session/request-tools.ts)已需要另一套可用能力规则。SDK 可接入有价值，但不是每一个上游字段都值得实现。先明确支持子集；只有真实消费者需求才能推进扩展。不能因审查“聚焦”就直接删除近期明确实现的 API 能力或破坏现有客户端。 |
| “个人与团队平台”的产品叙事 | **让个人研发工作成为介绍与默认场景的中心，保留小团队共享使用** | [README](../../README.md)仍以个人和团队、工程团队分工展开；[容量文档](../scaling-and-concurrency.md)花篇幅讨论多群、多用户容量。结合用户本次明确定位，团队应是共同使用一个助手的场景，不成为组织权限、租户、审批和企业工作流的平台目标。当前所需鉴权和隔离不能因此削弱。 |
| 继续增加 playbook 条款 | **冻结无证据的规则增长，优先删重复和过期动作** | 本轮实测 task-lead 2,993 units，delegation 2,390，合计 5,383；所有手册 10,683。它们按需加载，units 不是账单 token，不能据此宣称每轮花费；但负责人要同时理解两份长协议。先用已有失败样本找必须保留的分支，将确定性事实留给工具和 brief，不以任意字数达标为目标。 |
| token 节省的局部优化 | **作为有测量支持的小适配器维护，避免升级为主线** | [rtk 适配](../../src/tools/command-optimizer.ts)默认关闭，边界目前较小。其价值应看完整任务是否少返工、少重读，而非输出短了多少。保留已有可选能力即可，不值得为此建立通用命令重写框架。 |

“收起”与“删除”不同。收起默认入口可以先减少用户和模型的选择成本；删除实现还需要确认真实用法与替代路径。不能用再加一个配置层来完成所谓简化。

## 五、不应为了变小而删掉的机制

以下复杂度直接换来可持续委托，属于主线：

- **任务日志、输入确认、结算幂等、关闭恢复和投递重试。** 当前工作树已经补上最终报告送达确认、归档中断恢复与未知费用表示，应保留这些成果；不能重新把“关闭”降成一次文件移动，也不能把已知成本冒充全部成本。
- **运行时推导状态和真实等待来源。** 不恢复模型声明 waiting、不增加层层审批或 PASS 门禁；运行时守机制事实，负责人判断成果。
- **task、run 与 job 的内部区别。** 项目、执行者和进程的生命周期不同。用户入口以任务为中心，不意味着底层必须合成一个万能 Work 对象。
- **事件生成独立任务实例，以及零 token 的条件检查。** 事件回答何时发生，任务负责一次结果；提醒和有状态工作继续区分，不把 cron 塞回任务。
- **直接聊天与临时委派。** 简单工作无需建项目。不要为了统一追踪，把所有动作都强制变成 task。
- **记忆的来源保护、遗忘与反思边界。** 可简化展示和重复指导，不能把它退化成任意历史自动写入的大文件。
- **本地 daemon、TUI 客户端和 transport 边界。** 这是多入口共享工作状态的支撑；不需要为削代码回到终端内另一套独立 runtime。
- **架构约束、确定性恢复测试和可追溯行为评测。** 不为“轻”而删除验证；但优先改写已有低价值场景，避免测试和评测变成与产品同等庞大的第二个目标。

当前的复杂度主要集中在持续执行与恢复，不应把整个系统简单归类为“过度设计”。应删的是过期行动权、重复选择面和暴露给用户的机制管理负担。

## 六、建议的实施顺序

| 顺序 | 范围 | 做到什么就停止 |
| --- | --- | --- |
| 1：修正现有主线 | R1 议程行动权、R2 任务内通知、R3 结果保留 | 一个任务只有一个推进者；用户关注任务级决定；长期等待后仍有必要证据。各自独立改动，避免捆成一次新架构。 |
| 2：改善接管与交办 | D1 同工位显式接管投递；D4 项目目录设置；D2 同 checkout 的标准工作流 | 换入口能接续工作；新用户能把任务放到目标仓库；不让两个负责人默认同时改一棵树。先解决具体路径，不建设通用资源调度平台。 |
| 3：用证据继续做减法 | 收起 inline、减少角色选择和重复上下文；D3 归档发现 | 用户和模型更少选错入口，相似任务更少重读、重解释。需要自动学习或删除高级能力时，再用真实样本决定。 |
| 持续冻结 | 多人格、多租户组织平台、完整模型网关、固定全角色流水线、万能任务 DSL | 除非有反复发生且无法由现有 task/skill/执行器解决的个人工作需求，否则不启动。 |

这不是建议立刻再做一个大版本。前一批适合边界明确的小改动；后两批每次只改变一个假设，比较完整交付收益。不要以“统一”为理由重写现有 run/job/dispatch/记忆协议。

有一处可随 R1 顺手修正的旧语义：[`request-policy.ts`](../../src/webapi/request-policy.ts)拒绝 prompt 模板时，仍建议把长期规则放进“desk 的 AGENTS.md”，与只有 workspace 共享人格规则的设计不符。这类当前错误指引应修，历史 spec、验收和封存证据保持原样。

## 七、如何用实际工作判断改进是否有效

现有 task dev 场景已经覆盖作业返回、委派、提问和跨阶段新约束，不应将其贬为没有价值；[最近的修复记录](./2026-10-30-task-delivery-recovery.md)也明确说明了单次通过的证据边界。但这些证据不足以证明复杂编码交付已实现某个倍数的效率提升。

建议下一轮从日常真实工作中挑少量可复核项目，保留源码起点与最终产物，比较修改前后：

- 一项跨文件实现，包含失败后的窄范围返工与完整检查。
- 两项指向同一仓库的交办，中途聊天要求修改方向。
- 执行者返回后，用户长时间未答，再恢复任务；用确定性测试验证保留机制，用真实模型验证能否正确接续。
- 用户换入口接管已有工作，随后在新会话查找此前结论与依据。

记录人工主动追问、补背景和纠错的次数与大致耗时，最终遗漏与返工，完整交付耗时，以及已知费用、未知执行次数。不要只记录成功任务，也不要把用户没有发消息理解为认可。少量样本用于发现问题，不伪装成统计证明。

机制用 unit/e2e 证明；是否会正确转达、收敛返工和利用结果，用现有 eval 工具或实际项目证据证明。优先替换弱场景，不新增一个“个人效率评估平台”。
