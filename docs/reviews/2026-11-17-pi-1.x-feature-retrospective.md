# pi 1.0–1.5 未充分利用的能力复盘

日期：2026-11-17。Pipiclaw 基于当前工作区与已安装的官方 pi 1.5.2；上游以发布标签为准，不把 pi HEAD 未发布的 p2/Chord 功能算进来。本轮只做分析和离线探针，不修改生产代码、模型配置或已完成的依赖升级。

后续实施：用户已授权完成第 1 项，现已接通完整认证请求链与退出时凭据等待，见[实现与验收](2026-11-17-model-request-auth.md)。下文的“当前缺口”描述保留为修复前的审计证据；其他候选仍只是分析。

## 结论

值得优先投入的是两条线：**完整接通 SDK 的请求/认证生命周期**，以及**对适合的工作引入 codemode 式工具编排和按需发现**。前者已复现当前接入缺口；后者有明确机制收益，但还没有本项目真实模型任务的提效数据。

MCP 的价值在于接入项目目前没有的外部系统，需要先有具体工作流；图片生成也是特定工作流的增益。不能把这些条件性机会都说成普遍显著收益。分类器、虚拟模型路由和新 telemetry 不足以在当前代码上单独证明显著价值。

| 顺序 | 能力 | 当前接入 | 收益成立的条件 | 工程量判断 |
| --- | --- | --- | --- | --- |
| 1 | 完整请求认证与退出时 credential drain | 有 ModelRuntime，但多个推理入口只取 API key；未接 credential drain | OAuth、要求额外 headers 的网关、凭据轮换；已有确定缺口 | 请求链约 2–4 工日；关闭路径约 0.5–1 工日 |
| 2 | Codemode + 工具按需发现 | 自有工具全部直接声明，没有加载这两个 SDK 扩展 | 多步分页、批量读取/查询、先过滤后汇总、较大的工具结果 | 小范围 codemode 试验约 3–5 工日；完整接入约 1–2 周；单独按需发现约 2–4 工日 |
| 3 | MCP 外部能力接入 | pi-mcp 随 SDK 安装，没有接入本项目会话 | 已有明确外部系统任务，现有 skill/CLI 做得差或缺失 | 首个受限服务约 5–10 工日；完整配置/认证/多会话管理更多 |
| 条件候选 | 原生图片生成 | 当前没有相应模型工具 | 经常做前端素材、配图、视觉原型，且现有外部执行器不能完成 | 约 2–4 工日及图片模型费用 |

工时是熟悉项目后的单人工程估算，包含机制验证和文档，不是已完成工作或保证交期。不同部署的实际收益差异很大：如果主要工作已交给外部 Claude/Codex CLI，父代理自身的 codemode 收益会缩小；修复认证接线也不会让普通 API-key 请求自动变快。

## 审计范围与时间线

检查了 ai、agent、coding-agent、tui 和 MCP 的发布说明，以及当前会话构造、工具注册、认证、内部代理、记忆、压缩和用量处理。对照过 1.2/1.5 升级评估、spec 055 和 spec 067，区分“新发现”“早已识别但暂缓”“已经自动受益”。

| 版本段 | 与本项目有关的演进 | 当前判断 |
| --- | --- | --- |
| 1.0.0–1.0.4 | Codemode 提示收缩、模型图片生成接入、图片保存/返回；MCP OAuth 和项目覆盖完善；动态工具变更保缓存；thinking 对应采样参数 | 工具编排、外部能力仍未用；协议修复多数随升级生效 |
| 1.1 | 请求/工具耗时、取消结果、新分类器、图像分类与模型目录 | 已有自有延迟日志；分类器没有对应的已证实瓶颈 |

| 1.3 | 切模型清理旧 thinking、保缓存切 thinking、Kimi Code 协议、恢复工具集 | 大部分已有接入或随底层生效 |

| 1.5.1–1.5.2 | 消息线程、缓存保温、credential drain、网关和 OAuth 修复 | 前两项已另评；credential drain 仍缺宿主接线 |

MCP、tool search、codemode、虚拟模型和分类器的基础在 0.99.x 已存在。此处把“1.0 已可用、到 1.5 继续增强”的能力纳入复盘，不把它们伪称为 1.5 首次新增。特别是完整请求认证接口本身早于 1.0；1.x 的认证/供应商演进让当前部分接线问题更值得处理。

## 1. 完整请求认证：目前唯一已复现的功能缺口

当前主会话 `src/agent/session/session-host.ts` 的流直接调用 pi-ai compat `streamSimple`，认证由 `getApiKeyForModel()` 获取字符串。内部代理和记忆 sidecar 也沿用字符串 key 的接口。

SDK 的 `ModelRuntime.getAuth(model)` 实际返回 `apiKey`、`headers`、可能覆盖的 `baseUrl` 以及 provider env；`ModelRuntime.streamSimple()` 负责将它们合成请求，并通过当前 provider 派发。`ModelRegistry.getApiKeyForProvider()` 只返回其中的 key。本项目的压缩摘要已经单独转发完整认证中的部分信息，主聊天却没有同等接线。

**离线实测**：在全新临时 home 配置一个自定义 OpenAI-compatible provider，使用合成 key，并配置必需的 `X-Audit-Required: yes`。不读真实用户凭据，所有 fetch 都由本地函数处理。

| 路径 | 必需头是否存在 | 模拟网关结果 |
| --- | --- | --- |
| SDK `getAuth(model)` 的解析结果 | 是 | 表明配置和 SDK 解析正常 |
| 当前 `getApiKeyForModel()` + compat 流 | 否 | 401，最终 `stopReason: error` |
| SDK `ModelRuntime.streamSimple()` | 是 | 正常 SSE 完成，`stopReason: stop` |

这证明当前路径可以丢弃有效的网关配置，不是推测所有 OAuth 都有问题，也不是声称生产已经发生过这次模拟错误。普通 API key 端点不一定受影响。原 1.2/1.5 评估曾将完整认证转发记为后续工作，本轮补上了可复现证据，应从一般“未来能力”提升为明确接入修复。

建议把主会话、内部代理、记忆和摘要逐步统一到同一个 models 域请求端口，复用真实 ModelRuntime。保留目前 trace、备用模型、取消和 task budget 的控制，避免丢失它们；不要分别复制一套 header 合并规则。所有入口都要验证，不能只让主聊天正常而记忆后台继续失败。虚拟模型路由本身需另评，不应借这个修复顺手引入自动选模型策略。

另一个小而重要的收尾是 1.5.1 的 `settleCredentialWrites()`：SDK 在进程退出前等待已开始的 OAuth refresh 写入，本项目却直接调用同步 `session.dispose()`。应在 runtime 关闭总预算内协调相关 ModelRuntime 的 credential drain，不能只机械换成另一个 dispose，也不能无限等待。测试应证明旋转后的 token 真正落盘；缺少真实 OAuth 账号时，不能用 mock 声称全部认证已验收。

## 2. Codemode 与按需工具：最有潜力改善每项工作成本的机会

### Codemode 的价值是程序处理，而不仅是并行

模型用一次脚本描述确定的工具流程：分页取数、批量读取、解析、筛选、排序、汇总，最后只把需要的结果交回模型。例如“翻完若干页记录，按条件选出少数 id，再获取对应详情”，可以把无需语言模型判断的机械中间步骤交给程序。

当前 `bash` 已能做本地文件和文本处理，因此对纯 shell 任务重复引入 JavaScript 执行器价值不大。真正有区别的是组合现有 `web_fetch`、记忆查询、未来 MCP 等受控工具，且中间的大量结构化数据不必全部进入模型历史。现有直接工具调用也可以一次并行多项读取，不能把它错误比较为“每个读取都必须单独问一次模型”。

**实际发布包的沙箱探针**：通过公开 `createCodemodeExtension({ models: false })` 调用官方 QuickJS 执行器，以合成 extension context 提供 3 页、60 条记录。脚本依次分页并过滤，3 次工具返回合计 **61,900 字符**，交回的文字只有 **66 字符**，包含目标 id `[57,58,59]`。

这只验证“中间数据可在程序里处理，输出可收敛”的机制，不证明真实模型能写对脚本，也不是项目端到端耗时、token 计费或安全接线的测试。它没有调用模型或真实服务。要判断实际价值，应做分页查询、批量资料筛选、跨工具汇总三类任务的配对行为评测，比较成功率、模型往返、总输入及总时间。

SDK 提供公开工厂，内部工具调用经 `ctx.executeTool()` 复用校验、hook、取消和执行顺序。仍有实质接入成本：

- 默认脚本可调用当前 callable 工具，`models: false` 只关闭分类器/生图接口，不会把现有文件、任务或委派工具变成只读。小范围试验必须做真实可达工具过滤，不能只在提示里写“只读”。
- 本项目的 `details` 属于 runtime 通道，不是脚本结构化返回协议。没有 `outputSchema` 的工具在 codemode 中通常拿到 text，需要明确数据形式，不能把所有 details 暴露给脚本。
- 嵌套工具事件带 `parentToolCallId`，当前进度、计账、任务终止和错误分类没有专门为这项接入验证。SDK 不把每条嵌套原始结果单独保存成正常 transcript 条目，冷存储、记忆与压缩也要确认仍保留必要证据。
- 先限制为合适的数据查询/聚合工作，不把 `task_report`、`task_wait`、任务关闭和委派 settlement 等状态机控制包进任意脚本。写入租约、守卫、执行顺序与取消必须保留。

Codemode 不能兑现 spec 067 已撤销的 SDK 分段调度。本轮没有提出重建/修改 SDK，也不把另一种工具编排当作同一调度机制。

### 按需发现有可量化的空间，但不要把 schema 缩减等同账单缩减

本项目 `initialActiveToolNames` 会直接激活当前工厂给出的全部工具。SDK 的 `createToolSearchExtension()`、deferred exposure 和持久化 loadout 已可支持“先找工具，再声明并调用”，目前没有接入。

从实际工具工厂取得 schema，默认 web 关闭、任务与 inline 委派开启，并提供 `send_media` 的聊天集合为 **25 个工具、23,314 字符、3,342 prompt units**；任务集合为 **21 个、16,850 字符、2,452 units**。一个示意性的 11 工具核心集合为 9,549 字符、1,380 units；这还没有计算发现工具自身说明和延迟工具目录。units 是本项目的确定性长度度量，不是供应商 token。

`subagent_inline` 和 `event_manage` 两项就占 6,695 字符，约 28.7%。所以先考虑低频、重定义的业务管理工具延迟发现，保留文件工具、正常委派入口及任务会话必需的报告/提问/等待能力直接可见。已有角色覆盖充分的部署还可先利用现有 `subagentInline` 开关作低成本比较，不必为省一项 schema 立即引入整个新机制。

收益主要出现在新会话、冷缓存、不缓存的供应商及模型上下文压力上。稳定命中的 schema 前缀本来费用低；每次额外发现还可能增加一次模型往返。需要测发现召回率、总成本和“模型没发现关键工具”的失败率。之前的 SDK 评估并非从未记录这项能力，而是将其延后；本轮认为它应与 codemode 一起重新排入候选验证。

## 3. MCP：可能带来功能跨度，先选一条真实工作流

1.0 以来持续完善的 MCP 客户端、OAuth、namespace、资源与工具发现，可以让 Pipiclaw 直接访问已有 MCP 服务，而不必给每个业务系统重新写 skill + shell 脚本。SDK 主入口公开 `createMcpExtension()`，也有独立 `pi-mcp` 包。

当前工具配置没有 MCP，SessionHost 的 extensionFactories 也没有它。依赖包已安装不代表钉钉里的主代理可以使用其工具。适合的验证目标是用户确实反复处理、现有通路不顺畅的一个系统，例如工单检索到更新、知识库查询到文档汇总，先验证读取、分页、失败和认证续用，再决定写操作。若现有 skill/CLI 已稳定覆盖，这一项不一定值得迁移。

不能直接照搬 pi CLI 的交互管理：本项目需定义 app-home 配置/凭据归属、服务器连接复用与关闭、desk/task/request 的可达范围、网络守卫和 stdio 进程边界、消息体上限、取消、错误恢复，以及无 UI 时的 OAuth 管理。SDK 工具 hook 不会自动替远端服务套上 Pipiclaw 的文件与网络领域规则。MCP 应复用本项目 `content/details` 和执行追踪合同，不能假装都是现有本地工具。

建议首个服务采用 deferred + tool search，而非为接一个服务强制启用整个 codemode；SDK 支持这种 exposure。只有当服务内部确有大量机械编排时，再叠加 codemode。这样 MCP 与 codemode 可以分别验收，减少联动故障面。

## 4. 有条件的候选与暂不优先项

- **图片生成**：1.0 的 codemode 生图入口、后续图片落盘/返回，适合前端素材和视觉原型。更直接的接法是模型工具调用公共 `ModelRuntime.generateImages()`，将图片存到 desk 工作文件并由已有媒体通道发送，无需先启用 codemode。需要额外图片模型、费用计账、格式/大小限制、路径保护和取消。普通仓库维护并不普遍需要它，因此列作场景候选。
- **费用来源、耗时与 telemetry**：1.1 的 duration、1.4 的 tracing、1.5 的 `totalFromProvider` 可增强观测。当前已有请求/首输出/工具耗时 trace，主回合也已读取 `responseModel`；总费用已使用 SDK 合计。缺口主要是保留实报/估算来源和统一 provider 观测，适合作为上述接入的验证支持，不单独宣传为显著提效。
- **分类器**：1.1/1.4 的新 API 和图像能力适合大量固定标签/评分任务。本项目现有任务等待和记忆门控多为确定性规则，没有证据表明用分类器替换会变好；不应用它决定授权、任务 state 或完成真实性。
- **虚拟模型路由**：更早已有，当前没有充分使用。它可能降低混合工作成本，但需要自身策略、质量证据、计账和缓存切换验证；与刚讨论的默认模型调整有相同不确定性，暂不自动加路由器。
- **按 key 的 OpenRouter 目录**：当前 ModelRuntime 已内建 personalized catalog，`/model` 的 registry refresh 可触发，不能误列为尚未接入的新项目；首次离线创建并不等于永远不刷新。
- **新 schema builder、pi 自带文件工具、TUI UI、pi-durable/p2**：前者不要求重写当前 TypeBox；自带文件工具优化不替代已有 FileStore 实现；TUI 多为小改进；durable/p2 不能仅为追新而重做本项目任务与恢复系统。
