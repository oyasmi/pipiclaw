# pi 1.4.0 → 1.5.0 升级评估

日期：2026-11-09。Pipiclaw 基线：`0a0719817c15380c0cccb1794c2f812e24b903aa`，包版本 `0.9.5`。

## 意见

**建议升级，收益大于适配成本，按一次范围收紧的维护升级处理。** 最大收益是大工具调用的流式解析性能和可靠性修复；新增模型是次要收益。没有发现当前接入的阻断性不兼容，也不需要迁移历史会话或重写工具定义。

但不能称为“只改版本号、原测试全部通过”：直接升级后有一条 e2e 断言失败，因为它要求 SDK 保留一个上游现已修复的内存状态。仅在隔离副本更新该断言后，完整机制验证通过。此外，新校验器确有已复现的非有限数值缺陷；本项目现有领域校验挡住了相关风险，应明确接受这个有限风险，而不是把测试全绿解释为上游没有问题。

先行评估阶段主仓库仅增加本文，依赖、源码和测试未修改。实验副本是评估证据，不是发布分支。该阶段未修改用户配置、认证或运行中的 daemon，未调用付费模型。用户确认后的正式升级与真实模型验证见文末实施记录。

## 兼容性判断

### 工具参数：保留 TypeBox 即可，不宜顺便重写全部 schema

1.5.0 不再从 pi-ai 主入口导出 `Type`、`Static`、`TSchema`；AgentTool 的参数类型改用 pi-schema 推导，执行前校验也改用 pi-schema。`Type.Refine()`、codec 和 TypeBox 自注册 format 等非 JSON Schema 行为不再执行；部分复杂 TypeBox 类型不能继续自动推导。

当前 Pipiclaw 已从 `typebox` 自身导入构造器，工具使用普通 Object/String/Number/Integer/Boolean/Array/Union/Literal/Optional 等定义，没有依赖上述非标准能力。类型检查直接通过；没有必要增加 pi-schema 直接依赖或改写所有工具。现在迁移会额外引入对象是否允许附加字段等语义变化，收益很小。

错误信息内部条目改变，但外层 `Validation failed for tool "…"` 和 `Invalid arguments for tool "…"` 仍保留。`isArgumentValidationFailure()` 的分类继续有效，现有真实 SDK 校验测试通过，模型可自行修正的错误没有因此进入用户进度卡。

额外离线探针从实际聊天和任务工具工厂取得 30 个工具的 schema：

- 1,832 组常规输入比较 1.4/1.5 的接受/拒绝及转换结果，没有差异。包括缺字段、optional null、数字字符串、小数转整数、布尔字符串、标量与数组、嵌套对象。
- 扩展非有限数值后共 2,468 组，有 9 处差异，集中于 `web_fetch.maxChars`、`event_manage.definition.task.budget.usd`、`task_create.budget.usd`；详见下文。

这是有限参数探针，不是对所有 JSON Schema 的等价证明，也不是新增的项目测试用例。

### 会话写入：上游修复触发旧断言，需要保留本项目的保护

上游 `_appendEntry()` 现在在 `_persist()` 抛错时回滚 `fileEntries`、`byId`、`leafId`，避免后续条目指向一个没有写入磁盘的父条目。

既有 `fallback.test.ts` 故意让第二个 context edit 写入失败。旧 SDK 内存留下两个 edit、磁盘只有一个，所以断言要求内存长度为 2。1.5.0 回滚后内存和磁盘都是 1，原断言变红，属于修复后的预期变化。

隔离副本只将该长度断言改为 1 并更新注释，保留所有后续机制断言：部分写入后停止请求、reload 失败仍拒绝继续、重启从磁盘恢复、不自动重放备用请求、`/new` 可用。完整 e2e 随后通过，用例数量净增 0。

**不要删除 Pipiclaw 的 context fault 隔离。** 第一条 edit 已成功、第二条失败，整个上下文操作仍是部分提交；SDK 单次 append 回滚不能把两次 edit 变成事务。历史升级中为此建立的保护仍有价值。

### 既有接入继续成立

- 自建 Agent/AgentSession、持久化 canonical context、备用模型 context edit、请求工具集、内部裸 Agent 的接入没有新增必改点。既有首轮工具、备用模型去重、压缩预算、会话恢复等 e2e 通过。
- 私有 `_baseToolsOverride` 仍存在，当前重载适配可用；它仍是私有耦合，并未因此成为稳定 API。
- SDK 保留活跃工具的原顺序，可避免同一集合换序引发多余 system 更新；当前工具声明和持久化投影机制保持。
- 没发现新的会话格式迁移要求，保留原始 JSONL 和 context edit 机制。

## 当前能够获得的收益

| 变化 | 对 Pipiclaw 的实际价值 | 判断 |
| --- | --- | --- |
| 工具参数流式解析改为增量解析，原始流内部状态移出 content block | 主代理和内部子代理的大 `write`、`edit` 等调用更省 CPU/内存，减少事件循环阻塞；失败流不会夹带这些内部缓冲字段 | 本次最值得升级的收益 |
| 会话 append 失败回滚，fork 通过一个 fd 写入 | 改善持久化一致性及复制大历史的开销；仍需现有恢复保护 | 直接受益 |
| Claude 系统消息顺序、effort 上限兼容修复；GPT-5.4/5.5 切模型后工具 namespace 修复 | 减少长会话、切换模型和工具历史引发的请求失败 | 对应供应商用户直接受益 |
| Kimi K3.1 Pro 系列参数、thinking、动态工具与价格修正 | 新模型不再错误套用 K2 设置；Kimi Coding 旧 `k3-256k` 的费用元数据也修正 | 相关部署受益 |
| Z.ai 1308 不再按瞬时 429 重试；LiteLLM overflow 识别 | 减少无效等待，内部子代理的重试分类也能受益 | 直接机制收益，不保证所有本地备用策略随之改变 |
| OpenRouter reported cost | 原有累加器直接使用 `cost.total`，可获得更接近计费的总额 | 总额改善，来源展示仍缺接线 |
| TUI Markdown 缓存、Text 相同文本复用、中文 URL 边界、嵌套引用及键盘修复 | 本项目使用这些组件，重绘、显示和输入可靠性受益 | 中等收益；当前 TUI 最终答复才创建 Markdown，不能照搬上游逐 token 渲染的性能宣传 |
| GPT-6.1 Terra 等目录更新 | pi 内部代理可选择更多模型，Terra 支持关闭 thinking | 有用，但性价比需按任务评测；外部 Codex CLI 的模型支持由外部 CLI 决定 |

离线解析微基准使用两版发布包的实际解析器，对相同 JSON 按 128 字符分块喂入，校验最终参数一致：

| 参数 JSON 长度 | 分块数 | 1.4 全量重解析 | 1.5 增量解析 |
| --- | --- | --- | --- |
| 10,758 字符 | 85 | 约 50 ms | 约 4 ms |
| 96,468 字符 | 754 | 约 2.8 s | 约 10 ms |

这是单次本机解析路径测量，进程同时有测试负载，不能当作端到端延迟或固定倍数承诺。它说明大参数的本地开销确实可以显著减少；不代表模型生成更快，也不直接减少 token 费用。后续重复运行的原始数值保留在探针日志中。

## 能力变化与限制

### 新校验器存在已知缺陷，但当前相关边界可控

1.5.0 的普通 `number` 检查会接受 Infinity/NaN。不是完全不可达的 JS 特例：合法 JSON 数字 `1e999` 经最终参数解析会成为 Infinity，已通过真实 `parseToolCallArguments()` → `validateToolArguments()` 复现。

当前受影响的本地字段有独立处理：任务创建及事件模板的 `normalizeTaskBudget()` 要求有限正数，网页 `maxChars` 经 `clampInteger()` 遇非有限值回到配置默认值。离线调用这两个真实函数，Infinity、-Infinity、NaN 均被拒绝或回落；没有发现任务预算放开或网页长度失控。不能把这些局部保护推广为新校验器所有输入都安全。

上游已有发布后修复 [55a5c6914](https://github.com/earendil-works/pi/commit/55a5c6914570e2ae31ca36297654483bbbf46883)。另有相对根 `$id` 与本地 `$ref` 解析修复 [2bd2c2d0a](https://github.com/earendil-works/pi/commit/2bd2c2d0a6a13e9a2d760073bd6e67b662964a60)，当前工具没有使用这类引用。复杂 TypeBox 类型推导也在发布后继续完善。

这增加了对新校验器的审慎程度，但现有代码不依赖这些缺陷路径，不构成当前升级阻断。后续如新增复杂 schema/MCP 接入，要重新判断。保持官方版本，不混装未发布的 pi-schema，也不重新引入 spec 067 已放弃的自建 SDK 路线。

### 模型目录会收缩，部分请求协议和成本口径改变

对两版 npm 内置聊天目录比较：1,599 → 1,592，新增 50、移除 57、修改 173 个条目。目录减少不等于真实编码能力整体下降：部分移除是把 realtime/image 模型从聊天目录中剔除，但也包括部分 OpenRouter 免费、batch 和旧聊天模型。

正式升级前要核对部署的默认、备用和内部子代理模型引用。例子包括 `openrouter/nvidia/nemotron-3-super-120b-a12b:free`、`openrouter/openai/o3-mini` 的目录移除；不能只核对主模型。当前没有检查用户实际配置，不能保证某个部署不受影响。

OpenRouter 的 `~anthropic/claude-*-latest` 切到 Anthropic Messages API，以保留 thinking；有自建代理或自定义 baseUrl 的部署须核对协议与路由。普通 OpenAI/Anthropic、默认 Sonnet、常用 Z.ai 引用没有因此统一改名。

OpenRouter 的 `cost.total` 可以来自计费报告，输入/输出/缓存分项仍可能是目录估算，因而总额不再必然等于分项之和。现有总额累计可接收；`UsageTotals` 不保留 `totalFromProvider`，尚不能完整展示“实报/估算”的来源。不能把新字段描述成 Pipiclaw 已提供完整账单核对能力。

### 有些上游修复和新能力不会自动进入本项目

- SDK 摘要 OAuth 修复主要针对 `createAgentSession()` 安装的 runtime stream；Pipiclaw 自建 `streamSimple` 包装，并自行解析压缩认证。不能宣称此次升级自动解决所有 ChatGPT OAuth 或虚拟模型认证问题。
- pi CLI 的默认模型调整不等于 Pipiclaw 默认模型调整；Pipiclaw 自己选择模型并提供默认 Sonnet。
- pi 默认 system prompt 的精简主体被本项目自有 prompt 覆盖；SDK skills 指引有小幅措辞变化，但没有因此获得新的自主任务决策策略。
- 扩展更新说明、自更新命令、MCP OAuth、导出 HTML 等主要是 pi CLI 能力。当前没有启用的集成，不算 Pipiclaw 升级的直接收益。
- 工具调度仍只有官方 `sequential | parallel`，没有 spec 067 曾讨论的分段调度。升级不能解决所有工具批次及委派完成延迟。

## 建议的正式升级范围

1. 四个直接 pi 包一起精确锁定 1.5.0，提交对应 lock；保留当前 TypeBox 定义方式。
2. 更新既有 e2e 的 SDK 内存状态断言，保留部分写入隔离与原有恢复链；不删用例、不降低机制保护。
3. 记录模型目录、OpenRouter 协议和计费口径变化；上线前核对实际部署的模型引用。
4. 在正式升级分支完成项目门禁，再按已生成的 dev plan 做定向真实模型验证；这属于发布验收，当前评估没有代做。

不建议把 schema 全面迁移、认证流重构、新模型切换和用量来源展示塞进同一升级。当前有明确的性能/可靠性收益，适配量小；限定上述范围，升级性价比为正。若实际部署只使用外部 coding CLI、很少产生大的 SDK 工具调用，升级紧迫性会降低，但没有必要仅因版本号变化就长期冻结在 1.4.0。
