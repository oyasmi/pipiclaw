# 钉钉进度窗口：收缩后继续增长

## 问题与证据边界

用户在 `6ca4630037a1317252288548a7f9265238774664` 后观察到：卡片收缩为几行，下一次更新却恢复成长卡片。

代码审查确认：旧 `publishProgress` 在同一轮内循环排空队列，发送收缩快照后立刻追加积压行，没有可读的停留时间。单次追加还允许接近 1KB，而收缩快照只有约 200 字节，一条长进度即可大幅撑高卡片。旧测试只模拟字符串替换 / 拼接，没有覆盖连续多轮收缩、再增长和可读的更新间隔。

本地 `document` 原先在替换成功后已经重置，不能据此断言有一条确定的本地旧全文恢复路径。远端流式缓存或客户端动画的影响仍是推测，尚未真机定位。[官方 Python SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-python/blob/main/dingtalk_stream/card_replier.py) 将 `append` 映射为 `isFull` 的反值；实现使用这两个模式的公开语义，不把未经验证的缓存行为当作事实。

每次发送全文可以减少本地同步分支，但会反复传输旧内容，也把展示窗口限制在单次请求预算。本次最终采用周期编号、已确认前缀和有节奏的增量传输。

## 最终机制

| 项目 | 决策 |
| --- | --- |
| 默认模式 | 当前周期按顺序累积全部思考和活动，不限制行数；正文将超过约 2.9KB 时收缩，再重新累积 |
| 滚动模式 | 固定保留最近五条进度，包含思考和活动；顶部摘要另计；旧条目移出时替换窗口快照 |
| 默认模式收缩保留 | 最近两条活动和最新思考，通常收缩为 3–4 条列表行；旧条目真正移除 |
| 正常传输 | 首帧替换等待文案，之后用 `isFull: false` 只追加已确认前缀之后的新列表行；同一批事件合并发送 |
| 同步基线 | 每个周期有独立编号；只有写入成功后才应用该请求捕获的正文前缀及周期编号。替换成功后，新快照就是后续增量的基线 |
| 在途请求 | 收缩期间返回的旧请求只能确认它自己的旧周期；下一帧检测到周期变化就替换，不能把旧周期恢复为当前视图 |
| 单条和分帧 | 活动最多 180 字节，按字符边界裁剪；思考取尾部，其他活动取头部。每帧正文最多 1000 字节，按完整列表行分帧 |
| 顶部摘要 | 周期内保持不变，替换时刷新用时 / 工具次数；避免每次修改头部而无法追加 |
| 更新节奏 | 首批事件合并为一次异步更新；之后从请求完成起至少间隔 800ms，每个间隔只发一帧，无新内容时不轮询 |
| 高频输入 | 同周期待展示内容最多约 2.9KB，分帧追至当前视图；收缩时淘汰旧周期积压，不因持续输入后移已安排的发送时间 |
| 结果不确定 | 增量失败可能已在服务端生效，不直接重试该增量；开启短新周期，下一帧全量替换，再继续增量 |
| 模板限制 | 模板拒绝增量时，才退回每次不超过 1KB 的完整快照；此时默认模式的收缩预算随请求预算降低 |
| 结束和失败 | 最终答复、静默结束与停止不等待进度计时器；连续两次进度写失败后停止进度，最终答复仍独立发送 |

1KB 与 2.9KB 是沿用的项目预算，不是本次重新认定的钉钉平台上限。默认模式没有固定行数限制；滚动模式的五条限制才是持续移动窗口。列表行仍可能随屏幕宽度换行。高频事件可能在展示前就被后续收缩淘汰，不保证每条活动都在客户端停留，原有会话日志仍承载完整执行记录。

## 验证

扩展原有场景，用例数净增 0；未增加确定性 e2e 场景。覆盖多轮收缩 / 再增长、已移除内容不复现、默认模式超过 8 行、滚动模式最近五条、中文 UTF-8 预算、1KB 分帧、慢请求期间收缩、模板降级、节流不被持续输入推迟、最终答复和停止绕过计时器、增量已经应用但响应丢失后的恢复。

同一串进度还比较了实际发送的正文总字节数与每帧重发当前全文的总字节数，要求前者低于后者的一半，防止实现退回逐次全文重发；这是离线固定输入下的正文比较，不包含 HTTP 头，也不是线上流量测量。

最终验证结果：

- `npm run check` 通过：lint、类型、架构、deadcode，以及 142 个文件的 1010 项单测。
- `npm run test:e2e` 通过：27 个文件的 70 项确定性测试；构建使用最终增量实现。两套完整检查依次执行，日志分别保留在 `/tmp/pipiclaw-card-incremental-check.log` 与 `/tmp/pipiclaw-card-incremental-e2e.log`。
- 两次定向故障注入均变红：强制逐次全文传输、替换成功后仍拼接旧基线。它们都会在请求前缀用尽后丢失最新进度。故障已恢复，再运行完整检查；用例注释记录了验证。

真机动画、客户端缓存和实际可读性仍需部署后验证；离线测试证明请求与本地状态满足上述机制约束。
