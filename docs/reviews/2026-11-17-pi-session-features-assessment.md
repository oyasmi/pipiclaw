# pi 1.5.2 后续能力接入评估

日期：2026-11-17。依赖升级已完成，见[升级验收](2026-11-17-pi-1.5.2-upgrade-assessment.md#正式实施与验收2026-11-17)。本文只评估消息线程、缓存保温和默认模型选择，不实施这些功能。

后续取舍：结合实际收益，本轮暂缓这三项功能，仅实施复盘中明确复现的[完整认证请求链](2026-11-17-model-request-auth.md)。下文保留候选分析，不代表已排期或已经接入。

## 建议

| 方向 | 建议 | 主要收益 | 完整接入工作量估算 |
| --- | --- | --- | --- |
| 消息线程 | 值得接入，先覆盖长聊天/任务会话与官方 Anthropic 端点 | 减少历史上传和服务端重复处理，改善长循环首 token 等待 | 约 1–2 工日，另加实际端点验证 |
| 缓存保温 | 暂缓全局启用；有证据后做显式可选功能，先考虑工作回合仍活跃的情况 | 避免长工具间隙使缓存过期，可能减少下一次冷启动费用 | 约 2–4 工日，需要额外模型费用与使用数据 |
| 默认模型选择 | 优先梳理选择规则；新模型先做候选评测，不直接替换用户配置 | 新安装体验可预测，可能改善任务成功率和单位成功成本 | 选择规则约 0.5–1 工日；候选比较另约 1–2 工日及模型费用 |

以上是单人熟悉项目后的工程量判断，包含有价值的机制验证和文档，不是已完成工作或交付承诺。实际端点、供应商和角色差异会扩大范围。没有因本次依赖升级自动获得这些收益。

## 消息线程：适合长循环，值得做，但应保持本地会话为准

Anthropic 消息线程让请求只上传新增消息。服务端恢复已有上下文后仍向模型提供完整会话；它不会扩大 context window、代替压缩或直接改变 token 计费。官方说明将其主要收益定位为长 agent 循环的上传、验证/分词开销与首 token 延迟改善。线程是短时、尽力保存的状态，过期必须从完整本地历史重建。[官方说明](https://platform.claude.com/docs/en/build-with-claude/message-threads)

这与 Pipiclaw 相容：本项目已经有持久化 canonical context、按会话串行的执行、context edit 和恢复链。保留这些机制，把线程当作可丢弃的请求优化即可。长任务内频繁工具往返可能最受益；间隔很久才来一句话的钉钉聊天、一次性无历史请求、单次记忆 sidecar 的收益有限。这是从代码形态得出的判断，本次没有测量真实流量或端到端提速。

pi-ai 1.5.2 已实现前缀/固定参数指纹比较、增量发送、部分线程错误的全量回退以及进程内状态清理。本项目无需再维护一套远程线程数据库，也不应实现另一套消息差分算法。当前缺少的是宿主接线与验证：

- 主 Agent 使用真实 SDK `SessionManager.getSessionId()` 作为请求 `sessionId`；task lane 本来有独立 SessionManager，自然隔离。不能用 desk 名或 channel id 代替会话 id。`/new`、fork、切换、退休时，id 和清理必须跟随真实 SDK 会话。
- 当前 `AgentSession.dispose()` 会清理其 session id 对应的 provider 状态，适合复用；裸内部 Agent 若以后接入，应给每次 run 独立 id 并显式清理。不要为了统一参数给单次 sidecar 引入无价值的长期状态。
- 保留网关的 `compat.supportsMessageThreads` 能力配置。SDK 默认只在官方 Anthropic 端点开启，未知代理不强开；传入 `sessionId` 也会影响其他供应商的 affinity/cache key，因此相关供应商请求需要验证。
- 压缩、历史省略、提示/工具变动和备用模型切换后，交给 SDK 按实际请求指纹判断重新创建线程。摘要、回放或保温请求应使用独立请求 id，或明确 `disableContinuation`，不能占用正常会话的续传位置。
- 后台压缩可能与前台推理并行；不能把所有 `session.agent.streamFunction()` 调用都强行盖上主会话 id。Web API 的临时 instructions、分支重建及迟到回调也应纳入验证。
- 观测实际请求字节、create/continue 比例、线程回退次数与首 token 延迟；只有真实端点数据才能说明值不值。pi 的流仍构建并比较完整本地请求，不能承诺本地序列化成本全部消失。

优先扩展既有会话/压缩/备用模型 e2e，检查真实 provider 请求体和磁盘历史一致、取消/重启后的全量恢复，不能用回复文案证明上下文完整。若现有场景不能区分前缀丢失、重复消息或摘要污染，再按项目用例准入规则增加覆盖并做 mutation check。

## 缓存保温：有经济条件才成立，不宜直接照搬 idle 默认

正常请求已经可以使用供应商 prompt cache；没有主动保温并不意味着没有缓存。稳定 system/tools 前缀、可复用的消息历史和正常请求携带缓存标记，是先应保证的基础。保温则是临近过期时主动重复一次请求，额外支付缓存读和少量输出费用，换取下一次真实请求命中的机会。长保留时间也是可比较的替代方案，并非总比主动保温贵或便宜。[官方缓存说明与价格](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

pi-ai 公共策略的单次决策近似为：

`预期收益 = TTL 内继续调用概率 × 下一次丢失缓存的额外成本 − 本次保温成本`

1.5.2 在 idle 阶段使用固定概率 0.15，要求预期收益至少 $0.05；idle 最长 30 分钟，工作回合仍活跃时最长 1 小时。这些来自上游使用经验，不能当作钉钉用户或当前部署的实测概率。多次保温还应看整个保温周期的净成本，不能把每次局部判断当成最终节省证明。[上游策略源码](https://github.com/earendil-works/pi/blob/v1.5.2/packages/ai/src/cache-warming.ts)

实际调用 1.5.2 的公开 `evaluateCacheWarming()`，按内置模型价格和 100K prompt 计算，idle 情况为：

| 模型 | 单次保温估价 | 预期净节省 | 上游策略 |
| --- | --- | --- | --- |
| Sonnet 4.5 | $0.030015 | $0.021735 | 不保温 |
| Sonnet 5.5 | $0.010010 | $0.025990 | 不保温 |
| Opus 5.5 | $0.020020 | $0.051980 | 保温 |

这是静态目录和上游假定概率的计算，不是实际账单或 Pipiclaw 流量预测。特别是 Sonnet 4.5 开启 budget-based thinking 时，上游 `isCacheWarmingReplayable()` 会另外拒绝回放，因为压到一个输出 token 会改变 thinking budget 和缓存条件；经济计算通过也不能越过该检查。

Pipiclaw 有许多后台任务、渠道和持久会话，不应给每个闲置会话都挂保温定时器。钉钉聊天较长间隔、短任务结束后不再继续、上下文经常变化时，预付保温费可能浪费。反过来，长工具执行期间确实还要继续模型循环，保温更可能有价值；连续快速工具回合的正常请求本来就会刷新缓存，也无需多发请求。

完整接入成本主要在宿主机制：

- 1.5.2 的 coding-agent 主入口只导出 CacheWarmer 相关类型，不导出其构造器；不宜导入 SDK 私有内部路径。可复用 pi-ai 的公共策略 helpers，但按本项目自建流实现会话级调度和取消，或先推动上游公开合适的接入接口。
- 只记录实际请求的不可变上下文快照，模型、提示或历史改变即停止；限制保留上下文造成的内存占用。切换、压缩、停止、闲置过久和 daemon 关闭时必须取消在途请求与定时器。
- 保温必须直走推理流，不进入 Agent 工具执行或产生用户消息、工作日记、任务推进/唤醒。使用 `disableContinuation: true`、输出上限 1、无自动重试，并遵守可安全回放检查；未知价格或 TTL 不自动启用。
- 将每次保温的实际花费接入项目 UsageLedger，可使用 `sidecar` 和专用 label，保留 desk/channel/task 归属。只写 SDK `cache_warm` 条目不够：当前事件处理没有自动把它计入项目账本/任务预算的接线。
- 需要总并发限制、费用上限和正常请求优先级，避免用户不说话时后台持续消耗额度或把活跃请求限流。把开关作为明确产品配置，初版默认关闭；不要把算法概率和每个阈值都做成新配置项。

因此先观察缓存读写、长等待与续聊间隔，再考虑只对活跃长任务或明确开启的长聊天保温。缺少当前部署的证据时，保温的优先级低于消息线程和默认选择规则。

## 默认模型：值得优化，先区分选择策略与模型质量

当前 `src/models/runtime.ts` 的真实顺序是：用户保存的 provider/model 且可用 → `getAvailable()[0]` → 硬编码 Sonnet 4.5。app-home 模板不填写默认 provider/model；硬编码值也用于初始化占位。因此“把 Sonnet 4.5 常量改成新模型”未必影响已有凭据的正常启动，更不会替换已配置用户的默认值。

这里更值得解决的是**没有显式配置时选择可预测**：新安装尽量明确选择；自动选择时有稳定、按 provider 能力与凭据可用性决定的偏好，不能让目录第一项代表产品推荐。自定义网关和本地模型不可硬套公共模型 id；配置引用失效时应明确诊断，避免无声选中更贵或不合适的模型。这是后续产品行为调整，当前仍保持原逻辑。

具体模型方面，可优先把同 provider 的 Sonnet 5.5 作为 Sonnet 4.5 的比较候选，而不直接照搬 pi 默认 Opus 5.5。查询日官方每百万 token 标价：

| Anthropic 官方模型 | 输入 | 输出 | 缓存读 |
| --- | --- | --- | --- |
| Sonnet 4.5 | $3 | $15 | $0.30 |
| Sonnet 5.5 | $2 | $10 | $0.10 |
| Opus 5.5 | $4 | $20 | $0.20 |

来源：[官方价格表](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#pricing)。这是官方 API 单价，不是代理折扣、OAuth/订阅额度的现金成本或项目成功率证据。Sonnet 5.5 具备更低标价和更大的内置窗口，因此值得测；不能从型号和单价推断它在本项目一定更好或更便宜。更大窗口也可能延后压缩、增加实际输入；不同 thinking 规则、输出长度、重试和工具失败会改变总成本。

建议按主代理、内部执行角色、压缩/记忆三个用途观察质量与成本，先复用已有默认、`subagentModel`、角色 model 和 thinking 配置，不急于增加自动路由器或每个 sidecar 一个配置项。外部 CLI 的模型配置独立，SDK 默认值不能替它决定。

使用现有 dev 集先排明显问题，再按 candidate 的冻结 case/seed/控制做两模型配对比较；以任务成功率、工具修正/重复调用、记忆约束保持、总延迟和每次成功的总费用为依据，保留失败证据。改动默认策略或模型时才执行这些真实探针并记录 run id；本轮只是依赖升级与评估，没有真实比较结果。

没有付费评测证据前，建议保持已有用户配置，先验证候选；通过后只调整新安装/无明确选择时的推荐。模型本身的优化潜力可能超过传输层优化，但它同时会影响行为质量，不能用本次 unit/e2e 全绿为新默认模型背书。
