# Prompt、playbook 与工具发现的组织建议

日期：2026-11-17。基线：`b66286f`，SDK 为本地安装的 pi 1.5.2。本轮为代码分析与离线体积试验，未修改产品实现、实际提示词、部署配置或既有讨论稿，未调用真实模型。

## 判断

建议按三个独立阶段推进：**先缩短工具说明，再让 playbook 按操作分层，最后试验“加载一份操作指南，同时启用对应工具”。** 保留精简的常驻行为规则、能力入口与核心直接工具。

当前主要问题并非 system prompt 太长，而是信息的加载粒度不匹配：一个低频工具的完整参数说明一直在场；执行一次普通操作又可能读入整份机制、恢复与运维知识。单独延迟工具，只解决前一半问题，还可能多出发现轮次。将知识加载与工具启用合并，才有机会同时改善成本和执行效果。

这与既有本地工具编排讨论草稿的关系是：先建立更紧凑的直接调用基线，再比较延迟发现；Codemode 仍是独立试验，不是这次组织优化的前提。

## 先做工具描述减负，保持直接可用

工具说明应负责三件事：何时选它、调用对象/范围、容易犯错且影响本次调用的语义。字段说明保留单位、默认值、条件必填、替换/覆盖语义和关键副作用。跨工具工作法、示例、完整恢复流程归 playbook。

最明显的机会在 `subagent_inline`：顶层 description 有 868 字符，反复解释 fallback、角色配置、自行提供完整参数，并再次枚举 schema 已给出的字段。可以压成以下候选：

> Fallback when no configured role fits; otherwise use subagent. Supply task and systemPrompt. Read agent-delegation.md for setup and isolation.

仍应在 `mutates` 字段就地保留“包括 bash 写入也要声明 write”，在工作目录字段保留“cwd 不等于写隔离”。不能把这些正确调用所需的条件全赶到附录。

`event_manage` 应就地保留：事件属于当前 desk、新建投递当前频道、更新保留投递频道且整体替换，因此先 show；`timeoutMs` 是毫秒、cron 使用宿主时区、text/task 二选一等。事件任务模板为什么存在、实例重叠行为的详细说明、示例与传感器策略放手册。

离线试验只替换这两个工具的描述和字段注释，逐项验证去掉 description 后 schema 完全相同：

| 配置 | 字符 | 单位 | 相对原集合 |
|---|---:|---:|---|
| 当前 | 23,314 | 3,342 | 基线 |
| 仅改两项顶层说明 | 22,442 | 3,198 | 单位减少 4.3% |
| 同时精简两项字段注释 | 21,167 | 2,960 | 字符减少 9.2%，单位减少 11.4% |

这不增加工具发现轮次；但**保持 schema 结构不等于保持模型行为**，还需验证选路与调用成功率。原始测量及候选 schema 保存在 `/tmp/pipiclaw-prompt-analysis-20261117.json`，临时文件不是随仓库发布的长期证据。

进一步可查 `grep`、普通 `subagent`、`job`、`skill` 等说明中的重复叙述。不要为缩小字数删除 grep 的匹配/分页语义、bash 的超时单位，或恢复时可执行的下一步。

还有一个值得单独审查的接口问题：`event_manage` 的模型 schema 列出必然被拒绝的 `immediate`，并提供次要 timeout 别名。可以只向模型呈现推荐的合法形状，运行时依旧拒绝非法调用；这涉及广告接口变更，应与纯文本精简分开验证，不计入上述收益。

## Playbook 改写：按正在做的操作加载

每个入口采用统一顺序：**适用环境 → 选择分支 → 最短正常流程 → 成功证据 → 出错后的精确下一步**。恢复细节在后，示例只覆盖容易误用的参数组合。目录 description 以用户意图触发，正文则直接给模型可执行流程。

不建议统一翻译成英文来追求单位下降。提示单位对中英文的估算规则不同，必须看目标模型实际 token 和行为。保留中文意图词、英文工具名与协议字段更稳妥。

建议的知识归属如下；是内容规划，不是要求立刻新增这些文件：

| 内容组 | 常用入口保留 | 只有触发时再读 |
|---|---|---|
| 导航 | desk/workspace/cwd 区别、当前上下文入口、状态所有者、不能跨环境绕过 | app-home 全地图、频道换绑细节、daemon 运维 |
| 聊天管理 task | 什么工作需要 task、如何写 Goal/DoD、转达/暂停/取消 | 任务内部每步推进、等待、返工与收尾 |
| task 执行 | brief 使用、等待来源、报告/提问/关闭、DoD 与副作用证据 | 复杂恢复、预算耗尽、周期实例改进 |
| 委派 | 值不值得、角色选择、自足 task、cwd/worktree、结果检查 | inline 全配置、失联/续接、复杂租约诊断 |
| 事件 | text/task 选择、新建/更新和最短验证流程 | preAction 传感器、超远期提醒、故障退役 |
| 记忆 | 存/查/纠正/忘记、主人/范围/时效 | 后台学习期限、skill 编写与来源规则 |

当前 task guide 混合聊天管理与 task 执行，尤其适合按已有 session profile 选择正文：聊天不需背下步骤预算和收尾协议，任务也不需阅读如何创建另一个任务。共享的授权和事实纪律只留一个权威出处，在操作点留短提醒。

委派优先拆出 inline 细节。读普通委派指南不应自动付出 inline 的全部知识/schema 成本。普通角色已足够时，inline 的“高级备用入口”只需一行路由。

事件短流程可以写成：

> 普通聊天使用。提醒/小检查选 text，需要持续状态和验收的定时工作选 task。新建绑定当前频道；修改已存在事件先 show，再提交完整替换定义，投递频道不变。成功以工具结果为准；参数被拒时按错误修正，不改事件文件绕过。涉及传感器才读传感器说明，写 task 模板才读任务契约说明。

具体类型、必填字段和单位仍由 schema 给出，短流程不复抄字段表。已在当前有效上下文里的正文复用；压缩丢失后才重新加载，不能因磁盘有“读过”标记而假设模型仍知道。

要避免两种分拆反效果：一是短入口末尾要求“继续读全部附录”；二是每次加一层目录跳转。常用入口应直接可用，只有真的进入异常或高级分支才追加读取。长手册的分层目标首先是减少无关输入和决策干扰，是否节省账单还取决于后续调用与缓存。

目前还发现一处文档漂移：`docs/runtime-playbooks.md` 声称 agent-delegation 恒在、不设 requires-tools，但真实文件使用 `requires-tools: subagent`。实施时需同步目录表和解释。`skill` 确实支持 list/read，并非无效入口。

## 工具发现：让一次加载同时拿到知识与能力

现有 `requires-tools` 仅决定手册是否出现在目录，`read` 不改变活动工具。只增加 SDK `tool_search` 容易产生：

1. 读手册；
2. 搜索并加载工具；
3. 调用业务工具。

前两步通常可以合并。针对七类内置机制，目录已足以承担语义发现，不一定需要模型先做开放关键词搜索。

推荐试验一个按准确名字加载的入口，例如 `playbook_load(name)`：返回该场景短指南，同时通过 session 激活它绑定的、当前环境确实允许的工具。后续模型请求同时看到指南与完整 schema，再正常调用原工具。名称只是候选，不是本轮已新增的 API。

例如：

| 入口 | 返回 | 激活策略 |
|---|---|---|
| 事件正常流程 | 短事件指南 | 仅 event_manage |
| 普通委派 | 普通派发指南 | 已有直接 subagent 不变，不连带启用 inline |
| 临时 inline 委派 | inline 指南 | 仅在配置允许时启用 subagent_inline |
| task 执行 | 对应 profile 的执行指南 | 不开放 chat 专属能力 |

已有规则要求首次复杂使用读取指南，所以这类场景可以复用原本的读取轮次。但原来简单操作无需读指南时，新入口仍会增加一轮；不能宣称对所有请求都“零额外调用”。加载工具也不会消除下一轮模型决策。

如果试验期希望避免新增入口，可以在 Session 扩展中识别对**内置、规范路径**指南的成功读取并激活关联工具；这节省一个工具定义，但会使 read 承担隐含的会话状态变更，且必须处理分页、失败读取和路径伪装。长期更倾向显式 loader：语义清楚，也更容易报告当前已声明集合。不要同时默认上两套入口。

SDK 的词法 tool_search 可以保留给工具规模更大、尚未由内置目录覆盖的能力。七类已知机制优先准确入口；若采用搜索，目录提供准确工具名与少量中英关键词。既有离线探针已显示中文意图不一定命中纯英文描述，不能假设它是跨语言语义搜索。

加载接线必须满足：

- 区分**当前 profile 允许注册的能力、可发现能力、当前声明工具**。playbook 目录按前两者筛选，不能按当前声明工具筛选，否则工具和手册会互相隐藏。配置禁止、request 无持续地址、task 禁止的能力永不因加载恢复。
- `requires-tools` 保持 any-of 可达性语义；另行声明加载关联，不把它误当“需要把这些工具全启用”。绑定只来自内置受控 metadata，workspace skill 和任意 read 内容不能授予能力。
- 保持已加载集合，处理 resume/fork、压缩、工具重建和 `/reload`；恢复时与当前允许集合求交。工具仍已加载而指南正文已丢失时，可重读知识，不必重复搜索。
- 当前 SessionHost 初始化与重建都把全部 tools 设为 active，需一并调整；仅给 AgentTool 对象加 deferred 字段不够，应走 SDK 支持的 ToolDefinition 注册与加载接口。
- 指南内容留在正常工具结果/会话上下文，不因每次加载重写整段常驻 system prompt。动态激活本身仍可能改变供应商工具声明与缓存行为，需要实际请求验证。
- 观测要报告实际发送的声明与指南正文成本。当前 `/context` 的 currentTools 在全部直接声明时适用，引入 deferred 后不能再拿它代表线上输入。

这里还有本项目特有的缓存核对点：最终边界扩展会在 `before_agent_start` 返回完整 systemPrompt；本地 SDK 的 `_installAgentForcedPromptProjection` 会把它和当前工具声明投影到请求头，并过滤历史 system 消息。因此，“工具变更在会话里增量记录”不能直接证明供应商请求仍然只在尾部追加。应观察最终请求、声明顺序和 cache usage；同样不能把每次 rebuild 本身当作缓存失效证据。

工程归属：playbooks 域负责只读内容、目录和关联 metadata；工具适配层只做参数与返回；session 层拥有激活集合和 SDK 接线。不要让底层 playbooks 导入 tools/agent，或让通用 read 自己维护会话状态。

## 常驻 prompt 应保留什么

保留行动完成纪律、验证与未验证项、授权边界、检索内容是数据、状态写入所有权、异步工作完成自动回流等少量规则。它们不是普通操作说明，不能因为指南已经写过就从所有入口删除。

可以将现在宽泛的“non-trivial use 前读 guide”改成更明确的条件：首次进入该机制的写操作或跨工具流程时加载相应短指南；简单只读 list/show 不强制读完整手册；正文仍在上下文就复用。究竟哪些简单写操作可直调，应按风险与 eval 结果决定，不能全局放开或强制一刀切。

角色目录继续保留紧凑的名称、候选用途和可用性；详细角色 prompt 不进入常驻上下文。当前任务独立会话、请求白名单等已有结构化裁剪优先于再加一个意图分类模型。也不建议用关键词检测用户消息来自动猜该装哪些有副作用工具。

手册里“用户确认后更新模板”等语句还应改成授权条件：已明确要求的调整直接执行；只有新增目标、扩大范围或缺少必要授权时才询问，避免对已经授权的同一动作重复确认。

## 如何判断是否值得

缓存命中会降低工具定义的边际输入费用，但不会让它不占上下文；正文读取、发现推理、修复调用和整合成本也要计入。可以用下式组织测量，不能把字符节约直接换成费用承诺：

`净收益 = 未加载 schema 在后续请求中的实际费用节省 − loader/目录增量 − 指南增量与重复读取 − 额外发现/修复请求 − 缓存变化`

移入 playbook 的文字不是免费：一旦读取会随历史继续占输入；内容全部被加载之后，收益可能缩小甚至逆转。工具延迟加载和指南分层的收益也不能简单相加。

建议按序比较：

| 版本 | 变量 | 要回答的问题 |
|---|---|---|
| A | 当前直接工具 + 当前手册 | 基线 |
| B | 压缩说明，仍直接调用 | 不增加轮次能省多少，调用质量是否保持 |
| C | B + 按场景改写手册 | 是否减少无关正文、重复读取和错误分支 |
| D | C + 两个候选延迟，一次加载知识和工具 | 相对紧凑基线的额外收益是否覆盖发现与缓存成本 |

先确认 subagent_inline/event_manage 在真实工作分布中的频率；工具大不等于工具低频。如果 inline 根本不需要，现有配置开关就是更便宜的对照。保留核心文件操作、普通委派和 task 报告/提问/等待直接可见，不把所有工具改成“先问目录”。

行为探针优先复用已有 dev 集，再定向覆盖事件、角色/inline 分流、任务管理与步骤、跨回合续接。额外必须检查的组合包括：简单提醒、更新完整定义、定时任务模板、仅配置角色、无合适角色、task 禁用事件、一次性请求禁止后台工作、重载后继续、压缩后重读指南、结果未知时不重放副作用。开发诊断可以扩展同一场景链，不以新增永久用例数量为目标。

质量看目标完成、正确选路、参数修复、授权范围、幂等与交付证据；成本看整个会话的实际 input/cache/output token、指南读取量、额外模型请求、总耗时与已知费用。冷启动、暖缓存、短会话和两项工具都用过的长会话分开报告。不能以“成功调用 loader”替代用户目标完成。

纯描述与正文改动后跑 typecheck、unit，并执行受影响行为探针；接 session/发现机制后还要 deterministic e2e，重点扩展现有初始化/重载/恢复链，新增机制用例按项目规则做 mutation。真实模型运行先通过 oracle controls，失败证据保留。
