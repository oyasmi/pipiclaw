# Pipiclaw 设计哲学

> Pipiclaw 不是一个“会聊天的脚本”，而是一个让不可靠的模型能够长期、受约束地工作的运行时。

## 1. 把短暂的对话变成可恢复的工作

对话会中断，进程会重启，模型会忘记。真正的工作状态不能只存在于上下文窗口里，必须落在可阅读、可审计、可修复的持久化结构中：`SESSION.md` 保存当前工作状态，`MEMORY.md` 保存 durable memory，`HISTORY.md` 保存较旧的摘要，任务和冷日志保存恢复所需的证据。

因此，重启不应意味着“重新猜一遍”；下一次执行应能从文件、账本和明确的 wake 继续。

## 2. 运行时守住不变量，模型负责判断

模型适合理解意图、规划路径和处理例外，不适合独自维护并发、状态转移、预算、权限和恢复语义。队列、原子写、生命周期、确定性 gate、验证和 governor 属于 runtime；模型只在这些边界允许的范围内做判断。

Prompt、playbook 和 memory 是帮助模型做出更好判断的材料，不是安全边界，也不是状态机。凡是“必须成立”的事情，都应有代码或外部系统证据支撑。

## 3. 每一次自主都必须有边界

无人值守能力首先要能停止，其次才是能继续。每项长期工作都应有明确的范围、唤醒条件、预算、截止时间、可观察副作用和恢复动作；遇到不确定性时停下来并说明下一步，不用乐观猜测把任务推过终点。

Pipiclaw 的恢复语义是 at-least-once，而不是虚构的 exactly-once。凡是可能重复的外部动作，都必须通过稳定的操作标识、真实状态查询和幂等设计把重放变成安全行为。

## 4. 记忆要分层、克制、可追溯，也要允许遗忘

记住一切等于找不到重要的东西。记忆应有明确的作用域、来源、信任度、时效和敏感等级；写入要有证据，召回要有相关性，过期和遗忘要留下可解释的痕迹。频道隔离优先于“看起来更聪明”的跨频道共享。

记忆不是指令。来自历史、文件、网页和模型的内容都应按不可信数据处理；只有当前任务和 runtime 的真实契约拥有行动权。

## 5. 能力通过显式工具和契约进入系统

能力应有清楚的输入、输出、权限和失败语义。工具结果要结构化，错误要区分“模型可以自行修正的拒绝”和“用户必须知道的真实故障”；长输出必须保留可继续读取的路径。把能力塞进一段越来越长的 prompt，会让规则难以验证、难以升级、难以复用。

外部智能体也必须通过显式角色契约进入系统：启动命令、执行 runtime、读写声明、工作目录和时限都应可见、可审计。提示词里的“请只读”不能冒充 sandbox，`mutates` 声明也不能冒充权限控制。

## 6. 传输是端口，不是核心

Pipiclaw 以钉钉为第一运行场景，但 Agent 的工作语义不应被钉钉协议绑死。消息、进度、最终答复、媒体和生命周期通过 transport-neutral contract 连接；DingTalk、TUI 以及未来的其他入口共享同一套运行时原则。

## 7. 长期质量由结果证明，而不是由活动证明

调用次数、文件改动数、勾选的计划步骤和记忆条目数量，都不能单独证明工作取得进展。真正的质量指标是：重启后能否恢复，错误是否会止损，副作用是否可证明，记忆是否召回正确，重复任务是否越来越少走弯路。

## 一个总纲式的判断

新增任何能力前，先回答七个问题：真相存在哪里？重启后如何继续？并发时谁拥有写入权？失败时如何停止？花费如何受控？行动凭什么被证明？用户如何撤销或修复？答不清楚，就还不是完成的设计。
